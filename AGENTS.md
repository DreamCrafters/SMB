# Инструкции для AI-агентов

## Обязательный контекст

- Для задач в этом проекте использовать локальный skill `smb-monitor-project`, если он доступен.
- Перед изменением кода, архитектуры, документации или порядка задач читать `implementation_plan.md`.
- Перед изменением локального запуска, Docker, env или серверной инструкции читать `docs/local-server-run.md`.
- Перед изменением Google Sheets источников справочников читать `docs/google-sheets-source.md`.
- Считать `implementation_plan.md` актуальным планом реализации и обновлять его при изменении поведения, стека, архитектуры или очередности работ.
- Считать `docs/local-server-run.md` короткой инструкцией локального запуска и локального Docker, а `docs/google-sheets-source.md` — инструкцией по внешнему Google Sheets источнику справочников.

## Долговременные знания проекта

- Если в ходе запроса выясняется важное правило, которое должно влиять на будущие задачи, закреплять его в `AGENTS.md`.
- В `AGENTS.md` добавлять только устойчивые инструкции уровня подхода, безопасности, архитектурных границ, проверки и работы с данными.
- Не превращать `AGENTS.md` в журнал задач: детали реализации, временные решения и продуктовые очереди держать в `implementation_plan.md` или профильной документации.
- После любого изменения поведения, архитектуры, UI, контрактов или документации обновлять `implementation_plan.md`.
- В `implementation_plan.md` отмечать выполненные пункты, текущий активный пункт и ближайший следующий шаг.
- Не отмечать placeholder UI как готовую backend-функциональность: визуальный каркас, server boundary и реальные серверные данные должны быть явно разделены.

## Текущий стек

- Vite
- React
- TypeScript
- CSS без UI-фреймворка
- Backend workspace `server/` на Node.js + TypeScript
- Постоянная БД: MariaDB/MySQL

## Рабочий процесс

- Перед началом ответа писать в чате краткую оценку задачи. Сообщать выбранный уровень reasoning только когда MCP `reasoning-agents` доступен и глобальная маршрутизация действительно выбрала профилированного worker; если плагин отключён или недоступен, не выбирать уровень и не создавать заменяющий агент, чат или процесс.
- Сначала изучать существующую структуру проекта, соседние файлы, зависимости и уже принятые паттерны.
- Считать frontend и backend единым проектным контуром в одном репозитории: при изменении серверных контрактов, API, CORS/env, deployment-подключения, форм, сохранения данных или access/profile сразу обновлять все связанные части — `src/`, `server/`, типы контрактов, тесты и релевантные инструкции.
- Учитывать серверный сценарий обновления через Git: всё, что нужно для работы backend/frontend после `git pull`, должно быть внесено в tracked-файлы проекта; ручные действия на сервере допустимы только для непубличных `.env`, секретов, установки зависимостей, миграций и перезапуска сервисов, и должны быть явно описаны.
- `server/.env` находится в рабочем проекте и может правиться напрямую для runtime-настроек backend; секретные значения не выводить в ответы, логи или документацию.
- Расширять текущую структуру `src/App.tsx`, `src/content.ts`, `src/styles.css`, не создавать параллельные системы без необходимости.
- В React-обработчиках сначала синхронно копировать нужные `event.currentTarget.value`/`checked` в локальную переменную и только затем вызывать функциональный `setState`; запрещено читать `event.currentTarget` внутри callback вида `setState((current) => ...)`, потому что отложенное выполнение уже приводило к падению рендера и белому экрану.
- Все компактные модальные окна на `admin-db-modal-backdrop` должны закрываться только при нажатии на сам фон: нажатие внутри окна не закрывает его, а во время сохранения или другого выполняющегося изменения закрытие снаружи блокируется тем же guard, что и кнопка отмены.
- Перед локальным запуском Vite проверять слушатели `5173`/`5174` и не оставлять несколько frontend-процессов одного checkout. Если внешний браузер показывает старое поведение или частично потерянные стили при актуальных файлах сервера, сначала сравнить реально отданные CSS/JS через `curl`, затем проверить страницу на чистом origin/временном порту с принудительной пересборкой; исправление на новом origin означает устаревшую вкладку/HMR-состояние, после диагностики нужно остановить лишний процесс и вернуться к одному стандартному адресу `http://127.0.0.1:5173/`.
- Мобильные модальные окна должны ограничивать высоту относительно внутренней области backdrop после его отступов, а не напрямую через `vh`: иначе центрированное окно обрезается одновременно сверху и снизу на низком viewport или при открытой экранной клавиатуре. Верхний и нижний отступы backdrop обязаны учитывать `safe-area-inset-top` и `safe-area-inset-bottom`.
- Типы серверных контрактов, аккаунтов, доступов, статусов и показателей держать типизированными и централизованными.
- Не добавлять новые зависимости, backend, auth, chart-библиотеки, SDK интеграций или state manager без реальной задачи из плана.
- Backend-код держать в `server/`; не смешивать серверную валидацию, БД-запросы и API handlers с React/Vite frontend.
- Сохранять пользовательские изменения и не откатывать чужую работу.

## Данные и визуал

- В руководительской `Диспетчерская → Выработка` фильтры по марке в `Формовке` и `Сортировке` должны независимо и нормализованно искать внутри `facts`, исключать из найденной строки несовпавшие марки и пересчитывать суточный/месячный факт только по оставшимся маркам. План категории по маркам не распределять, поэтому при активном фильтре марочные строки не показывают план и отклонение.
- Административное разрешение рассылки хранить server-owned по паре `должность + тип сообщения` в `position_notification_permissions`, а персональные каналы — по паре `пользователь + тип сообщения` в `user_notification_settings`. Разрешение не выдаётся конкретному человеку: назначение должности сразу переносит на аккаунт её набор разрешённых рассылок. Вкладка `business.settings` не выдаётся должностям автоматически и включается администратором вручную как обычная рабочая вкладка. Во вложенной вкладке `Учётные записи → Уведомления` администратор выбирает должность и одним флажком `Вкл.` только разрешает ей тип уведомления; при каждом изменении этого разрешения персональные Email/MAX всех аккаунтов должности сбрасываются, а выключенный тип полностью скрывается из их настроек. Контакты остаются личными и редактируются отдельно для каждой учётной записи должности; там же администратор может включить её Email/MAX по каждому разрешённому типу — теми же правилами, что действуют в личной вкладке `Настройки`: канал доступен только при сохранённом контакте и только для разрешённого должности типа, а пользователь по-прежнему меняет свои каналы сам. Защита учётных записей и должностей на настройки рассылок намеренно не распространяется: любой администратор с `platform.manage_users` меняет разрешения и контакты рассылок в том числе у защищённого аккаунта и должности с правами админа. Единственная граница здесь — сама capability, а каждое изменение по-прежнему пишется в audit. Пользователь с вкладкой `Настройки` сам включает Email/MAX только для разрешённых типов и при наличии соответствующего контакта в `app_users`; удаление контакта снимает лишь недоступный персональный канал, но не административное разрешение. Персональные Email/MAX не импортировать из Google Sheets и редактировать только на сайте; экран `Учётные записи` разделять на вкладки `Учётные записи`, `Должности`, `Уведомления`. Клиент не определяет получателей: backend выбирает их по активной должности, статусу аккаунта, разрешению этой должности и персональному каналу. При передаче поручения Совета директоров на проверку отправлять Email/MAX всем возвращённым этой матрицей адресатам без дополнительного скрытого фильтра по должностям. Сбой внешней отправки после commit не должен откатывать сохранённое бизнес-действие и не должен блокировать другой канал; идентификаторы получателей не выводить в логи ошибок.
- В `ЦЗЛ → Химические анализы` свободную пробу выбирать единым server-backed combobox `Код лабораторной пробы`, без отдельного поискового поля. Ввод кода, номера или наименования передавать backend как `sampleQuery`, подсказки подписывать источником и датами и поддерживать клавиатурный выбор стрелками и Enter с закрытием по Escape, а после явного выбора хранить только стабильную ссылку `sampleSource + sampleId`. Ручная правка текста обязана сбрасывать прежний выбор; исправляемая связанная проба остаётся доступной как сохранённая опция, даже если обновление подсказок завершилось ошибкой.
- Для реестра `Огнеупорный цех → Вагоны` хранить необязательные server-owned `Садчик` и `Прессовщик`; строки без этих значений остаются читаемыми и исправляемыми. Раскрывающиеся списки обоих полей строить по текущей полной истории реестра и разрешать ручной ввод, а пустую новую форму заполнять из последней созданной записи. При выборе одного или нескольких вагонов в `Лаборатория → ОЦ → Качество сырцовой продукции` переносить марку, садчика и прессовщика из выбранного вагона с самой поздней датой садки; nullable значения не должны затирать уже введённые поля формы.

- В `ЦЗЛ → Регистрация проб` синхронизация дат всегда односторонняя: ручное изменение `Даты отбора` устанавливает такую же `Дату регистрации`, но отдельное изменение `Даты регистрации` никогда не меняет `Дату отбора`. Каждое последующее изменение даты отбора снова синхронизирует дату регистрации.
- В `ЦЗЛ → Регистрация проб` поле `Лаборант (отбор проб)` по умолчанию получает имя вошедшего пользователя, а после успешной первичной регистрации введённое значение становится значением следующих записей текущей frontend-сессии того же профиля; исправление истории этот выбор не меняет. Поле остаётся редактируемым и предлагает все уникальные ранее сохранённые значения из полной истории через manage-only form endpoint; новое сохранённое значение сразу добавлять в список.
- В `ЦЗЛ → Химические анализы` поле `Лаборант` следует тому же сессионному правилу: имя профиля является начальным значением, а непустое значение успешно созданного анализа переносится в следующие новые записи текущей frontend-сессии и сохраняется при переходе между вкладками; исправление истории этот выбор не меняет. Раскрывающийся список строить по уникальным значениям полной server-owned истории через manage-only form endpoint и сразу дополнять сохранённым значением.
- В `ЦЗЛ → Регистрация проб` поле `Место отбора пробы` по умолчанию получает место из последней созданной server-owned записи. Поздний ответ со списком мест не должен затирать уже начатый ручной ввод или более новое успешно сохранённое место. После первичной регистрации сохранённое место становится значением следующей записи; после исправления заново определять последнюю запись по server-owned истории, чтобы исправление самой свежей регистрации обновляло автоподстановку, а исправление более старой — нет.
- Истории всех текущих и будущих лабораторных журналов в рабочей вкладке лаборанта должны открывать исправление по клику на назначенную идентифицирующую колонку. Исправление выполняет только backend по стабильному server-owned `id`: текущая запись обновляется, а неизменяемые before/after-снимки с автором активной сессии и обязательное audit-событие сохраняются одной транзакцией. Руководительская вкладка и admin preview остаются read-only.
- Чётко отделять данные от визуального слоя.
- Все текущие и будущие табличные представления истории и журналов должны использовать общий контейнер `history-table-scroll`: ограничивать высоту таблицы, прокручивать её содержимое независимо от страницы по обеим осям и закреплять весь `thead` сверху. В ARIA-таблицах строка с `role="columnheader"` получает общий маркер `history-table-head`. Живые реестры и формы ввода не переводить на этот режим автоматически.
- При создании или доработке любой истории и любого журнала сортировать записи по основной дате и времени события по убыванию, чтобы самые свежие находились сверху. Иной порядок использовать только по явному требованию конкретного журнала.
- Все бизнес-данные, пользовательские данные, права доступа, аналитика, статусы, история, подтверждения и интеграционные payload должны храниться и проверяться на сервере.
- Клиент не должен быть источником истины: он запрашивает данные у сервера, отображает полученный ответ и отправляет пользовательские действия обратно на сервер.
- Во frontend допустимы типы контрактов, UI-состояния, состояние загрузки/ошибки и статический текст интерфейса; реальные бизнес-данные и демо-фикстуры с приватным смыслом не добавлять.
- Клиентские service-модули допустимы только как границы запросов к серверу; не добавлять в них fallback-данные, mock-ответы, локальные права или бизнес-фикстуры.
- Клиентские проверки доступа считать только UX-подсказкой. Защищённые действия всегда должны проверяться сервером.
- Временное отключение входа для учётной записи реализовывать через серверный `app_users.status` (`active`/`suspended`), а не через клиентское состояние: endpoint должен требовать capability `platform.manage_access`, при отключении отзывать все текущие сессии пользователя, запрещать отключение собственной активной учётной записи и не восстанавливать `archived` через обычный toggle.
- Удаление учётной записи в admin UI реализовывать как подтверждаемое серверное архивирование, а не физическое удаление исторических строк: установить `app_users.status = archived`, деактивировать все `account_accesses`, отозвать сессии и скрыть аккаунт из активного списка. Запрещать удаление текущей учётной записи.
- Защиту критичных учётных записей хранить в server-owned `app_users.is_admin_protected`, а для аккаунта с должностью, у которой включены права админа, вычислять ту же эффективную защиту по активному `account_accesses`. Только канонический аккаунт с нормализованным логином `admin` может включать или снимать явную защиту у других активных аккаунтов; сам `admin` всегда защищён. Для любого другого управляющего аккаунта backend обязан под блокировкой повторно проверять оба источника защиты и запрещать сброс пароля, смену должности, изменение пользовательских полей через общий редактор БД, включение/отключение входа, архивирование и изменение уведомлений защищённой записи. Capability и навигация сами по себе не дают права обходить защиту; frontend только показывает server-owned результат и отключает недоступные действия.
- Права админа должности хранить отдельно от технического `account_positions.is_protected` в legacy-колонке `account_positions.is_admin_protected`. Только канонический аккаунт с нормализованным логином `admin` может включать или снимать их; для `administrator` они включены постоянно. Права админа добавляют должности только `admin.accounts` и capabilities управления обычными аккаунтами, должностями и уведомлениями; корневые панели `admin.account_preview`, `admin.database`, `admin.user_actions` и соответствующие полномочия не выдавать. Для любого другого администратора backend обязан под блокировкой запрещать изменение названия, рабочих вкладок и порядка должности с правами админа, её удаление и назначение такой должности аккаунту. Frontend только показывает отметку `Права админа` и отражает server-owned ограничения.
- Матрица `Учётные записи → Должности → Доступ по вкладке` доступна только каноническому аккаунту `admin`. Она показывает аккаунты, но изменяет server-owned набор рабочих вкладок их должностей: строки аккаунтов одной должности всегда связаны, персональные overrides не создавать. Индивидуальное и массовое изменение должно одной транзакцией повторно проверять исходного `admin`, блокировать целевые должности, пересчитывать capabilities, синхронизировать `account_accesses`, отзывать затронутые сессии и записывать audit; конфликт блокировок с параллельным назначением должности повторять целиком. Отключать разрешено любую вкладку, включая последнюю: должность без рабочих вкладок — допустимое состояние, её аккаунты сохраняют вход и видят пустую рабочую область.
- Общий порядок пунктов левой панели хранить server-owned как одну полную последовательность всех известных `AccountNavigationItem`. Менять её может только системный администратор через корневую вкладку `admin.navigation` и capability `platform.manage_navigation_order`; делегированным администраторам эту вкладку и capability не выдавать. Каждый аккаунт видит только разрешённое ему подмножество пунктов, отсортированное по общей последовательности. Эта же последовательность определяет стартовый экран: при входе открывается первая доступная аккаунту вкладка левой панели, а не первый пункт жёстко заданного в коде каталога. Автовыбор срабатывает один раз за вход и отменяется любым переходом пользователя. Backend принимает только полный каталог без пропусков и повторов, а при появлении нового пункта добавляет его к сохранённому порядку без потери пользовательской перестановки.
- Админский просмотр и редактирование БД должны оставаться server-gated по capability `platform.manage_analytics_database`: frontend только отображает и отправляет действия через backend API, секреты и приватные payload не выводить в UI-логи или ответы. Каталог БД должен быть статическим allowlist русскоязычных прикладных представлений с безопасными пользовательскими полями; сейчас это пользователи и диспетчерские записи. Доступы и должности менять только через профильные admin-экраны с их полными правилами. Системные, auth-, архивные и append-only исторические разделы не показывать, но их данные не удалять; для текущих представлений запрещены удаление строк и массовая очистка. Запрещено отдавать клиенту `SELECT *`, password hashes, session IDs, dedupe/source keys, сырые dispatcher payload или неизвестные будущие таблицы. Описание редактора строки формирует backend: для диспетчерской записи это поля server-owned определения конкретной формы и понятные варианты выбора, без отображения технических ID/NULL/JSON. Диспетчерская запись показывает номер инцидента отдельной нередактируемой колонкой. Поиск по разделу выполняет backend по всем показанным колонкам представления и ни по одному скрытому полю: статус сравнивается по русской подписи из своего же списка вариантов, дата и отметка времени дополнительно по напечатанному дню, шаблон `like` экранируется, длина запроса ограничена, а счётчик строк и постраничная навигация считаются уже по отфильтрованному набору. Связующую идентичность записи (`reportDate`/`equipment`, номер закрываемого инцидента, связь выхода посетителя) через общий редактор не менять; изменение показателей оборудования обязано добавлять обычную ревизию полного дневного отчёта, а правка открытия инцидента обязана переносить дату/время, место, тип, критичность и описание в сохранённое закрытие того же номера, чтобы снятый при закрытии снимок не расходился с исправленным открытием. Изменение пользователя дополнительно требует `platform.manage_users`, его статуса — `platform.manage_access`; смена влияющих на доступ статусов отзывает затронутые сессии.

Ожидание этой блокировки внутри одного процесса сериализовать до получения соединения из пула, а закрытый HTTP-запрос удалять из очереди до получения соединения. Автора результата испытаний всегда брать из `ServerUserProfile.displayName`; клиентское значение автора игнорировать. Результат и обязательное audit-событие сохранять одной транзакцией, историю не перезаписывать. Печатный протокол формировать защищённым backend PDF-endpoint: постоянную шапку держать в server-owned шаблоне, условные строки определять отметками профиля сырья/готовой продукции из матрицы, свободный объект входящего контроля сопоставлять с профилем нормализованным вхождением, а при сохранении фиксировать снимок показателей и ГОСТов внутри payload результата. Заявка server-owned остаётся ожидающей и не входит в историю или итоги до решения кладовщика. Она read-only: backend разрешает по этой capability только профильные `GET`, включая шесть лабораторных журналов (`rotary-kiln-2-journal`, `sample-registration-journal`, `chemical-analysis-journal`, `unshaped-product-sample-journal`, `raw-material-quality-journal`, `green-product-quality-journal`), и защищённые PDF-протоколы; любые `POST`, `PATCH`, form-only endpoint, банки и остальные лабораторные действия требуют `business.manage_laboratory_results`. Вкладка не содержит форм ввода. - `Журнал печи 2` хранить отдельным append-only server-owned реестром под capability `business.manage_laboratory_results`: один ввод содержит все заданные параметры обжига, обязательный `Производимый материал` сразу после `Времени`, введённые имена мастера смены, обжигальщика и лаборанта, а authenticated session отдельно остаётся автором audit-события. `t в полевой камере`, `Проход ч/з сито 0,5` и `Загрузка печи в ковшах в час` необязательны при создании и исправлении: пустые значения сохранять как `NULL`, не подменять нулём и показывать `—` в обеих историях; остальные поля сохраняют прежнюю обязательность. Материал выбирается из общего `Журнала марок` и канонизируется backend-ом тем же путём, что остальные поля марок; записи, сохранённые до появления поля, читаются без материала и не участвуют в расчёте банок. Если в журнале есть хотя бы одна запись с материалом, форма подставляет материал последней такой записи и оставляет его после успешного сохранения; предыдущее значение берётся только из полной выборки журнала, а не из отфильтрованной истории, и любая ручная правка поля отменяет дальнейшую автоподстановку. Поля `Мастер смены` и `Обжигальщик` остаются редактируемыми, но предлагают отдельные раскрывающиеся списки всех уникальных ранее сохранённых значений соответствующего поля; варианты читать отдельным manage-only endpoint из полной истории, а не из ограниченной или отфильтрованной выдачи журнала, и не открывать руководительскому просмотру или admin preview. После успешного сохранения новое введённое значение должно сразу появляться в списке текущей формы. При первом открытии формы через отдельный manage-only draft endpoint читать последнюю фактически созданную запись из полной истории по `created_at desc, id desc` и один раз подставлять `Дату`, `Мастера смены`, `Обжигальщика`, `Лаборанта`, `Проход ч/з сито 0,5`, `Насыпной вес` и `Загрузку печи в ковшах в час`; для `Времени` подставлять значение той же записи плюс один час с сохранением минут и переходом `23:xx → 00:xx`. Дата и время самой записи не должны менять выбор источника, а ручной ввод любого из этих полей до завершения загрузки нельзя перезаписывать. Draft endpoint не открывать руководительскому просмотру или admin preview. После успешного сохранения значения новой записи сразу становятся источником следующей подстановки, включая расчёт нового `Времени`; остальные параметры очищаются или получают свои обычные значения. Запись и обязательный audit сохранять одной транзакцией. - `Регистрация проб` хранить отдельным server-owned реестром под capability `business.manage_laboratory_results`; в форме вводить реквизиты регистрации и отбора и необязательное `Водопоглощение`, сохраняя заполненное значение текстом для поддержки десятичной запятой, а пустое — как `NULL` с отображением `—`. В управленческой вкладке коды оставлять read-only. Form-only endpoint и исправление не открывать capability просмотра или admin preview. Исторические записи до появления показателя читать без него и показывать `—`; остальные химические значения не возвращать в форму регистрации. `Химические анализы` хранить отдельным append-only реестром: лаборант выбирает свободную пробу из `Регистрации проб` или `Проб неформованной продукции`, frontend передаёт дискриминированную server-owned ссылку `sampleSource` + `sampleId`, а backend до сохранения и повторно под блокировкой строки внутри транзакции проверяет существование пробы и отсутствие другого анализа. Уже связанная проба не показывается в раскрывающемся списке; одинаковые код, номер и наименование различать по источнику и датам. Список должен иметь server-side поиск по обоим полным журналам, чтобы оставались доступны записи старше окна последних 500 проб. В химическом анализе обязательна только ссылка на пробу; номер лабораторного анализа, номер партии, дата анализа, лаборант, все химические показатели и примечания необязательны. Следующий номер лабораторного анализа считать backend-ом по полной истории как максимальное полностью числовое сохранённое значение плюс один и отдавать через manage-only form endpoint; frontend подставляет его при открытии и после сохранения, но оставляет поле редактируемым и не перезаписывает ручной ввод. Пустой номер партии сохранять как `NULL`, не включать в audit-значения отправки и показывать в истории как `—`; при исправлении audit должен явно показывать переход между значением и `—`. Химические показатели сохранять текстом для поддержки запятых и квалификаторов вроде `< 0,1`; для `Al2O3`, `Fe2O3`, `SiO2`, `CaO2`, `P2O5` и `ппп` backend принимает только неотрицательное число с необязательным квалификатором верхней границы `<`, `<=` или `≤` и отклоняет создание или исправление, если сумма числовых значений больше 100. Запись, связь с пробой, синхронизацию read-only номера у неформованной пробы и обязательный audit сохранять одной транзакцией. Исправление анализа может переносить его только на другую свободную пробу и обязано очистить прежнюю связь; номер в регистрации получать из связанного анализа, а у неформованной пробы синхронизировать server-owned `chemical_analysis_number`. Один источник допускает не более одного нового анализа: репозиторий блокирует строку пробы, а таблица `laboratory_chemical_analysis_sample_claims` атомарно резервирует пару `sampleSource` + `sampleId`. Вагон выбирать только по стабильному server-owned `id` из реестра `refractory_wagons`: требуется хотя бы один вагон, порядок выбора сохраняется, а номера отображаются через `;`. При подтверждении отчёта его `reportDate` записывать как report-linked событие в той же транзакции, заменяя события логического ключа `firing + дата + смена` при подтверждённой корректировке. Для длины, ширины и высоты второе значение автоматически повторяет первое до первой ручной правки второго поля; backend независимо валидирует оба значения. Размеры, вес, механическую прочность и плотность хранить как неотрицательные десятичные строки с поддержкой запятой. Создание, исправление по стабильному `id`, неизменяемая before/after-ревизия и audit выполняются в одной транзакции; руководительский просмотр остаётся read-only и фильтрует наименование только по марке изделия.
- При множественном выборе вагонов в `Журнале контроля качества сырцовой продукции` разрешать только вагоны с одной и той же известной нормализованной маркой: frontend не отмечает несовместимый следующий вагон и показывает понятное предупреждение, а backend повторно проверяет набор до любого изменения журнала или audit. Вагоны без исторической марки не считать отдельной маркой, чтобы legacy-записи оставались доступными.
- В форме `ЦЗЛ → Химические анализы` постоянное предупреждение о сумме контролируемых показателей не более 100 показывать заметным красным полужирным текстом; точная проверка создания и исправления остаётся server-owned.
- Журнал действий пользователей хранить на сервере как append-only `user_audit_events`: автора всегда определять из authenticated/dev server session; платформенный отчёт защищать capability `platform.view_audit`, а опциональную вкладку руководителя `business.user_actions` — отдельной capability `business.view_user_actions` с обязательным server-side ограничением событий и списка аккаунтов организационным scope. Клиентские события просмотров принимать только по статическому allowlist вкладок и экранов и повторно сверять с доступами активного аккаунта; для admin preview разрешать только экраны, которые реально доступны через `admin.account_preview`. Значения отправленных форм формировать только по server-owned описанию полей. Production-запись бизнес-/административного изменения и обязательного audit-события выполнять через общий `DatabaseTransactionRunner` в одной транзакции; сбой аудита должен откатывать изменение, а email/MAX запускать только после commit. Узкое исключение допустимо только для идемпотентного исторического backfill из tracked DB-миграции: источник должен быть явно зафиксирован, данные и соответствующие audit-события записываться в одной транзакции миграции с явным `system-*` автором, а повторное выполнение не должно создавать дубликаты; интерактивные и последующие импорты всегда используют обычную authenticated/dev session и `DatabaseTransactionRunner`. Отчёт показывает максимум последние три календарных месяца, но это только окно выборки: более старые audit-события и связанные данные не удалять и не очищать автоматически.
- Вкладку `Поручения Совета директоров` считать server-owned реестром с отдельными capabilities просмотра, создания, исполнения и проверки. В настройке неадминистративной должности выдавать не более одного взаимоисключающего варианта этой вкладки: только просмотр; просмотр и создание; исполнение и отправка на проверку; либо создание, приёмка и возврат на доработку. Backend должен формировать capabilities из выбранного варианта, а не из названия должности; вариант приёмки включает создание поручений. Срок исполнения задавать структурированным расписанием: `daily`/`weekly`/`monthly`/`yearly`/`once`, дата начала и дата окончания; текстовый `due_date` сохранять только как производный снимок для отображения и совместимости. Просроченное исполнение остаётся активным до передачи на проверку. После приёмки повторяющегося поручения вычислять первую дату расписания после дня приёмки в пределах периода без накопления пропущенных повторов; месячные и годовые повторы привязывать к исходному дню с переносом на последний день короткого месяца. Пользователь с правом исполнения может переводить активное `В работе` или `На доработке` только в `На проверке`, а пользователь с правом приёмки — завершать или возвращать такое поручение. Каждый переход требует комментарий, который добавляется в append-only `board_assignment_comments` вместе с серверным автором, временем и полученным статусом в одной транзакции с изменением поручения и обязательным audit-событием. К живому незавершённому поручению пользователь с capability создания может прикрепить не более пяти PDF по 10 МБ каждый; хранить их в MariaDB/MySQL, проверять расширение, MIME и PDF-сигнатуру на backend, а загрузку и мягкое удаление проводить через authenticated endpoints с обязательным audit-событием. Удалённый из живого поручения файл сохранять для чтения из ранее зафиксированных снимков выполнения; публичные URL и физическое удаление исторического документа не использовать.
- Любой пользователь с capability `business.create_board_assignments` может редактировать все поля любого ещё не завершённого живого поручения независимо от автора; правка требует отдельный комментарий, добавляется в обычную историю комментариев, сохраняет before/after снимки в append-only ревизии и проходит одной транзакцией с audit-событием. Для повторяющегося поручения правка меняет только живую версию текущего и будущих исполнений и не меняет уже принятые периоды. При каждой приёмке до перехода к следующему повтору сохранять отдельный неизменяемый полный снимок выполненного периода со всеми полями, расписанием, датой исполнения и комментариями; историю выполнений читать только из этих снимков, а не восстанавливать из текущего состояния живой строки.
- Интерфейс `Поручений Совета директоров` строить отдельно под каждый вариант доступа, а не одной универсальной раскладкой: просмотр — спокойный read-only реестр; создание — явный первый шаг постановки поручения; исполнение — только карточки активных задач и одна прямая кнопка `Отправить на проверку`; приёмка — отдельная очередь ожидающих решения и прямые кнопки `Принять исполнение`/`Вернуть на доработку`. Не показывать выбор статуса там, где доступные переходы уже однозначно определены ролью и текущим состоянием.
- Админский `Предпросмотр` считать режимом входа в выбранную должность, созданную учётную запись или отдельную рабочую вкладку. Показывать эти варианты тремя подвкладками `Типы аккаунтов`, `Созданные аккаунты` и `Вкладки`; для первых двух использовать server-backed каталоги, чтобы созданный в текущей сессии аккаунт появлялся при следующем открытии панели, а для третьей — единый каталог поддерживаемой рабочей навигации. Переиспользовать единое рабочее пространство, реальную навигацию, формы и guards выданных рабочих вкладок, а не отдельные урезанные mock/preview-копии. Сама вкладка `admin.account_preview` не должна порождать изменяющие `business.*` capabilities: backend разрешает по ней только GET рабочих данных, а POST/PATCH/DELETE по-прежнему требуют реальные capabilities вошедшего аккаунта. В превью смешанной должности исключать `admin.*` и `platform.*`, чтобы режим просмотра не открывал реальные административные действия; карточки без рабочих вкладок показывать, но не открывать до появления production impersonation/audit-модели.
- Локальный Vite middleware в `vite.config.ts` считать только dev/preview server boundary, а не production backend и не БД; не обещать сохранность данных, пока не подключено постоянное серверное хранилище.
- Для действий, которые должны сохраняться в удалённой БД, использовать remote API boundary; исключение допустимо только для явно тестового fallback: временная dev-сессия в `sessionStorage` для входа в интерфейс и диспетчерские отправки в `localStorage`, когда сервер или `/api` хостинга не настроены или недоступны. - Постоянное хранение реализовывать через backend workspace `server/` и MariaDB/MySQL; изменения схемы делать через миграции, а не ручные ad-hoc SQL правки в коде обработчиков.
- Каждое новое MariaDB/MySQL-соединение backend-а обязано устанавливать session `time_zone = '+00:00'`: Jino работает с `SYSTEM = UTC+3`, поэтому одной настройки драйвера `timezone: "Z"` недостаточно и без UTC session абсолютные `timestamp` (включая `auth_sessions.expires_at`) сохраняются со сдвигом на три часа.
- Каждый deployment обслуживает ровно одну организацию. Сущности выбора или управления бизнесами, tenant ID и `businessAccountId` в runtime-контрактах и схеме быть не должно; для другой организации разворачивать отдельный экземпляр сайта со своей БД.

Администратор имеет platform scope, все неадминистративные аккаунты — organization scope. Технические ID и scope-defaults формирует backend, frontend не должен требовать их ручного ввода. Повторный логин при создании отклонять без изменения существующей записи; для смены пароля использовать отдельный reset-flow. Список учётных записей сортировать сначала по server-owned порядку должностей, затем по имени пользователя, чтобы одинаковые должности шли подряд.
- Должность пользователя хранить отдельно от технического `accountType`. Для всех должностей использовать единое рабочее пространство, способное переключаться между выданными вкладками; исторические значения `business_owner`/`worker`/`dispatcher` допустимы только как внутренняя совместимость и для специальных session-правил, но не должны ограничивать навигацию или выбирать отдельный UI. Доступ к вкладкам левого rail хранить в server-issued access как стабильные ID и синхронизировать с server-side capabilities; изменение вкладок или прав админа должно отзывать активные сессии пользователя. В форме должности разрешать выбирать только `business.*`; `admin.accounts` вычислять из server-owned прав админа, а остальные `admin.*` оставлять только системной должности исходного администратора. Запрещать смену должности любого access текущего вошедшего пользователя; в UI применять выбор только отдельной кнопкой сохранения и объяснять, что изменённому пользователю нужно войти заново.
- Должность является server-owned источником названия, `navigation_items`, вычисленных capabilities и единого порядка отображения; аккаунт хранит только ссылку на назначенную должность и наследует её доступы. Порядок администратор меняет полным упорядоченным списком, и backend применяет его к каталогу должностей, аккаунтам, вариантам выбора должности и preview/dev-спискам; новую должность добавлять в конец. В UI `Должности и доступы` ручной кнопки сохранения порядка нет: после перемещения отправлять только итоговый полный список через 5 секунд без новых перемещений, сбрасывая задержку при каждом следующем действии; отмена до отправки должна очищать ожидающее изменение. Фоновое обновление аккаунтов/каталога не должно стирать ожидающий порядок, изменения состава должностей до его сохранения нужно блокировать, а сетевые и серверные ошибки `5xx` — повторять с той же пятисекундной задержкой до успеха, нового перемещения или отмены. Поле базового кабинета в API и UI должности отсутствует. Новая неадминистративная должность получает внутренний совместимый тип только на backend-е, а при редактировании существующей должности её технический тип не меняется. Изменение должности должно отзывать активные сессии всех связанных аккаунтов.
- Любую неадминистративную должность, включая созданную миграцией или другим программным способом, разрешено удалять только при `usageCount = 0`, выключенных правах админа и после явного подтверждения. Происхождение должности и технический флаг `isProtected` не должны запрещать удаление свободной обычной должности; должность администратора, должность с правами админа и назначенные аккаунтам должности не удалять. Проверку выполнять в UI, API и транзакционно в repository; связь `account_accesses.position_code` должна оставаться защищённой внешним ключом `ON DELETE RESTRICT`.
- Любая неадминистративная должность может сочетать любые рабочие вкладки: `Обзор`, `Диспетчерская`, `Работа`, `План выработки`, `Действия пользователей` и `Форма`. Backend обязан отклонять неизвестный или содержащий `admin.*` пользовательский набор, но пустой набор рабочих вкладок допустим для любой должности: должность с правами админа так не получает лишний доступ к бизнес-данным, а обычную должность администратор может полностью закрыть, не удаляя её и её аккаунты. Отключение прав админа у должности без рабочих вкладок разрешено и оставляет её без доступов. Канонический login `admin` отдельно включает права админа для должности; backend производно добавляет только `admin.accounts`, `platform.manage_users` и `platform.manage_access`. Другие администраторы могут менять рабочие вкладки только обычных должностей без этой отметки и не могут назначать аккаунтам должности с правами админа. Системные неадминистративные должности разрешено редактировать по тем же правилам, системного администратора — нет. В форме должности показывать только секцию `Рабочие вкладки`, а отметку `Права админа` — отдельной колонкой общего списка, доступной только исходному `admin`.
- Диспетчерская анкета `Оборудование` хранит дневное состояние оборудования: запись уникальна по `Дата отчета` и оборудованию в общей истории организации; повторная отправка обновляет существующую запись, пишет запись изменения дневного отчёта в `dispatcher_equipment_report_revisions`, клиентские UX-черновики и локально внесённые кнопкой `Внести данные` позиции должны быть привязаны к выбранной дате отчёта и оборудованию, переключение даты должно показывать сохранённые в БД данные именно выбранной даты и не переносить статус заполненной иконки с другого дня, переключение оборудования не должно копировать значения между позициями, кнопка `Внести данные` добавляет выбранную позицию в дневной пакет, а `Отправить отчет начальству` активна и отправляет отчёт только когда внесены все позиции оборудования; backend и локальный fallback должны отклонять неполный equipment batch; причина простоя требует время простоя больше 0, время простоя больше 0 требует причину простоя, причина простоя `Резерв` допускает только 8 часов простоя, простой за смену не может быть больше 8 часов, а простой меньше 8 часов требует выработку больше 0.
- Диспетчерская форма `Выработка` является server-owned дневной сводкой: дата отчёта обязательна, дополнительно нужен хотя бы один показатель. Диспетчер вводит суточный факт, марку изделия, суточные показатели фракций грануляции, а в блоке `Замеры банок` — до четырёх замеров каждой банки, `Засыпали`, `Отгрузили` и обязательного мастера ЦОШ. Первый замер каждой банки обязателен; план, поля месяца, отклонения, расход, среднее, плотность, объём и расчётные веса вручную не вводятся. Таблицу строить по образцу `Банки!G1:K17`; frontend показывает live-пересчёт, но backend при сохранении заново читает текущие назначения банок, последние плотности `Журнала печи 2` и справочник объёма, удаляет присланные производные `jarStart*`/`jarEnd*`/`jarShipmentStart*`/`jarShipmentEnd*` и сохраняет собственный снимок расчёта. Начало дня по замерам брать из конца сводки предыдущей календарной даты, начало дня по отгрузкам — из конца последней сводки строго раньше даты отчёта, конец дня по обоим весам — из текущего серверного расчёта. Подтверждённую сводку ЦОШ выбранной даты разрешено использовать только для начального заполнения legacy-отчёта; в обычной диспетчерской форме поля редактируемы, а в admin preview остаются read-only. История `Диспетчерская → Выработка → Замеры банок` обязана создавать строку при наличии любого из четырёх итоговых значений, показывать начало, конец и расход отдельно `По замерам` и `По отгрузкам` и считать оба набора итогов; отчёты только с `jarShipment*` не скрывать. В полной таблице выбранной даты показывать сохранённое в диспетчерской ревизии содержимое банки, а для legacy-записи без снимка — текущее назначение Лаборатории. Формовка, сортировка, неформованная продукция и шамот используют один общий `Журнал марок` и одинаковые горизонтальные таблицы: диспетчер добавляет марочные столбцы с полем `Факт за сутки`, каждый столбец обязан ссылаться на марку общей номенклатуры, а повтор марки внутри категории запрещён. Любой заполненный факт категории, включая `0`, требует выбранную марку, а выбранная марка требует заполненный факт; это правило проверяют frontend перед отправкой и backend. Для фактов формовки и сортировки первое `mousedown` по ещё неактивному полю должно отменять только нативный повторный шаг и синхронно ставить фокус; повторные нажатия по уже активному полю оставлять браузеру для обычной установки каретки. Переход между этими полями не должен запускать React-обновление или замену DOM-узла на `blur`. Новую марку диспетчер не создаёт: добавление и исправление доступны только в `Лаборатория → Марки`; backend канонизирует метку при отправке по текущему журналу. Месячные факт и план категории рассчитывать с первого дня календарного месяца по дату отчёта включительно по последней записи каждого дня, отклонение считать как месячный факт минус месячный план, расход банки — как начало дня минус конец дня. Для live-расчётов backend возвращает накопительный план выбранной даты и сохранённый месячный факт только предыдущих дней; frontend добавляет сумму текущих черновых фактов марочных столбцов, показывает read-only `План за месяц`, `Факт за месяц` и `Отклонение` и не добавляет эти значения в payload. Поэтому сохранённый факт редактируемого дня не учитывается дважды. Старые отчёты с одиночными полями формовки и сортировки продолжают читаться и при следующей отправке преобразуются в динамические марочные поля. Аналитика сохраняет накопленный месячный факт каждой динамической марки, не распределяя по маркам план категории. Расчётные таблицы формирует backend, а frontend только фильтрует и отображает строки; исключение — арифметическое добавление ещё не сохранённого суточного факта к server-owned месячному факту предыдущих дней. Локальный test fallback повторяет доступные расчёты лишь для явно тестового режима.
- В субботу и воскресенье диспетчер может отправить `Выработку` с заполненной `Сортировкой` и без факта `Формовки`: незавершённую строку Формовки с выбранной маркой, но пустым фактом считать пустой и не сохранять. Факт Формовки без марки по-прежнему отклонять; на рабочих днях и для остальных категорий требование полной пары `марка + факт` не ослаблять. Одинаковое правило применять в UI, локальном test fallback и backend.
- Месячный план выработки вводит должность `Экономист` через отдельную server-gated вкладку `business.production_plan` с capability `business.manage_production_plan`. На месяц предусмотрены четыре независимых положительных плана с точностью не более двух знаков после запятой: формовка, сортировка, неформованная продукция/контейнеры и цех обжига шамота; интерфейс принимает точку и запятую, нормализуя запятую в точку. План категории является суммой по всем её маркам и не хранится на уровне марки. Экономист свободно выбирает месяц и любую категорию, а каждая категория сохраняется отдельно и сразу обновляет составную месячную сводку. Категория имеет собственный подтверждаемый календарь: экономист выбирает пресет `Все дни` или `Только рабочие` (понедельник–пятница), а затем может вручную добавить или убрать любую дату. Для каждой категории до предпоследнего подтверждённого дня ставить целое значение `ceil(месячный план категории / количество дней)`, на последний — точный остаток с точностью до сотых без отрицательного значения. Каждое сохранение категории блокирует последний снимок выбранного месяца, добавляет составную append-only ревизию и обязательное audit-событие в одной транзакции, чтобы параллельные изменения разных категорий не затирали друг друга; frontend не рассчитывает и не хранит сохранённый итоговый план самостоятельно. Диспетчерская форма читает с сервера дневные и накопительные планы вместе с сохранённым месячным фактом предыдущих дней, показывает `Не задан` для категории без плана и не добавляет расчётные значения в payload.
- Вкладку огнеупорного цеха хранить как назначаемый navigation item `business.refractory_shop`, а не как фиксированную должность или отдельный тип аккаунта. Она содержит три независимо сохраняемые и подтверждаемые таблицы: `ЦОШ`, `Сводка по работе оборудования`, `Печное отделение`. Ключ таблицы — `reportType + reportDate + shiftNumber`; смена 1 длится `08:00–20:00`, смена 2 — `20:00–08:00`, а дата ночной смены равна дате её начала. Большая таблица оборудования должна сохранять первый столбец `Оборудование` закреплённым слева при горизонтальной прокрутке и использовать отдельные компактные ширины для числовых и текстовых колонок с переносом длинных заголовков. В ней выпуск продукции выделять светло-зелёным, простои — светло-красным, а `Простой всего` располагать сразу после отработанных часов. В печной таблице `Брак всего` располагать перед видами брака и использовать термин `Выплавка`. Все широкие таблицы ОЦ должны сохранять постоянно различимую горизонтальную полосу в отдельном нижнем пространстве, не перекрывающем последнюю строку; ЦОШ и сводка оборудования используют ограниченный по высоте контейнер, а `Выпуск обожжённых огнеупоров` показывается полностью по вертикали без внутренней вертикальной прокрутки. Числовые поля всех трёх таблиц должны фильтровать посторонние символы при вводе, принимать запятую как десятичный разделитель, отдельно ограничивать целые значения и локально проверять server-owned диапазоны и точность; перед отправкой неверные поля помечать `aria-invalid`, визуально выделять и описывать русскими подписями из таблицы без технических ключей payload, сохраняя ту же обязательную проверку на backend-е. Сообщения должны различать неверный числовой формат, выход за диапазон и превышение трёх знаков после запятой, а общий заголовок и каждую отдельную ошибку показывать с новой строки. При отклонении отправки backend возвращает безопасный массив типизированных деталей `fieldPath + message`, по которому frontend повторно помечает соответствующие видимые поля, не разбирая локализованный текст; одиночным показателям нельзя приписывать фиктивный номер строки, а повторяющиеся подписи ЦОШ должны сохранять название раздела. Каждая отправка создаёт append-only pending-ревизию; диспетчер с `business.review_refractory_reports` открывает очередь отдельной кнопкой на экране выбора форм, подтверждает или возвращает каждую таблицу отдельно, возврат требует комментарий, в режиме возврата кнопку подтверждения скрывать, диспетчер не редактирует значения и не подтверждает собственную отправку. Счётчик на отдельной кнопке, badge левого rail и toast должны сразу показывать появление pending-таблиц, но сами таблицы не выводить над обычными диспетчерскими формами. Аккаунт с `business.submit_refractory_reports` должен глобально опрашивать только свои актуальные pending/rejected и недавно подтверждённые ревизии: переход pending → approved показывает toast о принятии, pending → rejected — toast с причиной возврата, а открытый экран ОЦ сразу перечитывает актуальный статус. Вкладка `business.refractory_shop` в левом rail должна показывать красный badge с количеством актуальных rejected-ревизий без временного ограничения, которые ещё не заменены повторной отправкой; внутри ОЦ тот же счётчик нужно разбивать по трём кнопкам таблиц, показывая красную цифру только у типов с актуальными возвратами. Возврат наружу не рассылать, а сбой одного канала не должен откатывать сохранение/решение или мешать второму каналу. Подтверждение пока не запускает аналитику.

- Внутренняя вкладка Лаборатории `Банки` управляет текущим содержимым банок I–III: лаборант выбирает материал из журнала печи 2, а насыпной вес банки backend считает средним по последним десяти записям `bulk_density` этого материала; пока записей меньше десяти, усредняются все накопленные. Материал без записей журнала и неположительное среднее отклонять. Клиент не передаёт насыпной вес и не выбирает результат испытаний. Для каждой банки дополнительно сохранять неотрицательные `Засыпали` и `Отгрузили`, а второй вес считать server-owned как `предыдущий вес по отгрузкам + засыпали − отгрузили`; отрицательный остаток отклонять и показывать в отчётах пару `по замерам / по отгрузкам`. Это два параллельных расчёта: вес по замерам всегда пересчитывается от текущих замеров, а вес по отгрузкам ведёт собственную цепочку от предыдущего значения этой же банки (для сводки ЦОШ — последняя подтверждённая ревизия строго раньше её даты и смены, для диспетчерской выработки — последняя сводка строго раньше даты отчёта). Пропущенный день цепочку не рвёт: база ищется по дате отчёта, а не по предыдущему календарному дню. Начало дня по замерам, наоборот, остаётся привязанным ровно к предыдущей календарной дате — без её сводки поле остаётся пустым. Отсчётная точка цепочки — смена материала в банке: накопленный баланс принадлежит прежнему содержимому, поэтому при другом материале в предыдущей записи, при её отсутствии и на legacy-записях без сохранённого материала цепочка начинается заново с нуля. Вес по замерам в неё не входит ни на старте, ни дальше: это два полностью параллельных расчёта, и вес по отгрузкам складывается только из движений «Засыпали» и «Отгрузили». Материал сравнивать по наименованию, нормализованному по регистру и пробелам, а не по идентификатору назначения: повторное назначение того же материала не считается сменой содержимого. Фактическую базу сохранять вместе с расчётом (`shipmentBaseTons` в снимке ЦОШ, `jarShipmentStart` в диспетчерской выработке), чтобы расход по отгрузкам оставался равен `отгрузили − засыпали` и после смены материала. Предыдущее значение остаётся server-owned: клиент получает его только для live-предпросмотра и никогда не передаёт в payload. Отправку блокировать, если хотя бы одна банка не назначена или её первый замер пуст; нулевой объём и нулевую массу разрешать. Legacy-ревизии с дополнительными замерами сохранять полностью читаемыми в заблокированном режиме, а при создании исправления переносить в новый ограниченный payload только первые четыре значения.
- Общий badge вкладки ОЦ в левом rail остаётся глобальным по всем актуальным возвратам аккаунта и рядом перечисляет каждую уникальную дату и смену, в которые нужно зайти для исправления. Красные badge трёх внутренних кнопок всегда ограничивать выбранными `reportDate + shiftNumber`: возврат другой даты или другой смены на текущем экране не показывать.

Мобильное меню должно закрываться после выбора раздела, по кнопке закрытия внутри drawer, по клику на затемнение и по `Escape`, удерживать клавиатурный фокус внутри до закрытия и использовать `aria-expanded`/`aria-controls`; не создавать отдельные role-specific реализации навигации.
- Подтверждения успешных действий во всех кабинетах показывать через общий фиксированный toast-стек в правом нижнем углу поверх страницы, а не inline-блоком в потоке документа: появление уведомления не должно менять высоту контента или позицию прокрутки. При фоновом обновлении после такого действия сохранять уже показанный список или таблицу до получения нового ответа, чтобы временный loading-state не схлопывал страницу; состояния загрузки, ошибки и подсказки валидации оставлять рядом с соответствующим действием.
- Toast-уведомления всегда получают явный семантический тип: `warning` отображается красным для предупреждений, ошибок, просрочки и возврата на доработку; `suggestion` — жёлтым для предложений, напоминаний и ожидающих внимания действий; `success` — зелёным для приветствий, информационных подтверждений и успешно выполненных действий. Автоматически через четыре секунды закрывать все и только `success`; `warning` и `suggestion` оставлять до ручного нажатия на крестик. При удалении карточки оставшиеся уведомления должны плавно занимать освободившееся место; для FLIP-анимации фиксированного снизу стека сравнивать экранные координаты `getBoundingClientRect()`, а не локальный `offsetTop`. Не определять тип по тексту заголовка или сообщения.
- Первичную загрузку страницы, раздела, формы, справочника или доступа и ожидание отправки показывать через общий `LoadingIndicator` с размером по контексту, короткой понятной подписью и `role="status"`; не создавать отдельные спиннеры для каждого экрана и обязательно отключать движение через `prefers-reduced-motion`.
- Все уведомления, тосты, ошибки и статусные подсказки для неадминистративных пользователей должны быть максимально короткими и понятными: без id отправок, endpoint, CORS, `/health`, `localStorage`, remote/backend/server/feed и другой технической диагностики. Технические детали допустимы только в админских инструментах, логах, тестах и инструкциях настройки.
- Для иконок оборудования считать серверные отметки выбранной `Дата отчета` отдельным источником истины: при смене даты заново запрашивать dispatcher feed по payload `reportDate`; старые локальные данные без серверной записи могут показываться как `Черновик`, но не как `Внесено в отчёт`. Визуально `Нет данных` — серый фон и тёмно-серый текст, `Черновик` — серый фон и чёрный текст.
- Поля `Место (цех/участок)` и `Ответственный за регистрацию` в анкете `Открытие инцидента` обогащаются backend-ом из Google Sheets через `GET /api/dispatcher/forms`: источник работает либо как публичный CSV, либо как закрытая таблица через service account JSON на сервере; при `GOOGLE_SHEETS_CACHE_TTL_MS=0` справочник перечитывается при каждом запросе форм, при недоступности источника поле остаётся обычным текстовым вводом. В обычном диспетчерском аккаунте ответственным по умолчанию считать `ServerUserProfile.displayName` и добавлять это имя в варианты текущей формы, даже если его нет в Google Sheets; в admin preview использовать первый вариант справочника и не подмешивать имя просматриваемого аккаунта.
- Анкета `Закрытие инцидента` должна начинаться с отдельного экрана выбора: незакрытые сохранённые инциденты показываются обычными кнопками, а после выбора открывается существующая анкета закрытия с server-owned номером в скрытом поле и заметной карточкой выбранного инцидента; должна оставаться возможность вернуться и выбрать другой инцидент. Временная ошибка фонового обновления списка не должна размонтировать заполненную анкету; если успешное обновление подтверждает, что выбранный инцидент уже закрыт, UI возвращается к списку с коротким объяснением. Инциденты не закрываются автоматически в конце дня и могут быть закрыты в любой момент после открытия; backend и локальный fallback обязаны отклонять закрытие отсутствующего или уже закрытого номера, свободный ручной ввод номера не должен быть основным UX. Идемпотентность закрытия определять по паре `номер инцидента + дата/время закрытия`, чтобы точный повтор не создавал дубль, а ошибочная историческая запись закрытия, которая предшествует открытию, не блокировала новое корректное закрытие того же номера.
- После каждого успешного явного входа аккаунта с назначенной вкладкой `business.dispatcher_form` показывать один раз информационное окно с количеством незакрытых инцидентов из server-owned `openIncidents`; восстановление уже действующей сессии и admin preview не должны считаться новым входом. Кнопка перехода должна открывать существующую форму `incident_close`, а продолжение — только закрывать окно.
- Email/MAX-уведомления по открытиям и закрытиям инцидентов, посетителям, отчётам оборудования и выработке отправляются backend-ом только после успешного сохранения и получают адресатов из server-owned `user_notification_settings` с отдельными типами `incidents`, `visitors`, `equipment_reports` и `production_reports`; прежние Google Sheets колонки адресатов для этих сообщений больше не являются production-источником. Сообщение о закрытии инцидента должно быть самодостаточным и после номера показывать в порядке открытия исходные дату/время, место, тип, критичность и описание, затем введённые при закрытии корневые причины и предотвращающие меры, дату/время закрытия и утвердившего; исходные значения backend переносит из сохранённого открытия, а локальный test fallback повторяет то же правило. В сообщении о выработке замеры банок выводить одним блоком `Содержимое банок:` — по строке на банку вида `- Банка N (содержимое), начало дня, по отгрузкам: A; по замерам B, на конец дня C / D` и отдельной строкой `Мастер ЦОШ`; остальные поля блока `Замеры банок` в текст не попадают. Содержимое банки брать из снимка самой сводки, а текущее назначение Лаборатории использовать запасным источником; отсутствующее значение показывать как `—`, а сводку без полей банок оставлять вовсе без этого блока. Отчёт оборудования отправлять одним сообщением на весь дневной пакет через `/api/dispatcher/equipment-report`; одиночный `/api/dispatcher/submissions` для `equipment` не должен рассылать уведомления, чтобы не создавать спам. Новые pending-таблицы ОЦ по-прежнему отправлять диспетчерам из строк `2–20` Google Sheets колонок `Адресаты Диспетчеры (емейлы)`/`Адресаты Диспетчеры (МАКС)`, а подтверждённые таблицы — адресатам колонок `Адресаты ОЦ (емейлы)`/`Адресаты ОЦ (МАКС)` только после commit решения. Для backend-среды `SMB_APP_ENV=test` каждое Email- и MAX-сообщение завершать отдельной строкой `Примечание: Тестовое сообщение`; production-сообщения не помечать. SMTP/MAX-секреты держать только в `server/.env`, сбой внешней отправки не должен откатывать сохранённую форму или ревизию ОЦ. Если Jino/Node не доверяет сертификату `platform-api2.max.ru`, добавлять доверенный PEM через `MAX_CA_CERT_FILE`, а не отключать TLS глобально.
- Google Sheets справочники должны влиять только на новые варианты выбора; отправленные dispatcher submissions обязаны хранить выбранные значения в payload как исторический снимок, чтобы удаление или изменение строки в Google Sheets не ломало старую аналитику.
- В таблицах огнеупорного цеха все поля `Марка изделия` получать через единый server-gated `Журнал марок`. Один поисковый список доступен в сводке оборудования, выпуске неформованных огнеупоров и печном отделении; сохранённую ранее марку оставлять историческим значением ревизии.
- Исторический импорт Google Sheets вкладок `Оборудование`, `Инциденты` и `Посетители` выполнять только через server-gated admin preview/confirm flow в существующий `dispatcher_submissions`. Все записи относятся к единственной организации deployment-а. Сохранять исходные даты/время, не запускать email/MAX, не перезаписывать существующие строки и обеспечивать идемпотентность одновременно по source key и нормализованному содержимому записи. Одинаковые строки внутри одной книги, в повторном импорте или в копии книги должны схлопываться до одной записи, а единый для import/live уникальный `dedupe_key` должен защищать от параллельных импортов и одновременной live-отправки. Legacy-нарушения текущих правил показывать как предупреждения предпросмотра, а структурные ошибки не скрывать.
- Диспетчерские формы посетителей разделены на `Вход посетителя` и `Выход посетителя`: вход запрещён для посетителя с тем же ФИО/организацией, который уже вошёл и ещё не вышел; выход выбирается из всех открытых входов независимо от их даты и не должен вручную дублировать поля посетителя. Незакрытый вход датой не сгорает: отметить выход можно и на следующий день, как и закрыть инцидент прошлого дня. При входе диспетчер получает окно с числом незакрытых инцидентов и числом посетителей без отметки выхода; окно показывается, только если есть хотя бы одно из двух, и ведёт прямо в нужную форму.
- Выбор диспетчерских форм должен оставаться сгруппированным по смыслу и визуальному акценту: `Оборудование`, `Инциденты`, `Посетители`.
- `Обзор` владельца должен сохранять компактные блоки оборудования, выработки и последних посетителей. Server-owned сводка считает за текущий месяц и сегодня: лабораторные результаты, отобранные пробы, химические анализы и показания `Журнала печи 2`; формовку, сортировку, неформованную продукцию, шамот и грануляцию. Грануляция складывает две действующие фракции `16/30` и `12/18`, а новый месяц без записей начинается с нулей. Посетителей строить из общей сохранённой dispatcher-истории: выход сначала связывать по server-owned ID, а если такого входа нет — по нормализованной паре ФИО + организация для legacy-данных; существующую корректную ID-связь этим fallback не заменять. Старые подробные карточки последнего открытия и последнего закрытия инцидента не возвращать: их заменяет новая сводка `Инциденты`, а детали остаются во вкладке `Диспетчерская`. Закрытие инцидента по-прежнему должно получать тип и место из server-owned payload либо связанного открытия с тем же номером; backend обязан переносить оба значения в payload новых закрытий.
- Вкладка владельца `Диспетчерская` должна показывать 4 раздела, а не сырую форму-фильтрацию: расчётные таблицы выработки, агрегаты оборудования, объединённый список открытия/закрытия инцидентов с незакрытыми к началу периода и список посетителей. Внутри выработки держать отдельные кнопки-таблицы для формовки, сортировки, неформованной продукции, цеха обжига шамота, замеров банок и участка грануляции; дата строки открывает полный дневной отчёт. Все разделы используют единый выбор периода `Сегодня`, `Текущий месяц`, `Текущий год`, `Своё`; месяц и год считаются от начала периода по сегодняшний день, а `Своё` по умолчанию оставляет обе даты пустыми и показывает данные за всё время. История владельца должна автоматически дочитываться страницами через backend, а не молча обрезаться лимитом одной страницы; периодический polling после полной загрузки обновляет только последнюю страницу и повторяет полный проход лишь при рассинхронизации количества записей.
- В remote/server-PC/VPS режиме открывать в сеть только backend API; MariaDB/MySQL держать доступной только локально для backend или по явно разрешённому IP, не публиковать порт `3306` наружу без отдельного осознанного решения.
- Test и production считать двумя средами одного кода, а не двумя расходящимися приложениями: текущий Jino-вариант деплоит оба домена из одной ветки, frontend собирается два раза через `npm run build:web:test` и `npm run build:web:production`, а backend runtime остаётся раздельным по доменам из-за разных `server/.env`, `DATABASE_URL`, cookie name и БД. В production всегда `SMB_APP_ENV=production`, `VITE_SMB_APP_ENV=production`, `DEV_ACCESS_ENABLED=false`; dev-session endpoints, role-picker и клиентские `sessionStorage`/`localStorage` auth/data fallback не должны работать как production-auth или production-хранение.
- Полную синхронизацию production → test считать отдельной разрушительной test-only операцией: backend требует `SMB_APP_ENV=test`, capability `platform.manage_analytics_database`, явный `PRODUCTION_SNAPSHOT_ENABLED=true`, отдельный read-only `PRODUCTION_DATABASE_URL`, точное совпадение `PRODUCTION_SNAPSHOT_TARGET_DATABASE` с test `DATABASE_URL` и разные имена source/target БД. До мутации проверять равенство таблиц, DDL и `schema_migrations`, отсутствие триггеров и InnoDB для всех таблиц. Все записи test-backend, migration/auth CLI и синхронизацию сериализовать общим server-wide advisory lock; строки всех таблиц заменять внутри одной транзакции без `DROP/CREATE`, чтобы ошибка или остановка процесса сохраняла прежнее состояние test. Production использовать только для чтения, test полностью заменять снимком данных, а в том же коммите оставлять `auth_sessions` пустой. Никогда не показывать URL/пароль production в UI, ответах или логах и не включать endpoint/UI в production.
- В test-среде экран `Выбор доступа` должен получать актуальный server-backed каталог должностей через dev-only boundary и создавать dev-сессию по выбранной должности с её текущими вкладками/capabilities; не возвращать фиксированный список из четырёх технических типов кабинета. При недоступном backend локальный fallback может показывать только базовые системные должности. В production этот каталог и dev-session endpoint должны оставаться отключёнными.
- Экран входа является самостоятельным прокручиваемым контейнером и после обычного открытия или восстановления страницы должен начинаться сверху. Safari может восстановить `scrollTop` вложенного `.auth-shell` уже во время `pageshow`, после следующего animation frame или при последующей загрузке server-backed карточек доступа, поэтому lifecycle экрана должен временно удерживать верхнюю позицию и отпускать защиту сразу после реального пользовательского `wheel`/touch/pointer/keyboard-ввода; одного `window.scrollTo`, CSS-высоты или однократного animation frame недостаточно. Jino должен отдавать HTML с `Cache-Control: no-cache, no-store, must-revalidate`, чтобы Safari после deploy заново получил ссылки на актуальные hashed assets.
- Сессии с техническим `accountType = dispatcher` должны автоматически завершаться ежедневно в `07:45` по московскому времени: production backend ограничивает `auth_sessions.expires_at` ближайшей границей, test/dev границы повторяют это поведение, а открытый frontend вызывает штатный logout по server-issued `expiresAt` или по ближайшим `07:45 МСК`. На остальные типы аккаунтов ежедневное ограничение не распространять.
- Текущий Jino deployment-контекст: production домен `smb.aonmou.ru` использует `~/domains/smb.aonmou.ru/app`, test домен `test.smb.aonmou.ru` использует `~/domains/test.smb.aonmou.ru/app`; собранная статика публикуется в соответствующий `public_html`, Node entrypoint домена — соответствующий `app.js`.
- При deploy с `SMB_RUN_TESTS=true` запускать тесты на managed Jino только последовательно через `npm run test:jino` с `--test-concurrency=1`: обычный параллельный `node --test` превышает лимит процессов/потоков и может зависнуть после `pthread_create: Resource temporarily unavailable`. В одном test-файле не создавать заново Vite SSR-сервер для каждого сценария с одинаковым env: закрытые графы модулей удерживают нативную память до завершения процесса и managed Jino убивает такой файл через `SIGKILL`; общий сервер закрывать в `test.after`, а отдельный создавать только когда сценарий действительно меняет build env. Не отключать тесты ради обхода лимита; локальный `npm test` оставлять параллельным.
- В JSDOM-тестах, которые временно заменяют browser globals, сохранять и восстанавливать полные property descriptors и устанавливать значения через `Object.defineProperty`: Jino Node.js 22 предоставляет глобальный `navigator` как getter-only, поэтому прямое присваивание падает до запуска проверяемого сценария.
- Первичную настройку SSH-ключа на Jino выполнять через панель `Управление → Консоль` или файловый менеджер: добавить публичный ключ в `~/.ssh/authorized_keys`, сохранить существующие ключи и выставить права `0700` на `.ssh` и `0600` на `authorized_keys`. Из локальных deploy-инструментов открывать отдельную панель хостинга `https://cp-hosting.jino.ru/`, а не общий корень `https://cp.jino.ru/`; после выбора контейнера пользователь переходит в `Управление → Консоль`. До проверки входа убедиться, что услуга `Поддержка SSH` подключена, в `Управление → SSH-подключение` задан SSH-пароль и текущий IP разрешён. Если verbose SSH-лог содержит `Server accepts key`, а затем `Connection closed`, ключ уже установлен и повторять `ssh-copy-id`/добавление ключа не нужно: исправлять услугу, SSH-пароль или IP allowlist. Не считать `ssh-copy-id` надёжным основным путём для managed hosting Jino.
- Успешно опубликованную версию каждой Jino-среды фиксировать только после копирования frontend и restart backend в `${domainRoot}/.smb-deploy-state` с `branch`, `commit` и UTC-временем; status bar и другие deploy-инструменты должны сравнивать этот marker с commit выбранной ветки в `origin`, а не считать один только HEAD серверного checkout доказательством успешной публикации.
- Для обоих Jino-доменов принудительный HTTP → HTTPS redirect выполнять на Apache/Jino boundary через tracked `public/.htaccess` с `X-Forwarded-Protocol`; deploy обязан публиковать dotfiles. Не разрешать HTTP-origin в production CORS и не снимать `Secure` с auth-cookie: отсутствие redirect нужно исправлять на уровне хостинга и проверять для `/`, `/health` и `/api/*`.
- Рабочая Jino managed DB — `j53403317_bot1` с пользователем `j53403317_robot`; при запуске backend на Jino использовать DB host `localhost`, а если TCP-подключение даёт `user@127.0.0.1` access denied, подключать backend через `socketPath=/var/lib/mysql/mysql.sock` в `DATABASE_URL`; при внешней проверке/VPS использовать `mysql.584e7697571.hosting.myjino.ru` с IP allowlist.

- Видимый бренд продукта — `НМОУ Вектор`; основной брендмарк хранится в `public/nmou-vector-icon.png`, а favicon и Apple Touch Icon являются его прозрачными уменьшенными версиями. Заголовок вкладки production — `Вектор`, test — `Вектор Тест`. Технические идентификаторы `smb-*`, env-переменные, package names, storage keys и deployment-пути не переименовывать вместе с видимым брендом, чтобы не ломать окружения и сохранённые данные.
