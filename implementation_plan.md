# План реализации НМОУ Вектор (Система управления бизнесом)

## Цель продукта

НМОУ Вектор — платформа для мониторинга ключевых показателей организации и их динамики во времени. Каждый экземпляр сайта обслуживает ровно одну организацию и до 50 одновременных пользователей; для другой организации разворачивается отдельный экземпляр со своей БД.

Платформа должна отделять администратора с платформенными правами от единого рабочего пространства организации. Любой неадминистративный аккаунт получает через должность только нужные рабочие вкладки и может переходить между ними в общей навигации. Система должна проводить данные через подтверждение перед использованием в аналитике, сохранять историю исправлений и готовиться к интеграциям с 1C, Excel, Google Sheets, Email и MAX.

- Диспетчерская система перенесена в backend-контур как 6 активных server-owned форм и единый журнал регистраций.

В каждой производственной категории можно добавлять до 50 марочных столбцов с поисковым выбором марки и полем `Факт за сутки`; все марки берутся из первого столбца `Наименование` вкладки Google Sheets `Номенклатура`. Любой заполненный факт, включая `0`, требует марки, выбранная марка требует факт, а повторы внутри категории отклоняются frontend-ом и backend-ом. Старые одиночные поля формовки/сортировки продолжают читаться и при повторной отправке преобразуются в динамический формат. Backend перед DB-транзакцией канонизирует марки по актуальной номенклатуре. Дневной план, накопительный план до выбранной даты включительно, месячный факт и отклонение `факт − план` отображаются в каждой из четырёх таблиц одинаковыми read-only колонками и не входят в payload. Для live-расчёта backend исключает факт редактируемого дня и возвращает сохранённый месячный факт предыдущих дней, а форма добавляет сумму текущих марочных фактов, поэтому сохранённый день не удваивается. Те же месячные план/факт, марочные накопления и отклонение используются в руководительской `Диспетчерской`; отправка сохраняется через общий dispatcher submissions контур и фиксируется обязательным аудитом. Выбор поддерживает поиск; отсутствующую марку диспетчер или пользователь ОЦ может добавить через server-gated API в первую свободную ячейку столбца A, начиная с `A2`. Отдельная таблица марок удаляется миграцией `022_google_sheets_production_brands`, а разделы марок исключены из админской `БД`.

План каждой категории является суммарным по всем её маркам. До предпоследнего дня категории backend ставит целую округлённую вверх долю, на последний — точный остаток с точностью до сотых; отрицательный остаток отклоняется. ## Технические правила

- Не добавлять внешний auth provider, state manager, chart library, UI framework, SDK интеграций и новые зависимости без отдельной задачи и проверки текущих локальных возможностей.
- Держать типы аккаунтов, доступы, статусы, периоды и показатели типизированными и централизованными.
- UI должен быть тонким: отображение, ввод и вызов прикладной логики.
- Бизнес-правила, проверки, переходы статусов, права доступа и подготовку данных держать отдельно от JSX и CSS.
- Любые формы, импорты, подтверждения, исправления, доступы, аудит и интеграции считать security-sensitive и покрывать проверками.
- Не использовать реальные приватные данные в тестовом контенте интерфейса.
- Все реальные бизнес-данные, пользовательские данные, права, аналитика, подтверждения и история должны храниться и проверяться на сервере.
- Клиент хранит только типы контрактов, UI-состояние и статический текст интерфейса; итоговые данные и разрешения получает по запросу к серверу.
- В remote/server-PC/VPS режиме открывать в сеть только backend API; MariaDB/MySQL оставлять локальной для backend или доступной только по разрешённому IP и не публиковать порт `3306` наружу без отдельного решения.
- `docs/local-server-run.md` держать коротким runbook локального запуска: отдельно локальный Docker для MariaDB и отдельно локальный запуск backend/frontend.
- Внешние справочники из Google Sheets подключать через backend, а не через frontend; текущий Google Sheets источник для полей `Место (цех/участок)` и `Ответственный за регистрацию` должен работать либо через публичный CSV, либо через service account JSON для закрытой таблицы и документироваться в `docs/google-sheets-source.md`.
- Email- и MAX-рассылку диспетчерских событий выполнять на backend после успешного сохранения формы; адресаты должны читаться из Google Sheets фиксированными строками, SMTP-пароли и MAX bot token хранить только в `server/.env`, а ошибка отправки уведомления не должна отменять уже сохранённую dispatcher submission. Отчёт оборудования рассылать одним кратким дневным batch-сообщением после полного `/api/dispatcher/equipment-report`, а не отдельным уведомлением на каждую позицию.
- Справочники Google Sheets являются источником актуальных вариантов выбора, но не источником истории: отправленные записи должны хранить выбранное значение в payload, чтобы удалённые из справочника люди и значения оставались доступны в старой аналитике.

## Последовательность реализации

### 1. Базовая серверная модель аккаунтов и данных

Сначала зафиксировать минимальные типы серверных контрактов: пользователь, тип аккаунта, platform/organization scope, выданные сервером права, показатель, период, статус ввода данных, статус подтверждения, событие аудита и канал интеграции. Отдельной runtime-сущности бизнеса и tenant ID нет.

Реализованная часть шага: четыре типа аккаунта `admin`, `business_owner`, `worker`, `dispatcher`; серверный ответ access/profile; контракты user profile, data entry status, confirmation status, dispatcher form definitions, dispatcher submissions, dispatcher feed summary и audit event summary. Администратор имеет platform scope, остальные аккаунты — organization scope; multi-business и подразделения удалены как неиспользуемые сущности. Клиент не хранит локальную матрицу прав как источник истины и не содержит прикладные фикстуры.

Результат: типизированная основа, на которую можно опирать UI и backend-контракты без смешивания данных с визуалом. Клиентская boundary для `access/profile` уже существует, а первый backend-контур реализован для dispatcher submissions; остальные backend-домены ещё впереди.

Проверки: typecheck; unit-тесты добавлять тогда, когда появятся функции правил доступа, валидации или переходов статусов.

### 2. Каркас приложения и навигации

Собрать первый реальный экран без старого визуального прототипа: запрос текущего access/profile с сервера, отображение типа аккаунта, переключение доступных разделов и пустые рабочие области там, где сервер ещё не отдаёт данные.

Первый shell уже собран как визуальная основа без production backend: профиль и доступы запрашиваются через `access/profile` boundary. В локальном Vite dev server endpoint отвечает профилем выбранной dev-сессии или `{"profile": null}`, а при отсутствующей `/api`-ручке static/frontend-хостинга вход может временно собрать клиентскую тестовую dev-сессию в `sessionStorage`. После входа пользователь может выйти из временного dev-аккаунта через общую навигацию и вернуться к выбору типа доступа; desktop rail можно свернуть до логотипа, а mobile drawer открывается из верхней панели и доступно закрывается без смены страницы. Рабочие области не показывают декоративные placeholder-плашки вместо отсутствующих серверных данных.

Результат: пользователь видит структуру продукта, но без фальшивой аналитики и без приватных данных.

Проверки: typecheck, build, ручной запуск через Vite.

### 3. Матрица ролей и доступов

Описать capabilities для серверного профиля доступа: управление пользователями, управление интеграциями, просмотр аудита, просмотр логов, использование debug-функций, просмотр статистики организации, отправка форм, отправка диспетчерских форм, просмотр диспетчерской истории, просмотр уведомлений и просмотр собственных отправок.

Реализованная часть шага: capability-значения централизованы в `src/contracts/accounts.ts`, `access/profile` отклоняет неизвестные capability, локальный Vite server выдаёт dev-профили с разными capabilities для admin, business owner, worker и dispatcher, а admin-профиль показывает только реальные capabilities из server profile без заглушечных административных панелей.

Результат: интерфейс получает права от сервера и использует их только для отображения доступных действий; сервер остаётся единственным источником защиты.

### 4. Область данных организации

Использовать одну серверную границу данных организации без tenant-иерархии: администратор работает в platform scope, любой неадминистративный аккаунт — в organization scope текущего deployment.

Результат: должность меняет набор рабочих вкладок и прав, но не создаёт tenant-сущности или технические подразделения и не разрывает общую историю организации.

Проверки: миграция старых scopes, создание аккаунтов всех типов, смена должности, typecheck, build.

### 5. Ввод данных пользователями

Сделать поток ввода данных для работника: выбор доступной формы или рабочего контекста, периода, показателя, натурального объёма, денежного значения, комментария и источника.

Текущее состояние: рабочая форма для роли `worker` ещё не реализована, и worker не получает список диспетчерских форм. Диспетчер сначала выбирает одну из 6 активных server-owned форм в 4 визуальных группах: производство, оборудование, открытие/закрытие инцидента и вход/выход посетителя. `Выработка` содержит дату отчёта, четыре одинаковые горизонтальные таблицы с динамическими марочными столбцами, три банки с замерами начала/конца дня и участок грануляции с фракциями `16/30` и `12/18`. Все поля марки диспетчера и ОЦ используют один поисковый список из `Номенклатура!A:A`; новая метка сохраняется в первую свободную ячейку сверху, а повтор марки внутри одной категории отклоняется. Во всех четырёх категориях факт и марка образуют обязательную пару: условные required-поля сразу направляют пользователя к пропущенной половине, а backend повторяет ту же проверку перед сохранением. Диспетчер вводит только `Факт за сутки`; дневной план, сумма суточных планов до выбранной даты включительно и сохранённый месячный факт предыдущих дней приходят с backend-а, после чего форма read-only показывает live-месячный факт и отклонение с текущим черновиком. Диспетчерская отправка идёт через remote boundary `VITE_SMB_REMOTE_API_URL` в backend workspace `server/`, где сервер валидирует `formId`, разрешённые статические и динамические поля `payload`, даты, числа, актуальную номенклатуру марок и сценарные ограничения. Остальные формы сохраняют ранее описанные server-owned правила оборудования, инцидентов и посетителей. Газовые формы остаются legacy-id только для чтения истории. При недоступном backend Vite dev-режим может использовать явно помеченный локальный `localStorage` fallback; он не является production-хранением и не заменяет Google Sheets или серверную валидацию.

Реализован отдельный ввод огнеупорного цеха: новая вкладка не закреплена за фиксированной должностью и назначается администратором через обычный каталог вкладок. Внутри выбирается одна из трёх таблиц, дата начала смены и смена `1 · 08:00–20:00` или `2 · 20:00–08:00`; после полуночи ночная смена по умолчанию остаётся на предыдущей дате. Имя мастера берётся из активного профиля и не передаётся как доверенный пользовательский ввод. Порядок секций, названия полей, группировка колонок и итоговые строки максимально сохранены по рабочим бумажным бланкам, а служебные подписи даты, мастера и подписей заменены общими server-owned полями и маршрутом подтверждения.

Актуальное уточнение по подсказкам анкеты `Оборудование`: ошибки локальной проверки после кнопки `Внести данные` показываются красной подсказкой, а успешное внесение остаётся обычным статусом. Если время простоя больше 0, причина простоя обязательна; если выбрана причина простоя `Резерв`, время простоя должно быть ровно 8 часов.

Актуальное уточнение по анкете `Оборудование`: `Дата отчета` является отдельной настройкой дневного отчёта; локальные UX-черновики и позиции, внесённые кнопкой `Внести данные`, хранятся по ключу выбранной даты и оборудования, а при выборе даты UI показывает сохранённые в БД отметки именно за эту дату и не переносит статус внесённой позиции с другого дня.

Актуальное уточнение по состояниям иконок анкеты `Оборудование`: при смене `Дата отчета` клиент заново запрашивает серверную историю через фильтр `reportDate` по payload отчёта, а legacy/local данные без серверной записи поднимаются только как `черновик`, не как `внесено в отчёт`. Иконка `нет данных` имеет серую заливку и тёмно-серый текст, `черновик` — серую заливку и чёрный текст.

Актуальное уточнение по навигации диспетчерских форм: после успешной отправки выработки, дневного отчёта оборудования, регистрации/закрытия инцидента, регистрации входа посетителя или регистрации выхода посетителя интерфейс автоматически возвращается на страницу выбора форм и показывает самозакрывающееся всплывающее уведомление об отправке; при ошибке отправки или проверки заполнения пользователь остаётся на текущей форме.

Актуальное уточнение по анкете `Закрытие инцидента`: после открытия сначала показывается отдельный компактный экран незакрытых инцидентов в виде обычных кнопок; каждый инцидент занимает отдельную строку, список отсортирован по дате открытия от новых к старым. После выбора открываются существующие поля закрытия с уже подставленным server-owned номером и возможностью выбрать другой инцидент. После первой успешной загрузки фокус получает первая кнопка инцидента, после выбора — карточка выбранного инцидента, а последующее фоновое обновление списка не перехватывает фокус повторно. Временная ошибка фонового обновления сохраняет открытую заполненную анкету; если успешное обновление подтверждает, что выбранный инцидент уже закрыт другим пользователем, UI возвращается к актуальному списку и показывает короткое объяснение.

Актуальное уточнение по пользовательским уведомлениям: для неадминистративных пользователей тосты, ошибки и статусные подсказки должны быть короткими и без технических деталей вроде id отправки, endpoint, CORS, `/health`, `localStorage`, remote/backend/server/feed; техническая диагностика остаётся в админских инструментах, логах, тестах и инструкциях.

Результат: черновик записи создаётся в статусе ожидания подтверждения и ещё не попадает в аналитический источник.

Проверки: валидация пустых, некорректных, отрицательных и неожиданных значений; unit-тесты правил создания записи.

### 6. Подтверждение данных ответственными пользователями

Добавить очередь подтверждений: кто внёс данные, кто должен подтвердить, текущий статус, комментарии, решение и timestamp.

Реализован первый production-контур подтверждения для трёх таблиц ОЦ: capability `business.review_refractory_reports` выдаётся вместе с вкладкой диспетчера `business.dispatcher_form`, очередь обновляется каждые 5 секунд, а новая запись показывает toast, счётчик в левом rail и счётчик на отдельной кнопке `Таблицы огнеупорного цеха` в меню форм. Только эта кнопка открывает экран ожидающих решений; очередь не выводится над выбором или открытой обычной формой. Решение принимается отдельно по каждой таблице; возврат требует комментарий и скрывает кнопку подтверждения, повторное или собственное решение отклоняется backend-ом. Для отправителя ОЦ отдельный `GET /api/refractory-reports/own` возвращает только ревизии текущего server-owned account ID; глобальный polling рабочего пространства показывает toast при принятии либо возврате, включает причину возврата и обновляет открытый отчёт. После commit новой pending-ревизии backend читает строки `2–20` колонок `Адресаты Диспетчеры (емейлы)` и `Адресаты Диспетчеры (МАКС)` и отправляет краткое уведомление с видом таблицы, датой, сменой, ревизией и мастером. После commit принятой ревизии адресатам колонок `Адресаты ОЦ (емейлы)` и `Адресаты ОЦ (МАКС)` отправляется полное server-owned содержимое таблицы с датой, сменой, мастером, диспетчером и рассчитанными итогами; возврат на доработку внешнюю рассылку не запускает.

Результат: только подтверждённые записи становятся источником аналитики.

Проверки: тесты переходов статусов, запрет самоподтверждения там, где оно недопустимо, проверка истории решений.

### 7. Исправления и история

Реализовать поток корректировки уже существующих данных: причина исправления, автор, дата, старое значение, новое значение, статус исправления и связь с исходной записью.

Для таблиц ОЦ реализована append-only история ревизий: после возврата пользователь исправляет сохранённые значения и отправляет следующую ревизию, а после подтверждения начинает исправление отдельной явной кнопкой. Старые pending/rejected/approved строки и авторы решений не переписываются.

Результат: ошибки, перенос бумажных данных и последующие корректировки не затирают историю.

Проверки: unit-тесты неизменности аудита и корректных переходов статусов.

### 8. Аналитические периоды и KPI

Собрать расчётные правила для последнего дня, текущего неполного месяца, текущего неполного года и динамики по выбранному периоду. Покрыть области: работники, входящие ресурсы, выполненные действия, полученный результат, задачи и активность пользователей.

Результат: аналитика строится из подтверждённых данных и явно учитывает неполные периоды.

Проверки: unit-тесты расчётов, граничные даты, пустые периоды, неполный месяц и неполный год.

### 9. Интерфейс владельца бизнеса

Собрать dashboard summary, вложенные аналитические разделы, диспетчерскую ленту и уведомления.

Реализованная часть шага: добавлена отдельная вкладка владельца `Диспетчерская`, которая запрашивает live-историю отправленных диспетчером регистраций с backend API. Левый rail владельца является единственным переключателем между `Обзор` и `Диспетчерская`; `Обзор` показывает server-owned показатели инцидентов и лаборатории за текущий месяц/сегодня и сохраняет прежние компактные блоки оборудования, месячной выработки и посетителей из dispatcher-истории. Подробные карточки последнего открытия и закрытия инцидента в `Обзоре` заменены новой числовой сводкой. `Диспетчерская` не показывает placeholder-плашки и выводит четыре рабочих раздела. Выбор раздела занимает отдельную верхнюю строку, переключатель периода располагается следующей строкой, а поля пользовательских дат при выборе `Своё` всегда открываются отдельной строкой под кнопками, включая широкий desktop. Единый переключатель периода для всех разделов содержит `Сегодня`, `Текущий месяц`, `Текущий год` и `Своё`; текущие месяц и год ограничены сегодняшней датой, а `Своё` открывает свободные поля начала/окончания, которые по умолчанию пусты и означают всю историю. В разделе `Инциденты` отдельная кнопка `Все незакрытые` одной операцией показывает открытые инциденты за всю доступную историю независимо от выбранного периода, не меняя период остальных разделов. `Выработка` разделена на шесть кнопок-таблиц: формовка, сортировка, неформованная продукция, цех обжига шамота, замеры банок и участок грануляции. Для формовки и сортировки показаны суточные и накопительные месячные план/факт с разницей; в таблицах неформованной продукции и шамота отдельная колонка показывает только названия нормализованных марок, а суточные и месячные значения остаются в собственных колонках; банки показывают начало, конец и расход; грануляция — суточные и месячные суммы фракций `16/30` и `12/18`. Месячный итог строится по последней записи каждого дня с начала календарного месяца до даты строки, даже если начало месяца не входит в видимый пользовательский диапазон; клик по дате открывает полный набор заполненных показателей в server-owned порядке полей формы. `Оборудование` агрегируется за диапазон по названию, суммарной выработке, суммарному простою и причинам простоя с часами; клик по названию оборудования открывает окно расшифровки с дневными строками из текущего периода, чтобы владелец видел составляющие итоговых чисел. `Инциденты` объединяют открытие и закрытие, показывают статус и включают записи, которые не были закрыты к началу выбранного диапазона. `Посетители` показывают входы за тот же выбранный период с временем выхода или пометкой, что выход не отмечен. В Vite dev-режиме при недоступном backend та же dispatcher-история читается из локального тестового `localStorage` и помечает источник данных.

Результат: владелец бизнеса получает обзор своего бизнеса, динамику и проблемные зоны без доступа к платформенным административным возможностям.

Проверки: typecheck, build, ручная проверка основных сценариев.

### 10. Расширенный рабочий интерфейс

Собрать формы ввода и корректировки данных, доступную статистику по серверно выданным правам и напоминания о событиях.

Реализованная часть шага: должность `Экономист` получила отдельную вкладку `План выработки` со свободным выбором месяца и категории, отдельным календарём каждой категории, пресетами всех календарных дней и понедельника–пятницы, ручной корректировкой дат и независимым сохранением категории в append-only месячный снимок. После каждого сохранения нижняя серверная сводка обновляется сразу и показывает, сколько из четырёх расписаний уже заполнено. Эта capability не выдаётся автоматически; администратор может назначить вкладку любой неадминистративной должности.

Результат: работник или пользователь с расширенными рабочими правами может поддерживать данные своего направления и видеть только разрешённую аналитику.

Проверки: тесты валидации форм и прав доступа, typecheck, build.

### 11. Ограниченный интерфейс работника

Ограничить worker-flow разрешённым вводом данных и минимальной навигацией без административных и аналитических возможностей сверх доступа.

Результат: работник может выполнить только разрешённые действия.

Проверки: тесты запрета лишних capabilities.

### 12. Интерфейс администратора

Добавить управление пользователями, типами аккаунтов, должностями, базой аккаунтов и аналитической базой. Отдельно предусмотреть смену паролей при ротации сотрудников.

Реализованная часть шага: администратор управляет учётными записями и отдельным server-backed каталогом должностей. У неадминистративной должности задаются только название и компактный список любых рабочих вкладок с пояснениями; поля базового кабинета нет. Аккаунт выбирает должность и наследует её название, навигацию и capabilities без индивидуальных галочек, а изменение должности отзывает сессии всех связанных пользователей. Все рабочие должности открываются в едином workspace; административная должность остаётся отдельной и защищённой. `Просмотр аккаунта` показывает полный каталог должностей и актуальные server-backed аккаунты, переиспользуя реальные рабочие страницы; административные карточки не запускают preview до production impersonation/audit-модели. `Учётные записи` также поддерживает создание логина, сброс пароля и временное отключение входа. Доступы и должности меняются только в профильных admin-экранах, а server-owned `БД` показывает только allowlisted прикладные разделы без auth-секретов, raw payload, технических ID и массового удаления. Импорт Google Sheets остаётся отдельным server-gated двухшаговым действием без перезаписи существующих записей и без email/MAX-уведомлений.

Вкладка `Действия пользователей` показывает понятный журнал за последние три календарных месяца: фильтр по каждому аккаунту отдельно, категории действий, время, имя/должность/логин автора и раскрываемые введённые значения. Просмотры фиксируют открытие основных вкладок и диспетчерских форм, но не каждый клик. Для администратора доступ проверяется backend-ом через `platform.view_audit`; у любой неадминистративной должности вкладка включается отдельно и получает `business.view_user_actions`, а backend возвращает только аккаунты и события organization scope. Старые audit-события остаются в БД и только не попадают в текущую выборку.

Результат: администратор может обслуживать структуру платформы без прямого вмешательства в аналитику вне разрешённых действий.

Проверки: тесты административных прав, запретов для неадминистраторов и валидации критичных действий.

### 13. Диспетчерская лента и уведомления

Собрать единый поток событий: новые записи, ожидание подтверждения, отклонения, исправления, напоминания, просрочки и интеграционные ошибки.

Реализованная часть шага: для диспетчерских отправок добавлен первый live-feed contract `GET /api/dispatcher/submissions` через remote API. Endpoint поддерживает фильтры `formId`, `dateFrom`, `dateTo`, постраничные `limit`/`offset` и возвращает `summary` по количеству регистраций; вкладка владельца автоматически дочитывает все страницы истории. После успешного `POST /api/dispatcher/submissions` backend отправляет email- и MAX-уведомления по открытию/закрытию инцидента и входу/выходу посетителя в человекочитаемом формате, а оборудование рассылает только после полного batch-сохранения через `POST /api/dispatcher/equipment-report` одним кратким сообщением на все позиции дневного отчёта. Для закрытия инцидента сервер дополнительно подтягивает из сохранённого открытия дату/время, место, тип, критичность и описание: уведомление после номера показывает эти исходные данные, затем время закрытия и утвердившего. Тестовая среда сохраняет тот же формат и добавляет в конце отдельное примечание `Тестовое сообщение`. Общие адресаты берутся из строк `2–20` Google Sheets колонок email/MAX, дополнительные адресаты механики — из строк `22–25`, электрики — из строк `27–30`; посетительские адресаты берутся из отдельных колонок `Адресаты по посетителям (емейлы)` и `Адресаты по посетителям (МАКС)` строк `2–20`. Новые pending-таблицы ОЦ отправляют краткое уведомление диспетчерам строк `2–20` колонок `Адресаты Диспетчеры (емейлы)` и `Адресаты Диспетчеры (МАКС)`, а подтверждённые таблицы — полное содержимое отдельным адресатам колонок `Адресаты ОЦ (емейлы)` и `Адресаты ОЦ (МАКС)`; возвраты наружу не рассылаются. MAX поддерживает несколько ID в одной ячейке этих строк, спецгруппы добавляются по причине простоя, типу инцидента или тексту закрытия. Это ещё не единая диспетчерская лента всех событий.

Отправленный диспетчером отчёт `Выработка` после commit рассылается по email и MAX базовой группе адресатов оборудования из строк `2–20`; механические и электрические дополнительные группы для него не применяются.

Email- и MAX-уведомление по оборудованию оформлено как нумерованный отчёт в порядке оборудования из анкеты: заголовок и дата вынесены отдельно, выработка, причина простоя, время и примечание показываются отдельными строками, нулевые показатели скрываются, а блоки оборудования разделяются пустой строкой.

Результат: владелец бизнеса, администратор и ответственные работники видят разрешённые рабочие события в одном месте.

Проверки: тесты фильтрации событий по роли, организации и статусу.

### 14. Контракты интеграций

Подготовить adapter-контракты для 1C, Excel, Google Sheets, Email и MAX без реальных секретов и SDK. Для Excel и Google Sheets отдельно описать настройку форматирования импорта.

Реализованная часть шага: первый Google Sheets reference-source добавлен без SDK и без хранения секретов в git. Backend умеет читать публичный CSV или закрытую таблицу через service account JSON на сервере, ищет значения под колонками `Места (цех/участок)` и `Ответственный за регистрацию` с двоеточием или без него, по умолчанию перечитывает результат при каждом запросе форм и обогащает серверное описание формы `Открытие инцидента`. Этот же источник читает email-адресатов и MAX ID уведомлений из фиксированных строк, включая колонки подтверждённых таблиц ОЦ `Адресаты ОЦ (емейлы)`/`Адресаты ОЦ (МАКС)` и колонки pending-уведомлений `Адресаты Диспетчеры (емейлы)`/`Адресаты Диспетчеры (МАКС)`. Для исторической миграции добавлен отдельный workbook reader exact-вкладок и import-specific parser: он читает неформатированные Google serial даты, сохраняет московское историческое время, строит lifecycle-записи инцидентов/посетителей и выдаёт предупреждения по legacy-расхождениям до подтверждения. Email-рассылка реализована через SMTP-конфиг, MAX-рассылка — через bot token и HTTP API; для Jino можно указать `MAX_CA_CERT_FILE` с доверенным PEM сертификатом Минцифры без отключения TLS, секреты хранятся только в `server/.env` и не коммитятся в git.

Результат: интеграции имеют безопасные границы и могут добавляться по одной без переписывания доменной логики.

Проверки: тесты нормализации входных данных, ошибок импорта и отсутствия логирования приватных payload.

### 15. Backend и постоянное хранение

После стабилизации frontend-прототипа выбрать backend, схему хранения, auth, audit storage и API-контракты. Frontend-only проверки доступа не считать достаточной защитой.

Текущее состояние: backend workspace `server/` хранит пользователей, password credentials, account access, каталог должностей, сессии, dispatcher submissions и append-only `user_audit_events` в MariaDB/MySQL. Admin API создаёт отдельные login identity/access, отклоняет повторный login, сбрасывает пароль, создаёт и редактирует должности; авторизация читает navigation items и capabilities из назначенной должности. Все неадминистративные должности используют единый рабочий каталог вкладок, а технический `accountType` сохраняется только как внутренняя совместимость и не принимается API настройки должности. `/api/admin/access-levels` удалён. Миграция `009_remove_account_access_levels` удалила старые presets, `010_dynamic_account_positions` ввела текущий каталог должностей, `014_dispatcher_spreadsheet_import_source` добавила уникальный source key для повторяемого импорта, `015_user_audit_events` создала постоянный журнал, а `016_remove_departments` удалила модель подразделений. Миграция `017_single_organization_scope` сохранила историю, перевела все неадминистративные доступы в organization scope, удалила business ID из рабочих таблиц и затем удалила таблицу бизнесов. Audit API серверно фиксирует входы/выходы, отправки форм, изменения БД, импорт, управление аккаунтами/должностями и allowlisted просмотры экранов; production-изменения и их audit-события проходят через общий транзакционный DB-контекст, а `GET /api/admin/audit-events` жёстко применяет rolling-окно трёх календарных месяцев и не удаляет более старые записи. Для администратора endpoint возвращает платформенный отчёт, а для неадминистративной должности с `business.view_user_actions` сервер ограничивает события и каталог аккаунтов organization scope. Database API отдаёт только безопасные редактируемые пользовательские представления; backend формирует поля редактора, валидирует статусы и диспетчерские формы, пересчитывает производные значения и не передаёт auth secrets, session identifiers, raw payload, dedupe/source keys и неизвестные таблицы. Import API отдельно валидирует прикладные данные, схлопывает одинаковые строки по нормализованному содержимому и транзакционно добавляет только отсутствующие dispatcher submissions единой организации, используя уникальный organization-wide `dedupe_key` как защиту от гонок. Лимит server/client dispatcher history увеличен до 2000 записей, чтобы первичный импорт 572 строк не вытеснил incident/visitor lifecycle из рабочих представлений. Test/production разделены через `VITE_SMB_APP_ENV`, `SMB_APP_ENV`, `DEV_ACCESS_ENABLED`, отдельные cookie/env/БД; production использует login/password auth и запрещает dev-session/client fallback. Personal plugin и VS Code extension `smb-jino-deploy` запускают существующий tracked deploy по SSH, не хранят секреты, требуют SSH-ключ, показывают актуальность test/production по post-publish marker, отображают один стандартный progress bar по реальным этапам deploy без автоматического открытия Output-панели и после публикации проверяют HTTP redirect и HTTPS health обеих сред; неинтерактивный SSH-runner отдельно активирует системный Jino Node.js 22 runtime из `/opt/alt` и проверяет Node/npm ещё в read-only preflight, а optional remote tests выполняются через последовательный `test:jino`, чтобы не превышать лимит процессов/потоков managed hosting. Production impersonation, безопасный bootstrap reset с re-auth/backup guard и общая аналитическая БД ещё не реализованы.

Миграция `009_remove_account_access_levels` завершает переход к полностью индивидуальным настройкам: она не меняет сохранённые `navigation_items` и capabilities аккаунтов, удаляет все оставшиеся связи и затем удаляет колонку `access_level_id` вместе с таблицей пресетов. Endpoint `/api/admin/access-levels` и связанные frontend/backend-контракты удалены.

Результат: появляется реальная доверенная граница для данных, ролей, подтверждений, истории и интеграций.

Проверки: тесты API-контрактов, авторизации, валидации входа, миграций и audit trail.
