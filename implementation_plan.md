# План реализации НМОУ Вектор (Система управления бизнесом)

## Цель продукта

НМОУ Вектор — платформа для мониторинга ключевых показателей организации и их динамики во времени. Каждый экземпляр сайта обслуживает ровно одну организацию и до 50 одновременных пользователей; для другой организации разворачивается отдельный экземпляр со своей БД.

Платформа должна отделять администратора с платформенными правами от единого рабочего пространства организации. Любой неадминистративный аккаунт получает через должность только нужные рабочие вкладки и может переходить между ними в общей навигации. Система должна проводить данные через подтверждение перед использованием в аналитике, сохранять историю исправлений и готовиться к интеграциям с 1C, Excel, Google Sheets, Email и MAX.

- Тестовая визуальная страница удалена.
- Тестовые Excel-данные и агрегаты удалены из проекта.

- Документация в `docs/` держит короткий локальный runbook `docs/local-server-run.md` и отдельную инструкцию внешнего Google Sheets источника `docs/google-sheets-source.md`.
- Добавлен первый TypeScript-контракт серверного ответа для типов аккаунта и прав доступа в `src/contracts/accounts.ts`.
- Собран минимальный app shell: left rail, кнопка выхода и рабочие поверхности без placeholder-плашек после входа.
- Диспетчерская система перенесена в backend-контур как 6 активных server-owned форм и единый журнал регистраций.
- Реальная разработка должна начинаться от этого плана, без переноса старого визуального прототипа.

Все поля блока `Замеры банок` (`jar*` и `coshMaster`) из построчного вывода убраны — предикат `isJarNotificationField` фильтрует их по префиксу `jar`, потому что все поля блока названы единообразно. Содержимое банки берётся из снимка сводки (`jarMaterial{N}`, server-owned значение именно этого отчёта), а список текущих назначений из задачи 93 остаётся запасным источником для legacy-записей без снимка; без обоих подставляется `Не назначено`. Отсутствующее число показывается как `—`, значения не переформатируются и уходят в том же виде, в каком сохранены в payload. Сводка без единого поля банок блок не получает вовсе. Прежний `spliceJarBankContent` из задачи 93 удалён: он подставлял содержимое в подписи `Замеры банок — Банка N`, которых в сообщении больше нет. - [x] Доработка задачи 3 (`Расчётный вес по отгрузкам, т`): цепочка веса по отгрузкам стартует с нуля, а не с веса по замерам. Предыдущая правка отвязала базу от текущего веса по замерам только там, где предыдущая запись существует и материал совпадает, а на старте цепочки (нет предыдущей записи, сменилось содержимое банки, legacy-запись без сохранённого материала) `readShipmentBaseTons` возвращал `materialMassTons` — поэтому в форме без истории оба веса совпадали. Теперь база в этих случаях равна `0`: вес по отгрузкам складывается только из движений `Засыпали` и `Отгрузили` от момента назначения материала в банку, а вес по замерам в него не входит вообще. Правка в одном `server/src/domain/bankMeasurement.ts`, который frontend переиспользует для live-предпросмотра через `src/services/bankMeasurements.ts`, поэтому сводка ЦОШ, диспетчерская выработка и предпросмотр остались согласованными. Проверка отрицательного остатка не изменилась и теперь на старте цепочки отклоняет отгрузку без предшествующей засыпки. `jarShipmentStart*` и `shipmentBaseTons` продолжают хранить фактическую базу, поэтому расход по отгрузкам остаётся равен `отгрузили − засыпали`. Пропущенный день цепочку не рвёт: база берётся из последней сводки строго раньше даты отчёта, а не из предыдущего календарного дня. Для сводки ЦОШ это уже работало через `findLatestApprovedCoshBefore`; для диспетчерской выработки добавлен `dispatcherSubmissionsRepository.findLatestProductionBefore` — один запрос с нормализацией `reportDate` (payload хранит и `DD.MM.YYYY`, и legacy `YYYY-MM-DD`) и сортировкой по дате отчёта, который используют и сохранение, и live-предпросмотр. Метод объявлен необязательным по образцу `listProductionCoshMasterOptions`, а `readPreviousProductionSubmission` в `app.ts` при его отсутствии возвращается к прежнему поиску за предыдущий календарный день. Начало дня по замерам (`jarStart*`) намеренно осталось привязанным ровно к предыдущей календарной дате: это конец прошлого дня, а не последнее известное значение, поэтому найденная сводка отдаётся туда только при совпадении даты (`readPreviousDayProductionPayload`). Миграция не потребовалась.
- [x] Общая сортировка историй (все вкладки): правило «сверху самые свежие» распространено на истории, которые ещё шли по возрастанию или по порядку поступления. `Диспетчерская → Выработка`: таблицы по маркам (формовка, сортировка, неформованные, шамот) и `Грануляция` сортируются по дате отчёта по убыванию на backend (`buildBrandRows`, `buildGranulationRows`) и в локальном test fallback (`buildProductionBrandRows`, `buildProductionGranulationRows`) — тем же приёмом, что и `Замеры банок`: сортируются готовые строки, а не исходный список отчётов, поэтому накопительные месячные план/факт остаются хронологическими. Из-за смены порядка `buildProductionMonthToDate` больше не берёт предыдущий день позиционным `.at(-1)`, а выбирает его существующим `readLatestProductionRow` по максимальной дате; остальные потребители (`buildProductionMonthOverview`, все `*Totals`, `filterProductionReportTables`) уже были независимы от порядка. `Диспетчерская → Оборудование`: дневная детализация выбранного оборудования перевёрнута на убывание. `Диспетчерская → Посетители`: журнал визитов сортируется по времени входа по убыванию вместо времени выхода — раньше незакрытые визиты уходили под вчерашние закрытые, а несколько открытых визитов оставались в порядке поступления. `Огнеупорный цех → Оборот вагонов`: `order by loading_date is null desc, loading_date desc, sequence_id desc` вместо только `sequence_id desc`; строка нового цикла ещё без садки остаётся сверху, а инвариант `selectLatestWagonCycles` («первая запись номера — текущий цикл») сохраняется, потому что циклы одного вагона идут только вперёд во времени. `Огнеупорный цех → Осмотр вагонов`: `order by inspections.approval_date desc, inspections.sequence_id desc`. Намеренно не тронуты: журналы `Регистрация проб`, `Регистрация проб неформованной продукции` и `Химические анализы` (сортировка по `Номеру пробы` по убыванию — явное требование задачи 92), справочный `Журнал марок` (нет даты события, сортировка по наименованию) и очереди на подтверждение `listPending` (FIFO, это не история). Миграция не потребовалась.
- [x] Доработка задачи 3 (`Расчётный вес по отгрузкам, т`): два веса банки стали полностью параллельными расчётами. Вес по замерам по-прежнему считается от текущих замеров, а вес по отгрузкам теперь продолжает собственную цепочку — `предыдущий вес по отгрузкам + засыпали − отгрузили` — и больше не пересобирается из веса по замерам текущей смены. Базу выбирает backend и никогда не принимает от клиента: для `Сводки по ЦОШ (ежесменной)` это последняя подтверждённая ЦОШ-ревизия строго раньше её даты и смены (новый repository-метод `findLatestApprovedCoshBefore`), для `Диспетчерская → Выработка` — сохранённый `jarShipmentEnd` сводки предыдущей календарной даты, то есть тот же источник, из которого уже заполняется `jarShipmentStart`. Отсчётная точка цепочки — смена материала в банке: вместе с весом backend читает материал предыдущей записи (`jarMaterial` в диспетчерском payload, `material` в снимке ЦОШ) и сравнивает его с текущим содержимым банки по нормализованному наименованию. Совпал — цепочка продолжается, не совпал (а также когда предыдущей записи нет или это legacy-строка без материала) — начинается заново с веса по замерам. Фактическая база сохраняется вместе с расчётом: `shipmentBaseTons` в снимке ЦОШ и `jarShipmentStart` в диспетчерской выработке, поэтому `Расход по отгрузкам` в отчётных таблицах остаётся равным `отгрузили − засыпали` и в смену, когда материал поменяли. Старые данные читаются без миграции. Проверка «Отгрузили больше расчётного остатка с учётом засыпки» теперь сравнивает отгрузку с этой же базой. Чтобы live-предпросмотр совпадал с тем, что сохранит POST, оба справочных endpoint отдают server-owned предыдущее значение: `GET /api/refractory-reports/banks` принимает `date` и `shift` и возвращает `previousShipmentMassTons`, а `GET /api/dispatcher/production-bank-contents` добавляет тот же список в `bankInput`. Миграция не потребовалась.
- [x] Задача 95 (`Лаборатория → Склад сырья`): в корневой ряд лаборатории добавлен раздел `Склад сырья`, а кнопки разложены на два ряда в требуемом порядке `Марки`, `Банки`, `Склад сырья`, `ЦЗЛ`, `ОТК`, `ОЦ`. Лабораторная должность (capability `business.manage_laboratory_results`) вводит дату, вид сырья из server-owned `Журнала марок`, номер штабеля/место, поступление с поставщиком и отгрузку с получателем; штабели, поставщики и получатели накапливаются из полной истории и возвращаются backend как варианты ввода. Новая запись сохраняется только со статусом ожидания и до решения кладовщика не входит ни в историю, ни в итоги. Назначение проверки хранится в отдельном server-owned признаке должности `can_review_raw_material_warehouse`, который при включённой лабораторной вкладке выдаёт только capability `business.review_raw_material_warehouse`: миграция однократно назначает его текущим должностям кладовщиков, синхронизирует доступы и убирает у них общее изменение остальных лабораторных журналов; переименование и цикл выключения/включения вкладки не меняют назначение. Кладовщик не создаёт заявки, не подтверждает собственную заявку даже через другой доступ, но может утвердить чужую ожидающую запись либо исправить ожидающую или уже подтверждённую. Подтверждение и исправление создают новую неизменяемую ревизию со статусом `Утверждено кладовщиком` или `Скорректировано кладовщиком`, именем кладовщика из активной сессии и audit-событием; перезаписи прежней версии нет. История без скрытого лимита сортируется по дате движения от новых к старым, фильтруется по периоду и одному поиску по сырью, поставщику или получателю, а над ней backend считает поступление, отгрузку и остаток по всему текущему фильтру. Удаление используемой марки без замены блокируется, а объединение марок переносит активные складские ссылки новой append-only ревизией. Миграция `071_laboratory_raw_material_warehouse` создаёт таблицу ревизий, индексы очереди/истории и выдаёт стабильное право кладовщика.
- [x] Доработка задачи 3 (`Огнеупорный цех → ЦОШ → Замеры банок`): прежние три карточки с произвольным числом замеров заменены одной таблицей по образцу `Банки!G1:K17`. Для каждой банки отображается назначенное Лабораторией содержимое, ровно четыре основных поля замера (первое обязательно, остальные необязательны; старые ревизии с дополнительными значениями остаются полностью читаемыми, а исправление переносит в новый payload первые четыре), среднее, актуальная насыпная плотность с датой последней лабораторной записи, объём по замерам, расчётный вес по замерам, вводимые `Засыпали`/`Отгрузили`, расчётный вес по отгрузкам и итоговая пара `по замерам / по отгрузкам`. Оба веса считает backend: он перед каждой загрузкой формы и отправкой обновляет плотность назначенного материала по текущему среднему последних записей `Журнала печи 2`, интерполирует объём по live-таблице `Банки`, затем считает `вес по отгрузкам = вес по замерам + засыпали − отгрузили` и отклоняет отрицательный остаток. В неизменяемом JSON-снимке ревизии сохраняются содержимое, до четырёх новых замеров (legacy-значения не обрезаются), среднее, объём, плотность и дата её источника, оба движения и оба веса; уведомления и диспетчерское подтверждение показывают ту же пару значений. Добавлено отдельное обязательное поле `Мастер ЦОШ`: оно предзаполняется именем текущего пользователя, допускает ручной ввод и получает накопительные подсказки из всех прошлых ЦОШ-ревизий (для старых ревизий используется прежний `master_display_name`). В `Диспетчерская → Выработка` прежний блок `начало/конец дня` в том же месте заменён read-only таблицей подтверждённой сводки ЦОШ за выбранную дату с четырьмя замерами, плотностью и её датой, объёмом, обоими весами, движениями и мастером; сохранение диспетчерского отчёта получает обе пары начала/конца только с backend из подтверждённых сводок предыдущего и выбранного дня, а не из скрытого клиентского ввода. Миграция не потребовалась — новые значения живут в существующем append-only payload ревизий.

- [x] Задачи 96–97 (Диспетчерская): для `Закрытия инцидента` ключ идемпотентности теперь включает не только номер, но и дату/время закрытия. Это сохраняет защиту от точного повтора и позволяет корректно закрыть номер, если в legacy-истории уже есть ошибочное закрытие раньше открытия — именно такая запись блокировала `INC-2026-10`; обычный `INC-2026-9` продолжает закрываться по тому же server-owned состоянию. ## Технические правила

- Не добавлять внешний auth provider, state manager, chart library, UI framework, SDK интеграций и новые зависимости без отдельной задачи и проверки текущих локальных возможностей.
- Держать типы аккаунтов, доступы, статусы, периоды и показатели типизированными и централизованными.
- UI должен быть тонким: отображение, ввод и вызов прикладной логики.
- Бизнес-правила, проверки, переходы статусов, права доступа и подготовку данных держать отдельно от JSX и CSS.
- Любые формы, импорты, подтверждения, исправления, доступы, аудит и интеграции считать security-sensitive и покрывать проверками.
- Не использовать реальные приватные данные в тестовом контенте интерфейса.
- Все реальные бизнес-данные, пользовательские данные, права, аналитика, подтверждения и история должны храниться и проверяться на сервере.
- Клиент хранит только типы контрактов, UI-состояние и статический текст интерфейса; итоговые данные и разрешения получает по запросу к серверу.
- В remote/server-PC/VPS режиме открывать в сеть только backend API; MariaDB/MySQL оставлять локальной для backend или доступной только по разрешённому IP и не публиковать порт `3306` наружу без отдельного решения.
- `docs/local-server-run.md` держать коротким runbook локального запуска: отдельно локальный Docker для MariaDB и отдельно локальный запуск backend/frontend.
- Внешние справочники из Google Sheets подключать через backend, а не через frontend; текущий Google Sheets источник для полей `Место (цех/участок)` и `Ответственный за регистрацию` должен работать либо через публичный CSV, либо через service account JSON для закрытой таблицы и документироваться в `docs/google-sheets-source.md`.
- Email- и MAX-рассылку диспетчерских событий выполнять на backend после успешного сохранения формы; адресаты должны читаться из Google Sheets фиксированными строками, SMTP-пароли и MAX bot token хранить только в `server/.env`, а ошибка отправки уведомления не должна отменять уже сохранённую dispatcher submission. Отчёт оборудования рассылать одним кратким дневным batch-сообщением после полного `/api/dispatcher/equipment-report`, а не отдельным уведомлением на каждую позицию.
- Справочники Google Sheets являются источником актуальных вариантов выбора, но не источником истории: отправленные записи должны хранить выбранное значение в payload, чтобы удалённые из справочника люди и значения оставались доступны в старой аналитике.

### 1. Базовая серверная модель аккаунтов и данных

Сначала зафиксировать минимальные типы серверных контрактов: пользователь, тип аккаунта, platform/organization scope, выданные сервером права, показатель, период, статус ввода данных, статус подтверждения, событие аудита и канал интеграции. Отдельной runtime-сущности бизнеса и tenant ID нет.

Администратор имеет platform scope, остальные аккаунты — organization scope; multi-business и подразделения удалены как неиспользуемые сущности. Клиент не хранит локальную матрицу прав как источник истины и не содержит прикладные фикстуры.

Результат: типизированная основа, на которую можно опирать UI и backend-контракты без смешивания данных с визуалом. Клиентская boundary для `access/profile` уже существует, а первый backend-контур реализован для dispatcher submissions; остальные backend-домены ещё впереди.

### 2. Каркас приложения и навигации

Собрать первый реальный экран без старого визуального прототипа: запрос текущего access/profile с сервера, отображение типа аккаунта, переключение доступных разделов и пустые рабочие области там, где сервер ещё не отдаёт данные.

Первый shell уже собран как визуальная основа без production backend: профиль и доступы запрашиваются через `access/profile` boundary. В локальном Vite dev server endpoint отвечает профилем выбранной dev-сессии или `{"profile": null}`, а при отсутствующей `/api`-ручке static/frontend-хостинга вход может временно собрать клиентскую тестовую dev-сессию в `sessionStorage`. После входа пользователь может выйти из временного dev-аккаунта через общую навигацию и вернуться к выбору типа доступа; desktop rail можно свернуть до логотипа, а mobile drawer открывается из верхней панели и доступно закрывается без смены страницы. Рабочие области не показывают декоративные placeholder-плашки вместо отсутствующих серверных данных.

Результат: пользователь видит структуру продукта, но без фальшивой аналитики и без приватных данных.

### 5. Ввод данных пользователями

Сделать поток ввода данных для работника: выбор доступной формы или рабочего контекста, периода, показателя, натурального объёма, денежного значения, комментария и источника.

Текущее состояние: рабочая форма для роли `worker` ещё не реализована, и worker не получает список диспетчерских форм. Диспетчер сначала выбирает одну из 6 активных server-owned форм в 4 визуальных группах: производство, оборудование, открытие/закрытие инцидента и вход/выход посетителя. `Выработка` содержит дату отчёта, четыре одинаковые горизонтальные таблицы с динамическими марочными столбцами, три банки с замерами начала/конца дня и участок грануляции с фракциями `16/30` и `12/18`. Все поля марки диспетчера и ОЦ используют один поисковый список из server-owned `Журнала марок`; новые марки добавляются только в `Лаборатория → Марки`, а повтор марки внутри одной категории отклоняется. Во всех четырёх категориях факт и марка образуют обязательную пару: условные required-поля сразу направляют пользователя к пропущенной половине, а backend повторяет ту же проверку перед сохранением. Диспетчер вводит только `Факт за сутки`; дневной план, сумма суточных планов до выбранной даты включительно и сохранённый месячный факт предыдущих дней приходят с backend-а, после чего форма read-only показывает live-месячный факт и отклонение с текущим черновиком. Диспетчерская отправка идёт через remote boundary `VITE_SMB_REMOTE_API_URL` в backend workspace `server/`, где сервер валидирует `formId`, разрешённые статические и динамические поля `payload`, даты, числа, актуальный `Журнал марок` и сценарные ограничения. Остальные формы сохраняют ранее описанные server-owned правила оборудования, инцидентов и посетителей. Газовые формы остаются legacy-id только для чтения истории. При недоступном backend Vite dev-режим может использовать явно помеченный локальный `localStorage` fallback; он не является production-хранением и не заменяет серверную валидацию.

Реализован отдельный ввод огнеупорного цеха: новая вкладка не закреплена за фиксированной должностью и назначается администратором через обычный каталог вкладок. Внутри выбирается одна из трёх таблиц, дата начала смены и смена `1 · 08:00–20:00` или `2 · 20:00–08:00`; после полуночи ночная смена по умолчанию остаётся на предыдущей дате. Имя мастера берётся из активного профиля и не передаётся как доверенный пользовательский ввод. Порядок секций, названия полей, группировка колонок и итоговые строки максимально сохранены по рабочим бумажным бланкам, а служебные подписи даты, мастера и подписей заменены общими server-owned полями и маршрутом подтверждения.

Актуальное уточнение по подсказкам анкеты `Оборудование`: ошибки локальной проверки после кнопки `Внести данные` показываются красной подсказкой, а успешное внесение остаётся обычным статусом. Если время простоя больше 0, причина простоя обязательна; если выбрана причина простоя `Резерв`, время простоя должно быть ровно 8 часов.

Актуальное уточнение по анкете `Оборудование`: `Дата отчета` является отдельной настройкой дневного отчёта; локальные UX-черновики и позиции, внесённые кнопкой `Внести данные`, хранятся по ключу выбранной даты и оборудования, а при выборе даты UI показывает сохранённые в БД отметки именно за эту дату и не переносит статус внесённой позиции с другого дня.

Актуальное уточнение по состояниям иконок анкеты `Оборудование`: при смене `Дата отчета` клиент заново запрашивает серверную историю через фильтр `reportDate` по payload отчёта, а legacy/local данные без серверной записи поднимаются только как `черновик`, не как `внесено в отчёт`. Иконка `нет данных` имеет серую заливку и тёмно-серый текст, `черновик` — серую заливку и чёрный текст.

Актуальное уточнение по навигации диспетчерских форм: после успешной отправки выработки, дневного отчёта оборудования, регистрации/закрытия инцидента, регистрации входа посетителя или регистрации выхода посетителя интерфейс автоматически возвращается на страницу выбора форм и показывает всплывающее уведомление об отправке, которое остаётся до закрытия крестиком; при ошибке отправки или проверки заполнения пользователь остаётся на текущей форме.

Актуальное уточнение по анкете `Закрытие инцидента`: после открытия сначала показывается отдельный компактный экран незакрытых инцидентов в виде обычных кнопок; каждый инцидент занимает отдельную строку, список приходит с backend-а в виде серверного `openIncidents` и отсортирован по дате открытия от новых к старым. После выбора открываются существующие поля закрытия с уже подставленным server-owned номером и возможностью выбрать другой инцидент. После первой успешной загрузки фокус получает первая кнопка инцидента, после выбора — карточка выбранного инцидента, а последующее фоновое обновление списка не перехватывает фокус повторно. Временная ошибка фонового обновления сохраняет открытую заполненную анкету; если успешное обновление подтверждает, что выбранный инцидент уже закрыт другим пользователем, UI возвращается к актуальному списку и показывает короткое объяснение.

Актуальное уточнение по пользовательским уведомлениям: для неадминистративных пользователей тосты, ошибки и статусные подсказки должны быть короткими и без технических деталей вроде id отправки, endpoint, CORS, `/health`, `localStorage`, remote/backend/server/feed; техническая диагностика остаётся в админских инструментах, логах, тестах и инструкциях.

Результат: черновик записи создаётся в статусе ожидания подтверждения и ещё не попадает в аналитический источник.

Проверки: валидация пустых, некорректных, отрицательных и неожиданных значений; unit-тесты правил создания записи.

### 6. Подтверждение данных ответственными пользователями

Добавить очередь подтверждений: кто внёс данные, кто должен подтвердить, текущий статус, комментарии, решение и timestamp.

Реализован первый production-контур подтверждения для трёх таблиц ОЦ: capability `business.review_refractory_reports` выдаётся вместе с вкладкой диспетчера `business.dispatcher_form`, очередь обновляется каждые 5 секунд, а новая запись показывает toast, счётчик в левом rail и счётчик на отдельной кнопке `Таблицы огнеупорного цеха` в меню форм. Только эта кнопка открывает экран ожидающих решений; очередь не выводится над выбором или открытой обычной формой. Решение принимается отдельно по каждой таблице; возврат требует комментарий и скрывает кнопку подтверждения, повторное или собственное решение отклоняется backend-ом. Для отправителя ОЦ отдельный `GET /api/refractory-reports/own` возвращает только ревизии текущего server-owned account ID; глобальный polling рабочего пространства показывает toast при принятии либо возврате, включает причину возврата и обновляет открытый отчёт. После commit новой pending-ревизии backend читает строки `2–20` колонок `Адресаты Диспетчеры (емейлы)` и `Адресаты Диспетчеры (МАКС)` и отправляет краткое уведомление с видом таблицы, датой, сменой, ревизией и мастером. После commit принятой ревизии адресатам колонок `Адресаты ОЦ (емейлы)` и `Адресаты ОЦ (МАКС)` отправляется полное server-owned содержимое таблицы с датой, сменой, мастером, диспетчером и рассчитанными итогами; возврат на доработку внешнюю рассылку не запускает.

Результат: только подтверждённые записи становятся источником аналитики.

Проверки: тесты переходов статусов, запрет самоподтверждения там, где оно недопустимо, проверка истории решений.

### 7. Исправления и история

Реализовать поток корректировки уже существующих данных: причина исправления, автор, дата, старое значение, новое значение, статус исправления и связь с исходной записью.

Для таблиц ОЦ реализована append-only история ревизий: после возврата пользователь исправляет сохранённые значения и отправляет следующую ревизию, а после подтверждения начинает исправление отдельной явной кнопкой. Старые pending/rejected/approved строки и авторы решений не переписываются.

Результат: ошибки, перенос бумажных данных и последующие корректировки не затирают историю.

Проверки: unit-тесты неизменности аудита и корректных переходов статусов.

### 8. Аналитические периоды и KPI

Собрать расчётные правила для последнего дня, текущего неполного месяца, текущего неполного года и динамики по выбранному периоду. Покрыть области: работники, входящие ресурсы, выполненные действия, полученный результат, задачи и активность пользователей.

Результат: аналитика строится из подтверждённых данных и явно учитывает неполные периоды.

Проверки: unit-тесты расчётов, граничные даты, пустые периоды, неполный месяц и неполный год.

### 9. Интерфейс владельца бизнеса

Собрать dashboard summary, вложенные аналитические разделы, диспетчерскую ленту и уведомления.

Реализованная часть шага: добавлена отдельная вкладка владельца `Диспетчерская`, которая запрашивает live-историю отправленных диспетчером регистраций с backend API. Левый rail владельца является единственным переключателем между `Обзор` и `Диспетчерская`; `Обзор` показывает server-owned показатели инцидентов и лаборатории за текущий месяц/сегодня и сохраняет прежние компактные блоки оборудования, месячной выработки и посетителей из dispatcher-истории. Подробные карточки последнего открытия и закрытия инцидента в `Обзоре` заменены новой числовой сводкой. `Диспетчерская` не показывает placeholder-плашки и выводит четыре рабочих раздела. Выбор раздела занимает отдельную верхнюю строку, переключатель периода располагается следующей строкой, а поля пользовательских дат при выборе `Своё` всегда открываются отдельной строкой под кнопками, включая широкий desktop. Единый переключатель периода для всех разделов содержит `Сегодня`, `Текущий месяц`, `Текущий год` и `Своё`; текущие месяц и год ограничены сегодняшней датой, а `Своё` открывает свободные поля начала/окончания, которые по умолчанию пусты и означают всю историю. В разделе `Инциденты` отдельная кнопка `Все незакрытые` одной операцией показывает серверный список открытых инцидентов за всю доступную историю независимо от выбранного периода и от загруженных страниц ленты, не меняя период остальных разделов; его длина всегда совпадает с показателем `Не закрыто сейчас` в `Обзоре`. `Выработка` разделена на шесть кнопок-таблиц: формовка, сортировка, неформованная продукция, цех обжига шамота, замеры банок и участок грануляции. Для формовки и сортировки показаны суточные и накопительные месячные план/факт с разницей; в таблицах неформованной продукции и шамота отдельная колонка показывает только названия нормализованных марок, а суточные и месячные значения остаются в собственных колонках; банки показывают начало, конец и расход; грануляция — суточные и месячные суммы фракций `16/30` и `12/18`. Месячный итог строится по последней записи каждого дня с начала календарного месяца до даты строки, даже если начало месяца не входит в видимый пользовательский диапазон; клик по дате открывает полный набор заполненных показателей в server-owned порядке полей формы. `Оборудование` агрегируется за диапазон по названию, суммарной выработке, суммарному простою и причинам простоя с часами; клик по названию оборудования открывает окно расшифровки с дневными строками из текущего периода, чтобы владелец видел составляющие итоговых чисел. `Инциденты` объединяют открытие и закрытие, показывают статус и включают записи, которые не были закрыты к началу выбранного диапазона. `Посетители` показывают входы за тот же выбранный период с временем выхода или пометкой, что выход не отмечен. В Vite dev-режиме при недоступном backend та же dispatcher-история читается из локального тестового `localStorage` и помечает источник данных.

Результат: владелец бизнеса получает обзор своего бизнеса, динамику и проблемные зоны без доступа к платформенным административным возможностям.

Проверки: typecheck, build, ручная проверка основных сценариев.

### 10. Расширенный рабочий интерфейс

Собрать формы ввода и корректировки данных, доступную статистику по серверно выданным правам и напоминания о событиях.

Реализованная часть шага: должность `Экономист` получила отдельную вкладку `План выработки` со свободным выбором месяца и категории, отдельным календарём каждой категории, пресетами всех календарных дней и понедельника–пятницы, ручной корректировкой дат и независимым сохранением категории в append-only месячный снимок. После каждого сохранения нижняя серверная сводка обновляется сразу и показывает, сколько из четырёх расписаний уже заполнено. Эта capability не выдаётся автоматически; администратор может назначить вкладку любой неадминистративной должности.

Результат: работник или пользователь с расширенными рабочими правами может поддерживать данные своего направления и видеть только разрешённую аналитику.

### 12. Интерфейс администратора

Добавить управление пользователями, типами аккаунтов, должностями, базой аккаунтов и аналитической базой. Отдельно предусмотреть смену паролей при ротации сотрудников.

Реализованная часть шага: администратор управляет учётными записями и отдельным server-backed каталогом должностей. У должности задаются название и компактный список только рабочих вкладок; поля базового кабинета и пользовательского выбора административных панелей нет. В таблице `Должности` исходный аккаунт `admin` отдельно включает `Права админа`: backend добавляет такой должности только `Учётные записи` и полномочия управления обычными аккаунтами, должностями и уведомлениями, а корневые панели предпросмотра, БД, порядка вкладок и журнала действий не выдаёт. Делегированный администратор может менять рабочие вкладки только неотмеченных должностей; отмеченные должности и назначенные им аккаунты защищены от его изменений. Порядок должностей меняется кнопками `Выше` / `Ниже` и автоматически сохраняется через 5 секунд; изменение рабочих вкладок или прав отзывает затронутые сессии. Отдельная корневая панель `Вкладки` позволяет системному администратору переставить и явно сохранить общую server-owned последовательность левого rail; `Предпросмотр`, `Вкладки`, `БД` и `Действия пользователей` остаются server-gated панелями системного администратора. Явная защита критичных аккаунтов из миграции `035_protected_admin_accounts` сохраняется и объединяется с эффективной защитой по должности с правами админа. Импорт Google Sheets остаётся отдельным server-gated двухшаговым действием без перезаписи существующих записей и без email/MAX-уведомлений.

Вкладка `Действия пользователей` показывает понятный журнал за последние три календарных месяца: фильтр по каждому аккаунту отдельно, категории действий, время, имя/должность/логин автора и раскрываемые введённые значения. Просмотры фиксируют открытие основных вкладок и диспетчерских форм, но не каждый клик. Для администратора доступ проверяется backend-ом через `platform.view_audit`; у любой неадминистративной должности вкладка включается отдельно и получает `business.view_user_actions`, а backend возвращает только аккаунты и события organization scope. Старые audit-события остаются в БД и только не попадают в текущую выборку.

Результат: администратор может обслуживать структуру платформы без прямого вмешательства в аналитику вне разрешённых действий.

Проверки: тесты административных прав, запретов для неадминистраторов и валидации критичных действий.

Миграция `051_protected_account_positions` добавила legacy-колонку `account_positions.is_admin_protected`; теперь она означает `Права админа`, а не отдельную пользовательскую защиту. Миграция `056_position_admin_rights` производно выдаёт отмеченной должности только управление учётными записями, удаляет у пользовательских должностей корневые админские панели, синхронизирует активные доступы и отзывает сессии. Только исходный `admin` управляет отметкой и может изменять, удалять или сдвигать такую должность; server-side проверки выполняются повторно внутри блокирующих транзакций, а назначенные ей аккаунты получают эффективную защиту.

### 13. Диспетчерская лента и уведомления

Собрать единый поток событий: новые записи, ожидание подтверждения, отклонения, исправления, напоминания, просрочки и интеграционные ошибки.

Реализованная часть шага: для диспетчерских отправок добавлен первый live-feed contract `GET /api/dispatcher/submissions` через remote API. Endpoint поддерживает фильтры `formId`, `dateFrom`, `dateTo`, постраничные `limit`/`offset` и возвращает `summary` по количеству регистраций; вкладка владельца автоматически дочитывает все страницы истории. После успешного `POST /api/dispatcher/submissions` backend отправляет email- и MAX-уведомления по открытию/закрытию инцидента, входу/выходу посетителя и выработке в человекочитаемом формате, а оборудование рассылает только после полного batch-сохранения через `POST /api/dispatcher/equipment-report` одним кратким сообщением на все позиции дневного отчёта. Адресаты этих четырёх типов берутся из server-owned матрицы аккаунтов с административным разрешением и выбранным пользователем каналом; Google Sheets больше не определяет их. Для закрытия инцидента сервер дополнительно подтягивает из сохранённого открытия дату/время, место, тип, критичность и описание: уведомление после номера показывает эти исходные данные, затем введённые при закрытии корневые причины и предотвращающие меры, время закрытия и утвердившего. Тестовая среда сохраняет тот же формат и добавляет в конце отдельное примечание `Тестовое сообщение`. Новые pending-таблицы ОЦ по-прежнему отправляют краткое уведомление диспетчерам строк `2–20` Google Sheets колонок `Адресаты Диспетчеры (емейлы)` и `Адресаты Диспетчеры (МАКС)`, а подтверждённые таблицы — полное содержимое отдельным адресатам колонок `Адресаты ОЦ (емейлы)` и `Адресаты ОЦ (МАКС)`; возвраты наружу не рассылаются. Это ещё не единая диспетчерская лента всех событий.

Отправленный диспетчером отчёт `Выработка` после commit рассылается по email и MAX пользователям с разрешённым типом `production_reports` и выбранным каналом. В тексте используются русские названия статуса и всех полей формы, включая динамические марки и факты четырёх категорий; техническая строка времени получения и внутренние имена полей не выводятся.

Email- и MAX-уведомление по оборудованию оформлено как нумерованный отчёт в порядке оборудования из анкеты: заголовок и дата вынесены отдельно, выработка, причина простоя, время и примечание показываются отдельными строками, нулевые показатели скрываются, а блоки оборудования разделяются пустой строкой.

Результат: владелец бизнеса, администратор и ответственные работники видят разрешённые рабочие события в одном месте.

Проверки: тесты фильтрации событий по роли, организации и статусу.

### 14. Контракты интеграций

Подготовить adapter-контракты для 1C, Excel, Google Sheets, Email и MAX без реальных секретов и SDK. Для Excel и Google Sheets отдельно описать настройку форматирования импорта.

Реализованная часть шага: первый Google Sheets reference-source добавлен без SDK и без хранения секретов в git. Backend умеет читать публичный CSV или закрытую таблицу через service account JSON на сервере, ищет значения под колонками `Места (цех/участок)` и `Ответственный за регистрацию` с двоеточием или без него, по умолчанию перечитывает результат при каждом запросе форм и обогащает серверное описание формы `Открытие инцидента`. Этот же источник читает email-адресатов и MAX ID уведомлений из фиксированных строк, включая колонки подтверждённых таблиц ОЦ `Адресаты ОЦ (емейлы)`/`Адресаты ОЦ (МАКС)` и колонки pending-уведомлений `Адресаты Диспетчеры (емейлы)`/`Адресаты Диспетчеры (МАКС)`. Для исторической миграции добавлен отдельный workbook reader exact-вкладок и import-specific parser: он читает неформатированные Google serial даты, сохраняет московское историческое время, строит lifecycle-записи инцидентов/посетителей и выдаёт предупреждения по legacy-расхождениям до подтверждения. Email-рассылка реализована через SMTP-конфиг, MAX-рассылка — через bot token и HTTP API; для Jino можно указать `MAX_CA_CERT_FILE` с доверенным PEM сертификатом Минцифры без отключения TLS, секреты хранятся только в `server/.env` и не коммитятся в git.

### 15. Backend и постоянное хранение

После стабилизации frontend-прототипа выбрать backend, схему хранения, auth, audit storage и API-контракты. Frontend-only проверки доступа не считать достаточной защитой.

Текущее состояние: backend workspace `server/` хранит пользователей, password credentials, account access, каталог должностей с единым server-owned порядком, общий порядок левой панели, сессии, dispatcher submissions и append-only `user_audit_events` в MariaDB/MySQL. Admin API создаёт отдельные login identity/access, отклоняет повторный login, сбрасывает пароль, создаёт, редактирует и атомарно переупорядочивает должности; авторизация читает navigation items и capabilities из назначенной должности. API настройки должности принимает только `business.*`, а `admin.accounts` и capabilities управления доступом выводит из server-owned отметки прав админа. Корневые `admin.account_preview`, `admin.navigation`, `admin.database` и `admin.user_actions` не распространяются через пользовательские должности. Только системный администратор под `platform.manage_navigation_order` меняет полную последовательность левой панели, а backend отдаёт каждому вошедшему аккаунту его разрешённое подмножество в этом порядке. Только канонический login `admin` меняет права админа и явную защиту аккаунтов; отмеченные должности и назначенные им аккаунты атомарно закрыты от изменений делегированными администраторами. `admin.account_preview` разрешает только чтение каталогов аккаунтов/должностей и GET рабочих данных без производных изменяющих `business.*` capabilities. `/api/admin/access-levels` удалён. Миграции `056_position_admin_rights` и `058_navigation_order` нормализуют административные права, синхронизируют `account_accesses` и отзывают затронутые сессии; остальные серверные границы auth, audit, database API, test/production и Jino deploy сохраняются без изменений. Production impersonation, безопасный bootstrap reset с re-auth/backup guard и общая аналитическая БД ещё не реализованы.

Миграция `009_remove_account_access_levels` завершает переход к полностью индивидуальным настройкам: она не меняет сохранённые `navigation_items` и capabilities аккаунтов, удаляет все оставшиеся связи и затем удаляет колонку `access_level_id` вместе с таблицей пресетов. Endpoint `/api/admin/access-levels` и связанные frontend/backend-контракты удалены.

Каталог должностей хранит server-owned отметку прав админа в legacy-колонке `is_admin_protected`. Канонический login `admin` управляет отметкой; отмеченная должность получает только `Учётные записи`, а корневые админские панели остаются у системного администратора. Для делегированных управляющих изменение, удаление, перемещение и назначение такой должности блокируются атомарно, а назначенные ей аккаунты считаются защищёнными. Миграция `056_position_admin_rights` синхронизирует производные вкладки, capabilities и активные доступы.

Результат: появляется реальная доверенная граница для данных, ролей, подтверждений, истории и интеграций.

Проверки: тесты API-контрактов, авторизации, валидации входа, миграций и audit trail.

Для доработки задачи 3 в `Диспетчер → Выработка → Замеры банок` проверить новую дату: поля четырёх замеров, `Засыпали`, `Отгрузили` и мастера ЦОШ должны редактироваться; обязательны первые замеры всех трёх банок и мастер. На следующий календарный день начало по обоим расчётным весам должно совпасть с концом сохранённой предыдущей диспетчерской сводки.

Для доработки задачи 3 отдельно проверить параллельность двух весов: в `Огнеупорный цех → Сводка по ЦОШ` и в `Диспетчерская → Выработка` за дату, у которой уже есть предыдущая подтверждённая сводка, строка `Расчётный вес по отгрузкам, т` должна равняться предыдущему значению этой же строки плюс `Засыпали` минус `Отгрузили` и не меняться при правке замеров, тогда как `Расчётный вес по замерам, т` от замеров меняться должен.
