# План реализации НМОУ Вектор (Система управления бизнесом)

## Цель продукта

НМОУ Вектор — платформа для мониторинга ключевых показателей организации и их динамики во времени. Каждый экземпляр сайта обслуживает ровно одну организацию и до 50 одновременных пользователей; для другой организации разворачивается отдельный экземпляр со своей БД.

Платформа должна разделять четыре типа аккаунта: администратора с максимальными правами, руководителя с просмотром всей статистики организации, работника с доступом только к отдельным рабочим функциям и диспетчера с доступом только к отправке диспетчерской формы. Система должна проводить данные через подтверждение перед использованием в аналитике, сохранять историю исправлений и готовиться к интеграциям с 1C, Excel, Google Sheets, Email и MAX.

## Текущее состояние после очистки

- Тестовая визуальная страница удалена.
- Тестовые Excel-данные и агрегаты удалены из проекта.
- Проект оставлен как чистый Vite + React + TypeScript + CSS каркас.
- Документация в `docs/` держит короткий локальный runbook `docs/local-server-run.md` и отдельную инструкцию внешнего Google Sheets источника `docs/google-sheets-source.md`.
- Добавлен первый TypeScript-контракт серверного ответа для типов аккаунта и прав доступа в `src/contracts/accounts.ts`.
- Собран минимальный app shell: left rail, кнопка выхода и рабочие поверхности без placeholder-плашек после входа.
- Диспетчерская система перенесена в backend-контур как 6 активных server-owned форм и единый журнал регистраций.
- Реальная разработка должна начинаться от этого плана, без переноса старого визуального прототипа.

## Технические правила

- Не добавлять внешний auth provider, state manager, chart library, UI framework, SDK интеграций и новые зависимости без отдельной задачи и проверки текущих локальных возможностей.
- Держать типы аккаунтов, доступы, статусы, периоды и показатели типизированными и централизованными.
- UI должен быть тонким: отображение, ввод и вызов прикладной логики.
- Бизнес-правила, проверки, переходы статусов, права доступа и подготовку данных держать отдельно от JSX и CSS.
- Любые формы, импорты, подтверждения, исправления, доступы, аудит и интеграции считать security-sensitive и покрывать проверками.
- Не использовать реальные приватные данные в тестовом контенте интерфейса.
- Все реальные бизнес-данные, пользовательские данные, права, аналитика, подтверждения и история должны храниться и проверяться на сервере.
- Клиент хранит только типы контрактов, UI-состояние и статический текст интерфейса; итоговые данные и разрешения получает по запросу к серверу.
- В remote/server-PC/VPS режиме открывать в сеть только backend API; MariaDB/MySQL оставлять локальной для backend или доступной только по разрешённому IP и не публиковать порт `3306` наружу без отдельного решения.
- `docs/local-server-run.md` держать коротким runbook локального запуска: отдельно локальный Docker для MariaDB и отдельно локальный запуск backend/frontend.
- Внешние справочники из Google Sheets подключать через backend, а не через frontend; текущий Google Sheets источник для полей `Место (цех/участок)` и `Ответственный за регистрацию` должен работать либо через публичный CSV, либо через service account JSON для закрытой таблицы и документироваться в `docs/google-sheets-source.md`.
- Email- и MAX-рассылку диспетчерских событий выполнять на backend после успешного сохранения формы; адресаты должны читаться из Google Sheets фиксированными строками, SMTP-пароли и MAX bot token хранить только в `server/.env`, а ошибка отправки уведомления не должна отменять уже сохранённую dispatcher submission. Отчёт оборудования рассылать одним кратким дневным batch-сообщением после полного `/api/dispatcher/equipment-report`, а не отдельным уведомлением на каждую позицию.
- Справочники Google Sheets являются источником актуальных вариантов выбора, но не источником истории: отправленные записи должны хранить выбранное значение в payload, чтобы удалённые из справочника люди и значения оставались доступны в старой аналитике.

## Последовательность реализации

### 1. Базовая серверная модель аккаунтов и данных

Сначала зафиксировать минимальные типы серверных контрактов: пользователь, тип аккаунта, platform/organization scope, выданные сервером права, показатель, период, статус ввода данных, статус подтверждения, событие аудита и канал интеграции. Отдельной runtime-сущности бизнеса и tenant ID нет.

Реализованная часть шага: четыре типа аккаунта `admin`, `business_owner`, `worker`, `dispatcher`; серверный ответ access/profile; контракты user profile, data entry status, confirmation status, dispatcher form definitions, dispatcher submissions, dispatcher feed summary и audit event summary. Администратор имеет platform scope, остальные аккаунты — organization scope; multi-business и подразделения удалены как неиспользуемые сущности. Клиент не хранит локальную матрицу прав как источник истины и не содержит прикладные фикстуры.

Результат: типизированная основа, на которую можно опирать UI и backend-контракты без смешивания данных с визуалом. Клиентская boundary для `access/profile` уже существует, а первый backend-контур реализован для dispatcher submissions; остальные backend-домены ещё впереди.

Проверки: typecheck; unit-тесты добавлять тогда, когда появятся функции правил доступа, валидации или переходов статусов.

### 2. Каркас приложения и навигации

Собрать первый реальный экран без старого визуального прототипа: запрос текущего access/profile с сервера, отображение типа аккаунта, переключение доступных разделов и пустые рабочие области там, где сервер ещё не отдаёт данные.

Первый shell уже собран как визуальная основа без production backend: профиль и доступы запрашиваются через `access/profile` boundary. В локальном Vite dev server endpoint отвечает профилем выбранной dev-сессии или `{"profile": null}`, а при отсутствующей `/api`-ручке static/frontend-хостинга вход может временно собрать клиентскую тестовую dev-сессию в `sessionStorage`. После входа пользователь может выйти из временного dev-аккаунта через общую навигацию и вернуться к выбору типа доступа; desktop rail можно свернуть до логотипа, а mobile drawer открывается из верхней панели и доступно закрывается без смены страницы. Рабочие области не показывают декоративные placeholder-плашки вместо отсутствующих серверных данных.

Результат: пользователь видит структуру продукта, но без фальшивой аналитики и без приватных данных.

Проверки: typecheck, build, ручной запуск через Vite.

### 3. Матрица ролей и доступов

Описать capabilities для серверного профиля доступа: управление пользователями, управление интеграциями, просмотр аудита, просмотр логов, использование debug-функций, просмотр статистики организации, отправка форм, отправка диспетчерских форм, просмотр диспетчерской истории, просмотр уведомлений и просмотр собственных отправок.

Реализованная часть шага: capability-значения централизованы в `src/contracts/accounts.ts`, `access/profile` отклоняет неизвестные capability, локальный Vite server выдаёт dev-профили с разными capabilities для admin, business owner, worker и dispatcher, а admin-профиль показывает только реальные capabilities из server profile без заглушечных административных панелей.

Результат: интерфейс получает права от сервера и использует их только для отображения доступных действий; сервер остаётся единственным источником защиты.

Проверки: unit-тесты на позитивные, запрещённые и пограничные сценарии доступа.

### 4. Область данных организации

Использовать одну серверную границу данных организации без tenant-иерархии: администратор работает в platform scope, любой неадминистративный аккаунт — в organization scope текущего deployment.

Результат: должность меняет кабинет и права, но не создаёт tenant-сущности или технические подразделения и не разрывает общую историю организации.

Проверки: миграция старых scopes, создание аккаунтов всех типов, смена должности, typecheck, build.

### 5. Ввод данных пользователями

Сделать поток ввода данных для работника: выбор доступной формы или рабочего контекста, периода, показателя, натурального объёма, денежного значения, комментария и источника.

Текущее состояние: рабочая форма для роли `worker` ещё не реализована, и worker не получает список диспетчерских форм. Диспетчер сначала выбирает одну из 6 активных server-owned форм в 4 визуальных группах: производство, оборудование, открытие/закрытие инцидента и вход/выход посетителя. Группы отличаются позицией и цветовым акцентом, после выбора диспетчер может вернуться к выбору из анкеты. `Выработка` повторяет табличные блоки бумажной сводки: дату отчёта, формовку, сортировку, четыре строки неформованной продукции, выпуск шамота, три замера банок и участок грануляции; дата обязательна вместе хотя бы с одним показателем. Диспетчерская отправка идёт через remote boundary `VITE_SMB_REMOTE_API_URL` в backend workspace `server/`, где сервер валидирует `formId`, разрешённые поля `payload`, даты, месяцы, целые и дробные числа, select-значения и сценарные ограничения для выработки, оборудования, инцидентов и посетителей. Поля `Место (цех/участок)` и `Ответственный за регистрацию` в открытии инцидента приходят как серверные select из Google Sheets источника: публичного CSV или закрытой таблицы через service account; при `GOOGLE_SHEETS_CACHE_TTL_MS=0` источник перечитывается при каждом запросе форм, а при недоступной таблице backend оставляет поля текстовыми, чтобы форма не блокировалась. Закрытие инцидента выбирается из текущих незакрытых инцидентов по сохранённому номеру `INC-год-номер`; инциденты не закрываются автоматически в конце дня, а клиент, backend и локальный fallback позволяют закрыть открытый инцидент в любой момент после открытия и отклоняют закрытие отсутствующего или уже закрытого номера. Поля дат получают сегодняшние defaults, поля дата-время — текущую дату и время, поля месяца отображаются и проверяются в формате `ММ.ГГГГ`, затем запись сохраняется в MariaDB/MySQL. Для анкеты `Оборудование` диспетчер видит прогресс по внесённым позициям за выбранную дату отчёта, печатает данные отдельно для каждого оборудования, добавляет выбранную позицию в дневной пакет кнопкой `Внести данные` и может нажать `Отправить отчет начальству` только после внесения всех позиций; полный пакет уходит через `POST /api/dispatcher/equipment-report`, а неполный пакет отклоняется backend-ом и локальным fallback. Уже внесённая позиция остаётся фиксированной версией дневного пакета: если диспетчер меняет её поля, UI помечает пункт `*`, показывает `Обновить данные`, а при переходе к другому оборудованию показывает короткое предупреждение с кнопками `Сбросить` и `Остаться`; автоматического сохранения в предупреждении нет. Отправка с теми же `reportDate` и `equipment` обновляет существующие записи, а клиент хранит напечатанные поля по каждому оборудованию как локальный UX-черновик, всегда подставляя сегодняшнюю дату при повторном входе или переключении оборудования. Клиентская pre-submit проверка оборудования не отправляет payload на сервер, если выбрана причина простоя без времени простоя больше 0, если простой больше 8 часов или если простой меньше 8 часов при нулевой/пустой выработке; backend и локальный тестовый fallback повторяют эти ограничения. Формы посетителей разделены на `Вход посетителя` с серверным `entryAt` и `Выход посетителя` с серверным `exitAt`: повторный вход того же открытого посетителя отклоняется, а выход выбирается только из посетителей, которые вошли сегодня и ещё не вышли. Газовые формы остаются legacy-id для чтения старой истории, но не выдаются в список выбора и не принимаются как активные формы ввода. Если backend не настроен или недоступен в Vite dev-режиме, сервисы диспетчерской используют локальный тестовый `localStorage` fallback с явной UI-пометкой и теми же локальными правилами для script-backed анкет; это не production-хранение и не заменяет серверную валидацию.

Актуальное уточнение по подсказкам анкеты `Оборудование`: ошибки локальной проверки после кнопки `Внести данные` показываются красной подсказкой, а успешное внесение остаётся обычным статусом. Если время простоя больше 0, причина простоя обязательна; если выбрана причина простоя `Резерв`, время простоя должно быть ровно 8 часов.

Актуальное уточнение по анкете `Оборудование`: `Дата отчета` является отдельной настройкой дневного отчёта; локальные UX-черновики и позиции, внесённые кнопкой `Внести данные`, хранятся по ключу выбранной даты и оборудования, а при выборе даты UI показывает сохранённые в БД отметки именно за эту дату и не переносит статус внесённой позиции с другого дня.

Актуальное уточнение по состояниям иконок анкеты `Оборудование`: при смене `Дата отчета` клиент заново запрашивает серверную историю через фильтр `reportDate` по payload отчёта, а legacy/local данные без серверной записи поднимаются только как `черновик`, не как `внесено в отчёт`. Иконка `нет данных` имеет серую заливку и тёмно-серый текст, `черновик` — серую заливку и чёрный текст.

Актуальное уточнение по навигации диспетчерских форм: после успешной отправки выработки, дневного отчёта оборудования, регистрации/закрытия инцидента, регистрации входа посетителя или регистрации выхода посетителя интерфейс автоматически возвращается на страницу выбора форм и показывает самозакрывающееся всплывающее уведомление об отправке; при ошибке отправки или проверки заполнения пользователь остаётся на текущей форме.

Актуальное уточнение по анкете `Закрытие инцидента`: после открытия сначала показывается отдельный компактный экран незакрытых инцидентов в виде обычных кнопок; после выбора открываются существующие поля закрытия с уже подставленным server-owned номером и возможностью выбрать другой инцидент. После первой успешной загрузки фокус получает первая кнопка инцидента, после выбора — карточка выбранного инцидента, а последующее фоновое обновление списка не перехватывает фокус повторно. Временная ошибка фонового обновления сохраняет открытую заполненную анкету; если успешное обновление подтверждает, что выбранный инцидент уже закрыт другим пользователем, UI возвращается к актуальному списку и показывает короткое объяснение.

Актуальное уточнение по пользовательским уведомлениям: для неадминистративных пользователей тосты, ошибки и статусные подсказки должны быть короткими и без технических деталей вроде id отправки, endpoint, CORS, `/health`, `localStorage`, remote/backend/server/feed; техническая диагностика остаётся в админских инструментах, логах, тестах и инструкциях.

Результат: черновик записи создаётся в статусе ожидания подтверждения и ещё не попадает в аналитический источник.

Проверки: валидация пустых, некорректных, отрицательных и неожиданных значений; unit-тесты правил создания записи.

### 9. Интерфейс владельца бизнеса

Собрать dashboard summary, вложенные аналитические разделы, диспетчерскую ленту и уведомления.

Реализованная часть шага: добавлена отдельная вкладка владельца `Диспетчерская`, которая запрашивает live-историю отправленных диспетчером регистраций с backend API. Левый rail владельца является единственным переключателем между `Обзор` и `Диспетчерская`; `Обзор` показывает компактную сводку по последним dispatcher submissions из того же server feed: оборудование, последний инцидент, последнее закрытие инцидента, последние посетители и текущее количество невышедших посетителей. `Диспетчерская` не показывает placeholder-плашки и выводит четыре рабочих раздела. Выбор раздела занимает отдельную верхнюю строку, переключатель периода располагается следующей строкой, а поля пользовательских дат при выборе `Своё` всегда открываются отдельной строкой под кнопками, включая широкий desktop. Единый переключатель периода для всех разделов содержит `Сегодня`, `Текущий месяц`, `Текущий год` и `Своё`; текущие месяц и год ограничены сегодняшней датой, а `Своё` открывает свободные поля начала/окончания, которые по умолчанию пусты и означают всю историю. `Выработка` показывает отчёты за выбранный период с ключевыми суточными показателями формовки и сортировки, итогами фактического выпуска неформованной продукции и шамота и выпуском сырцовой гранулы; клик по дате открывает полный набор заполненных показателей в server-owned порядке полей формы. `Оборудование` агрегируется за диапазон по названию, суммарной выработке, суммарному простою и причинам простоя с часами; клик по названию оборудования открывает окно расшифровки с дневными строками из текущего периода, чтобы владелец видел составляющие итоговых чисел. `Инциденты` объединяют открытие и закрытие, показывают статус и включают записи, которые не были закрыты к началу выбранного диапазона. `Посетители` показывают входы за тот же выбранный период с временем выхода или пометкой, что выход не отмечен. В Vite dev-режиме при недоступном backend та же dispatcher-история читается из локального тестового `localStorage` и помечает источник данных.

Результат: владелец бизнеса получает обзор своего бизнеса, динамику и проблемные зоны без доступа к платформенным административным возможностям.

### 12. Интерфейс администратора

Добавить управление пользователями, типами аккаунтов, должностями, базой аккаунтов и аналитической базой. Отдельно предусмотреть смену паролей при ротации сотрудников.

Реализованная часть шага: администратор управляет учётными записями и отдельным server-backed каталогом должностей. У должности задаются название, один из базовых кабинетов `Руководитель`, `Работник`, `Диспетчер` и компактный список вкладок с пояснениями; аккаунт выбирает должность и наследует её название, навигацию и capabilities без индивидуальных галочек. Изменение должности отзывает сессии всех связанных пользователей. Базово поддерживаются должности `Администратор`, `Владелец бизнеса`, `Председатель совета директоров`, `Член совета директоров`, `Генеральный директор`, `Работник` и `Диспетчер`; руководящие должности используют business-owner workspace. `Просмотр аккаунта` показывает полный каталог должностей и актуальные server-backed аккаунты, переиспользуя реальные кабинеты; административные карточки не запускают preview до production impersonation/audit-модели. `Учётные записи` также поддерживает создание логина, сброс пароля и временное отключение входа. Вкладка `БД` показывает только два прикладных раздела: пользователей и диспетчерские записи. Доступы и должности меняются только в профильных admin-экранах, где действуют полные правила смены доступа; системные/auth/архивные/append-only исторические таблицы не отображаются, но остаются в БД. Каждая показанная строка имеет server-owned набор редактируемых полей и понятные типы/варианты ввода; для диспетчерских записей поля строятся из определения конкретной формы, а raw payload, password hashes, session IDs, dedupe/source keys и технические ID не выводятся. Связующие значения отчёта оборудования, закрытия инцидента и выхода посетителя остаются server-owned и не меняются общим редактором; изменение показателей оборудования создаёт штатную ревизию полного дневного отчёта. Удаление строк и массовая очистка обоих разделов запрещены. Изменения дополнительно проверяют профильные capabilities, а затронутые сессии отзываются. В `БД` также добавлен server-gated двухшаговый импорт Google Sheets вкладок `Оборудование`, `Инциденты` и `Посетители`: администратор получает предпросмотр и отдельно подтверждает перенос без перезаписи существующих записей и без email/MAX-уведомлений. Импорт выполняется сразу в единую организацию без выбора, поиска или создания бизнес-сущности. Одинаковые lifecycle-записи схлопываются внутри файла и получают общий с live-формами organization-wide content key, поэтому повторный импорт, копия книги, параллельные импорты и одновременная диспетчерская отправка не создают дубли.

Вкладка `Действия пользователей` показывает понятный журнал за последние три календарных месяца: фильтр по каждому аккаунту отдельно, категории действий, время, имя/должность/логин автора и раскрываемые введённые значения. Просмотры фиксируют открытие основных вкладок и диспетчерских форм, но не каждый клик. Для администратора доступ проверяется backend-ом через `platform.view_audit`; у пользовательской должности с базовым кабинетом `Руководитель` вкладка включается отдельно и получает `business.view_user_actions`, а backend возвращает только аккаунты и события organization scope. Старые audit-события остаются в БД и только не попадают в текущую выборку.

Результат: администратор может обслуживать структуру платформы без прямого вмешательства в аналитику вне разрешённых действий.

Проверки: тесты административных прав, запретов для неадминистраторов и валидации критичных действий.

### 13. Диспетчерская лента и уведомления

Собрать единый поток событий: новые записи, ожидание подтверждения, отклонения, исправления, напоминания, просрочки и интеграционные ошибки.

Реализованная часть шага: для диспетчерских отправок добавлен первый live-feed contract `GET /api/dispatcher/submissions` через remote API. Endpoint поддерживает фильтры `formId`, `dateFrom`, `dateTo`, постраничные `limit`/`offset` и возвращает `summary` по количеству регистраций; вкладка владельца автоматически дочитывает все страницы истории. После успешного `POST /api/dispatcher/submissions` backend отправляет email- и MAX-уведомления по открытию/закрытию инцидента и входу/выходу посетителя в человекочитаемом формате, а оборудование рассылает только после полного batch-сохранения через `POST /api/dispatcher/equipment-report` одним кратким сообщением на все позиции дневного отчёта. Для закрытия инцидента сервер дополнительно подтягивает место из сохранённого открытия, чтобы строка `Место (цех/участок)` попадала в сохранённый payload закрытия и уведомления. Общие адресаты берутся из строк `2–20` Google Sheets колонок email/MAX, дополнительные адресаты механики — из строк `22–25`, электрики — из строк `27–30`; посетительские адресаты берутся из отдельных колонок `Адресаты по посетителям (емейлы)` и `Адресаты по посетителям (МАКС)` строк `2–20`. MAX поддерживает несколько ID в одной ячейке этих строк, спецгруппы добавляются по причине простоя, типу инцидента или тексту закрытия. Это ещё не единая диспетчерская лента всех событий.

Email- и MAX-уведомление по оборудованию оформлено как нумерованный отчёт в порядке оборудования из анкеты: заголовок и дата вынесены отдельно, выработка, причина простоя, время и примечание показываются отдельными строками, нулевые показатели скрываются, а блоки оборудования разделяются пустой строкой.

Результат: владелец бизнеса, администратор и ответственные работники видят разрешённые рабочие события в одном месте.

Проверки: тесты фильтрации событий по роли, организации и статусу.

### 14. Контракты интеграций

Подготовить adapter-контракты для 1C, Excel, Google Sheets, Email и MAX без реальных секретов и SDK. Для Excel и Google Sheets отдельно описать настройку форматирования импорта.

Реализованная часть шага: первый Google Sheets reference-source добавлен без SDK и без хранения секретов в git. Backend умеет читать публичный CSV или закрытую таблицу через service account JSON на сервере, ищет значения под колонками `Места (цех/участок)` и `Ответственный за регистрацию` с двоеточием или без него, по умолчанию перечитывает результат при каждом запросе форм и обогащает серверное описание формы `Открытие инцидента`. Этот же источник читает email-адресатов и MAX ID уведомлений из фиксированных строк. Для исторической миграции добавлен отдельный workbook reader exact-вкладок и import-specific parser: он читает неформатированные Google serial даты, сохраняет московское историческое время, строит lifecycle-записи инцидентов/посетителей и выдаёт предупреждения по legacy-расхождениям до подтверждения. Email-рассылка реализована через SMTP-конфиг, MAX-рассылка — через bot token и HTTP API; для Jino можно указать `MAX_CA_CERT_FILE` с доверенным PEM сертификатом Минцифры без отключения TLS, секреты хранятся только в `server/.env` и не коммитятся в git.

Результат: интеграции имеют безопасные границы и могут добавляться по одной без переписывания доменной логики.

Проверки: тесты нормализации входных данных, ошибок импорта и отсутствия логирования приватных payload.

### 15. Backend и постоянное хранение

После стабилизации frontend-прототипа выбрать backend, схему хранения, auth, audit storage и API-контракты. Frontend-only проверки доступа не считать достаточной защитой.

Текущее состояние: backend workspace `server/` хранит пользователей, password credentials, account access, каталог должностей, сессии, dispatcher submissions и append-only `user_audit_events` в MariaDB/MySQL. Admin API создаёт отдельные login identity/access, отклоняет повторный login, сбрасывает пароль, создаёт и редактирует должности; авторизация читает базовый кабинет, navigation items и capabilities из назначенной должности. `/api/admin/access-levels` удалён. Миграция `009_remove_account_access_levels` удалила старые presets, `010_dynamic_account_positions` ввела текущий каталог должностей, `014_dispatcher_spreadsheet_import_source` добавила уникальный source key для повторяемого импорта, `015_user_audit_events` создала постоянный журнал, а `016_remove_departments` удалила модель подразделений. Миграция `017_single_organization_scope` сохранила историю, перевела все неадминистративные доступы в organization scope, удалила business ID из рабочих таблиц и затем удалила таблицу бизнесов. Audit API серверно фиксирует входы/выходы, отправки форм, изменения БД, импорт, управление аккаунтами/должностями и allowlisted просмотры экранов; production-изменения и их audit-события проходят через общий транзакционный DB-контекст, а `GET /api/admin/audit-events` жёстко применяет rolling-окно трёх календарных месяцев и не удаляет более старые записи. Для администратора endpoint возвращает платформенный отчёт, а для руководителя с `business.view_user_actions` сервер ограничивает события и каталог аккаунтов organization scope. Database API отдаёт только безопасные редактируемые пользовательские представления; backend формирует поля редактора, валидирует статусы и диспетчерские формы, пересчитывает производные значения и не передаёт auth secrets, session identifiers, raw payload, dedupe/source keys и неизвестные таблицы. Import API отдельно валидирует прикладные данные, схлопывает одинаковые строки по нормализованному содержимому и транзакционно добавляет только отсутствующие dispatcher submissions единой организации, используя уникальный organization-wide `dedupe_key` как защиту от гонок. Лимит server/client dispatcher history увеличен до 2000 записей, чтобы первичный импорт 572 строк не вытеснил incident/visitor lifecycle из рабочих представлений. Test/production разделены через `VITE_SMB_APP_ENV`, `SMB_APP_ENV`, `DEV_ACCESS_ENABLED`, отдельные cookie/env/БД; production использует login/password auth и запрещает dev-session/client fallback. Personal plugin и VS Code extension `smb-jino-deploy` запускают существующий tracked deploy по SSH, не хранят секреты, требуют SSH-ключ, показывают актуальность test/production по post-publish marker, отображают один стандартный progress bar по реальным этапам deploy без автоматического открытия Output-панели и после публикации проверяют HTTP redirect и HTTPS health обеих сред; неинтерактивный SSH-runner отдельно активирует системный Jino Node.js 22 runtime из `/opt/alt` и проверяет Node/npm ещё в read-only preflight, а optional remote tests выполняются через последовательный `test:jino`, чтобы не превышать лимит процессов/потоков managed hosting. Production impersonation, безопасный bootstrap reset с re-auth/backup guard и общая аналитическая БД ещё не реализованы.

Миграция `009_remove_account_access_levels` завершает переход к полностью индивидуальным настройкам: она не меняет сохранённые `navigation_items` и capabilities аккаунтов, удаляет все оставшиеся связи и затем удаляет колонку `access_level_id` вместе с таблицей пресетов. Endpoint `/api/admin/access-levels` и связанные frontend/backend-контракты удалены.

Результат: появляется реальная доверенная граница для данных, ролей, подтверждений, истории и интеграций.

Проверки: тесты API-контрактов, авторизации, валидации входа, миграций и audit trail.
