# План реализации НМОУ Вектор (Система управления бизнесом)

## Цель продукта

НМОУ Вектор — платформа для мониторинга ключевых показателей бизнеса и их динамики во времени. Один пользовательский аккаунт может управлять несколькими бизнес-аккаунтами, а один бизнес должен поддерживать работу до 50 одновременных пользователей.

Платформа должна разделять четыре типа аккаунта: администратора с максимальными правами, владельца бизнеса с просмотром всей статистики своего бизнеса, работника с доступом только к отдельным рабочим функциям и диспетчера с доступом только к отправке диспетчерской формы. Система также должна поддерживать две модели оргструктуры, проводить данные через подтверждение перед использованием в аналитике, сохранять историю исправлений и готовиться к интеграциям с 1C, Excel, Google Sheets, Email и MAX.

## Технические правила

- Не добавлять внешний auth provider, state manager, chart library, UI framework, SDK интеграций и новые зависимости без отдельной задачи и проверки текущих локальных возможностей.
- Держать типы аккаунтов, доступы, статусы, периоды, показатели и оргструктуру типизированными и централизованными.
- UI должен быть тонким: отображение, ввод и вызов прикладной логики.
- Бизнес-правила, проверки, переходы статусов, права доступа и подготовку данных держать отдельно от JSX и CSS.
- Любые формы, импорты, подтверждения, исправления, доступы, аудит и интеграции считать security-sensitive и покрывать проверками.
- Не использовать реальные приватные данные в тестовом контенте интерфейса.
- Все реальные бизнес-данные, пользовательские данные, права, аналитика, подтверждения и история должны храниться и проверяться на сервере.
- Клиент хранит только типы контрактов, UI-состояние и статический текст интерфейса; итоговые данные и разрешения получает по запросу к серверу.
- В remote/server-PC/VPS режиме открывать в сеть только backend API; MariaDB/MySQL оставлять локальной для backend или доступной только по разрешённому IP и не публиковать порт `3306` наружу без отдельного решения.
- `docs/local-server-run.md` держать коротким runbook локального запуска: отдельно локальный Docker для MariaDB и отдельно локальный запуск backend/frontend.
- Внешние справочники из Google Sheets подключать через backend, а не через frontend; текущий Google Sheets источник для полей `Место (цех/участок)` и `Ответственный за регистрацию` должен работать либо через публичный CSV, либо через service account JSON для закрытой таблицы и документироваться в `docs/google-sheets-source.md`.
- Email- и MAX-рассылку диспетчерских событий выполнять на backend после успешного сохранения формы; адресаты должны читаться из Google Sheets фиксированными строками, SMTP-пароли и MAX bot token хранить только в `server/.env`, а ошибка отправки уведомления не должна отменять уже сохранённую dispatcher submission. Отчёт оборудования рассылать одним кратким дневным batch-сообщением после полного `/api/dispatcher/equipment-report`, а не отдельным уведомлением на каждую позицию.
- Справочники Google Sheets являются источником актуальных вариантов выбора, но не источником истории: отправленные записи должны хранить выбранное значение в payload, чтобы удалённые из справочника люди и значения оставались доступны в старой аналитике.

## Последовательность реализации

### 1. Базовая серверная модель аккаунтов и данных

Сначала зафиксировать минимальные типы серверных контрактов: бизнес-аккаунт, пользователь, тип аккаунта, область доступа, выданные сервером права, отдел, оргструктура, показатель, период, статус ввода данных, статус подтверждения, событие аудита и канал интеграции.

Реализованная часть шага: четыре типа аккаунта `admin`, `business_owner`, `worker`, `dispatcher`; серверный ответ access/profile; контракты business account, user profile, department, org structure mode, data entry status, confirmation status, dispatcher form definitions, dispatcher submissions, dispatcher feed summary и audit event summary. Клиент не хранит локальную матрицу прав как источник истины и не содержит бизнес-фикстуры.

Результат: типизированная основа, на которую можно опирать UI и backend-контракты без смешивания данных с визуалом. Клиентская boundary для `access/profile` уже существует, а первый backend-контур реализован для dispatcher submissions; остальные backend-домены ещё впереди.

Проверки: typecheck; unit-тесты добавлять тогда, когда появятся функции правил доступа, валидации или переходов статусов.

### 2. Каркас приложения и навигации

Собрать первый реальный экран без старого визуального прототипа: запрос текущего access/profile с сервера, отображение типа аккаунта, переключение доступных разделов и пустые рабочие области там, где сервер ещё не отдаёт данные.

Первый shell уже собран как визуальная основа без production backend: business/account значения запрашиваются через `access/profile` boundary. В локальном Vite dev server endpoint отвечает профилем выбранной dev-сессии или `{"profile": null}`, а при отсутствующей `/api`-ручке static/frontend-хостинга вход может временно собрать клиентскую тестовую dev-сессию в `sessionStorage`. После входа пользователь может выйти из временного dev-аккаунта через левый rail и вернуться к выбору типа доступа; рабочие области не показывают декоративные placeholder-плашки вместо отсутствующих серверных данных.

Результат: пользователь видит структуру продукта, но без фальшивой аналитики и без приватных данных.

Проверки: typecheck, build, ручной запуск через Vite.

### 3. Матрица ролей и доступов

Описать capabilities для серверного профиля доступа: управление бизнес-аккаунтами, управление пользователями, управление интеграциями, просмотр аудита, просмотр логов, использование debug-функций, просмотр всей статистики бизнеса, просмотр статистики отдела, отправка форм, отправка диспетчерских форм, просмотр диспетчерской истории, просмотр уведомлений и просмотр собственных отправок.

Реализованная часть шага: capability-значения централизованы в `src/contracts/accounts.ts`, `access/profile` отклоняет неизвестные capability, локальный Vite server выдаёт dev-профили с разными capabilities для admin, business owner, worker и dispatcher, а admin-профиль показывает только реальные capabilities из server profile без заглушечных административных панелей.

Результат: интерфейс получает права от сервера и использует их только для отображения доступных действий; сервер остаётся единственным источником защиты.

Проверки: unit-тесты на позитивные, запрещённые и пограничные сценарии доступа.

### 4. Оргструктура

Реализовать две модели отображения: классическую и существующую/current. Переключение модели не должно терять контекст выбранного бизнеса, отдела, периода и аналитики.

Результат: владелец бизнеса и администратор могут менять представление структуры без изменения исходных данных.

Проверки: тесты преобразования/выбора структуры, typecheck, build.

### 5. Ввод данных отделами

Сделать поток ввода данных для работника: выбор доступной формы, отдела или рабочего контекста, периода, показателя, натурального объёма, денежного значения, комментария и источника.

Текущее состояние: рабочая форма для роли `worker` ещё не реализована, и worker не получает список диспетчерских форм. Диспетчер сначала выбирает одну из 5 активных серверно описанных диспетчерских форм в 3 визуальных группах: оборудование отдельно, открытие/закрытие инцидента вместе, вход/выход посетителя вместе. Группы отличаются позицией и цветовым акцентом, после выбора диспетчер может вернуться к выбору из анкеты. Диспетчерская отправка идёт через remote boundary `VITE_SMB_REMOTE_API_URL` в backend workspace `server/`, где сервер валидирует `formId`, разрешённые поля `payload`, даты, месяцы, целые и дробные числа, select-значения и сценарные ограничения из исходных Apps Script для оборудования, инцидентов и посетителей. Поля `Место (цех/участок)` и `Ответственный за регистрацию` в открытии инцидента приходят как серверные select из Google Sheets источника: публичного CSV или закрытой таблицы через service account; при `GOOGLE_SHEETS_CACHE_TTL_MS=0` источник перечитывается при каждом запросе форм, а при недоступной таблице backend оставляет поля текстовыми, чтобы форма не блокировалась. Закрытие инцидента выбирается из текущих незакрытых инцидентов по сохранённому номеру `INC-год-номер`; инциденты не закрываются автоматически в конце дня, а клиент, backend и локальный fallback позволяют закрыть открытый инцидент в любой момент после открытия и отклоняют закрытие отсутствующего или уже закрытого номера. Поля дат получают сегодняшние defaults, поля дата-время — текущую дату и время, поля месяца отображаются и проверяются в формате `ММ.ГГГГ`, затем запись сохраняется в MariaDB/MySQL. Для анкеты `Оборудование` диспетчер видит прогресс по внесённым позициям за выбранную дату отчёта, печатает данные отдельно для каждого оборудования, добавляет выбранную позицию в дневной пакет кнопкой `Внести данные` и может нажать `Отправить отчет начальству` только после внесения всех позиций; полный пакет уходит через `POST /api/dispatcher/equipment-report`, а неполный пакет отклоняется backend-ом и локальным fallback. Уже внесённая позиция остаётся фиксированной версией дневного пакета: если диспетчер меняет её поля, UI помечает пункт `*`, показывает `Обновить данные`, а при переходе к другому оборудованию показывает короткое предупреждение с кнопками `Сбросить` и `Остаться`; автоматического сохранения в предупреждении нет. Отправка с тем же бизнесом, `reportDate` и `equipment` обновляет существующие записи, а клиент хранит напечатанные поля по каждому оборудованию как локальный UX-черновик, всегда подставляя сегодняшнюю дату при повторном входе или переключении оборудования. Клиентская pre-submit проверка оборудования не отправляет payload на сервер, если выбрана причина простоя без времени простоя больше 0, если простой больше 8 часов или если простой меньше 8 часов при нулевой/пустой выработке; backend и локальный тестовый fallback повторяют эти ограничения. Формы посетителей разделены на `Вход посетителя` с серверным `entryAt` и `Выход посетителя` с серверным `exitAt`: повторный вход того же открытого посетителя отклоняется, а выход выбирается только из посетителей, которые вошли сегодня и ещё не вышли. Газовые формы остаются legacy-id для чтения старой истории, но не выдаются в список выбора и не принимаются как активные формы ввода. Если backend не настроен или недоступен в Vite dev-режиме, сервисы диспетчерской используют локальный тестовый `localStorage` fallback с явной UI-пометкой и теми же локальными правилами для script-backed анкет; это не production-хранение и не заменяет серверную валидацию. Production auth и server-side capability checks ещё не реализованы.

Актуальное уточнение по подсказкам анкеты `Оборудование`: ошибки локальной проверки после кнопки `Внести данные` показываются красной подсказкой, а успешное внесение остаётся обычным статусом. Если время простоя больше 0, причина простоя обязательна; если выбрана причина простоя `Резерв`, время простоя должно быть ровно 8 часов.

Актуальное уточнение по анкете `Оборудование`: `Дата отчета` является отдельной настройкой дневного отчёта; локальные UX-черновики и позиции, внесённые кнопкой `Внести данные`, хранятся по ключу выбранной даты и оборудования, а при выборе даты UI показывает сохранённые в БД отметки именно за эту дату и не переносит статус внесённой позиции с другого дня.

Актуальное уточнение по состояниям иконок анкеты `Оборудование`: при смене `Дата отчета` клиент заново запрашивает серверную историю через фильтр `reportDate` по payload отчёта, а legacy/local данные без серверной записи поднимаются только как `черновик`, не как `внесено в отчёт`. Иконка `нет данных` имеет серую заливку и тёмно-серый текст, `черновик` — серую заливку и чёрный текст.

Актуальное уточнение по навигации диспетчерских форм: после успешной отправки дневного отчёта оборудования, регистрации/закрытия инцидента, регистрации входа посетителя или регистрации выхода посетителя интерфейс автоматически возвращается на страницу выбора форм и показывает самозакрывающееся всплывающее уведомление об отправке; при ошибке отправки или проверки заполнения пользователь остаётся на текущей форме.

Актуальное уточнение по пользовательским уведомлениям: для неадминистративных пользователей тосты, ошибки и статусные подсказки должны быть короткими и без технических деталей вроде id отправки, endpoint, CORS, `/health`, `localStorage`, remote/backend/server/feed; техническая диагностика остаётся в админских инструментах, логах, тестах и инструкциях.

Результат: черновик записи создаётся в статусе ожидания подтверждения и ещё не попадает в аналитический источник.

Проверки: валидация пустых, некорректных, отрицательных и неожиданных значений; unit-тесты правил создания записи.

### 6. Подтверждение данных другими отделами

Добавить очередь подтверждений: какой отдел внёс данные, какой отдел должен подтвердить, текущий статус, комментарии, решение и timestamp.

Результат: только подтверждённые записи становятся источником аналитики.

Проверки: тесты переходов статусов, запрет самоподтверждения там, где оно недопустимо, проверка истории решений.

### 7. Исправления и история

Реализовать поток корректировки уже существующих данных: причина исправления, автор, дата, старое значение, новое значение, статус исправления и связь с исходной записью.

Результат: ошибки, перенос бумажных данных и последующие корректировки не затирают историю.

Проверки: unit-тесты неизменности аудита и корректных переходов статусов.

### 8. Аналитические периоды и KPI

Собрать расчётные правила для последнего дня, текущего неполного месяца, текущего неполного года и динамики по выбранному периоду. Покрыть области: работники, входящие ресурсы, выполненные действия, полученный результат, задачи и активность пользователей.

Результат: аналитика строится из подтверждённых данных и явно учитывает неполные периоды.

Проверки: unit-тесты расчётов, граничные даты, пустые периоды, неполный месяц и неполный год.

### 9. Интерфейс владельца бизнеса

Собрать dashboard summary, переключатель оргструктуры, вкладки отделов, вложенные аналитические разделы, диспетчерскую ленту и уведомления.

Реализованная часть шага: добавлена отдельная вкладка владельца `Диспетчерская`, которая запрашивает live-историю отправленных диспетчером регистраций с backend API. Левый rail владельца является единственным переключателем между `Обзор` и `Диспетчерская`; `Обзор` показывает компактную сводку по последним dispatcher submissions из того же server feed: оборудование, последний инцидент, последнее закрытие инцидента, последние посетители и текущее количество невышедших посетителей. `Диспетчерская` не показывает placeholder-плашки и выводит три рабочих раздела. `Оборудование` агрегируется за диапазон по названию, суммарной выработке, суммарному простою и причинам простоя с часами; клик по названию оборудования открывает окно расшифровки с дневными строками из текущего периода, чтобы владелец видел составляющие итоговых чисел. `Инциденты` объединяют открытие и закрытие, показывают статус и включают записи, которые не были закрыты к началу выбранного диапазона. `Посетители` выбираются только за один день и показывают входы с временем выхода или пометкой, что выход не отмечен. В Vite dev-режиме при недоступном backend та же dispatcher-история читается из локального тестового `localStorage` и помечает источник данных.

Результат: владелец бизнеса получает обзор своего бизнеса, динамику и проблемные зоны без доступа к платформенным административным возможностям.

Проверки: typecheck, build, ручная проверка основных сценариев.

### 10. Расширенный рабочий интерфейс

Результат: работник или пользователь с расширенными рабочими правами может поддерживать данные своего направления и видеть только разрешённую аналитику.

Проверки: тесты валидации форм и прав доступа, typecheck, build.

### 11. Ограниченный интерфейс работника

Результат: работник может выполнить только разрешённые действия.

Проверки: тесты запрета лишних capabilities.

### 12. Интерфейс администратора

Добавить управление бизнес-аккаунтами, пользователями, типами аккаунтов, должностями, отделами, базой аккаунтов и аналитической базой. Отдельно предусмотреть смену паролей при ротации сотрудников.

Реализованная часть шага: администратор управляет учётными записями и отдельным server-backed каталогом должностей. У должности задаются название, один из базовых кабинетов `Руководитель`, `Работник`, `Диспетчер` и компактный список вкладок с пояснениями; аккаунт выбирает должность и наследует её название, навигацию и capabilities без индивидуальных галочек. Изменение должности отзывает сессии всех связанных пользователей. Базово поддерживаются должности `Администратор`, `Владелец бизнеса`, `Председатель совета директоров`, `Член совета директоров`, `Генеральный директор`, `Работник` и `Диспетчер`; руководящие должности используют business-owner workspace. `Просмотр аккаунта` показывает полный каталог должностей и актуальные server-backed аккаунты, переиспользуя реальные кабинеты; административные карточки не запускают preview до production impersonation/audit-модели. `Учётные записи` также поддерживает создание логина, сброс пароля и временное отключение входа. В `БД` добавлен server-gated двухшаговый импорт Google Sheets вкладок `Оборудование`, `Инциденты` и `Посетители`: администратор получает предпросмотр и отдельно подтверждает перенос без перезаписи существующих записей и без email/MAX-уведомлений. Выбор business account удалён из UI и клиентского API: backend использует единственный активный бизнес и блокирует неоднозначный импорт при нуле или нескольких активных бизнесах. Одинаковые lifecycle-записи схлопываются внутри файла и получают общий с live-формами business-scoped content key, поэтому повторный импорт, копия книги, параллельные импорты и одновременная диспетчерская отправка не создают дубли.

Результат: администратор может обслуживать структуру платформы без прямого вмешательства в аналитику вне разрешённых действий.

Проверки: тесты административных прав, запретов для неадминистраторов и валидации критичных действий.

### 13. Диспетчерская лента и уведомления

Собрать единый поток событий: новые записи, ожидание подтверждения, отклонения, исправления, напоминания, просрочки и интеграционные ошибки.

Реализованная часть шага: для диспетчерских отправок добавлен первый live-feed contract `GET /api/dispatcher/submissions` через remote API. Endpoint поддерживает фильтры `formId`, `dateFrom`, `dateTo` и возвращает `summary` по количеству регистраций. После успешного `POST /api/dispatcher/submissions` backend отправляет email- и MAX-уведомления по открытию/закрытию инцидента и входу/выходу посетителя в человекочитаемом формате, а оборудование рассылает только после полного batch-сохранения через `POST /api/dispatcher/equipment-report` одним кратким сообщением на все позиции дневного отчёта. Для закрытия инцидента сервер дополнительно подтягивает место из сохранённого открытия, чтобы строка `Место (цех/участок)` попадала в сохранённый payload закрытия и уведомления. Общие адресаты берутся из строк `2–20` Google Sheets колонок email/MAX, дополнительные адресаты механики — из строк `22–25`, электрики — из строк `27–30`; посетительские адресаты берутся из отдельных колонок `Адресаты по посетителям (емейлы)` и `Адресаты по посетителям (МАКС)` строк `2–20`. MAX поддерживает несколько ID в одной ячейке этих строк, спецгруппы добавляются по причине простоя, типу инцидента или тексту закрытия. Это ещё не единая диспетчерская лента всех событий.

Результат: владелец бизнеса, администратор и ответственные работники видят разрешённые рабочие события в одном месте.

Проверки: тесты фильтрации событий по роли, бизнесу, отделу и статусу.

### 14. Контракты интеграций

Подготовить adapter-контракты для 1C, Excel, Google Sheets, Email и MAX без реальных секретов и SDK. Для Excel и Google Sheets отдельно описать настройку форматирования импорта.

Реализованная часть шага: первый Google Sheets reference-source добавлен без SDK и без хранения секретов в git. Backend умеет читать публичный CSV или закрытую таблицу через service account JSON на сервере, ищет значения под колонками `Места (цех/участок)` и `Ответственный за регистрацию` с двоеточием или без него, по умолчанию перечитывает результат при каждом запросе форм и обогащает серверное описание формы `Открытие инцидента`. Этот же источник читает email-адресатов и MAX ID уведомлений из фиксированных строк. Для исторической миграции добавлен отдельный workbook reader exact-вкладок и import-specific parser: он читает неформатированные Google serial даты, сохраняет московское историческое время, строит lifecycle-записи инцидентов/посетителей и выдаёт предупреждения по legacy-расхождениям до подтверждения. Email-рассылка реализована через SMTP-конфиг, MAX-рассылка — через bot token и HTTP API; для Jino можно указать `MAX_CA_CERT_FILE` с доверенным PEM сертификатом Минцифры без отключения TLS, секреты хранятся только в `server/.env` и не коммитятся в git.

Результат: интеграции имеют безопасные границы и могут добавляться по одной без переписывания доменной логики.

Проверки: тесты нормализации входных данных, ошибок импорта и отсутствия логирования приватных payload.

### 15. Backend и постоянное хранение

После стабилизации frontend-прототипа выбрать backend, схему хранения, auth, audit storage и API-контракты. Frontend-only проверки доступа не считать достаточной защитой.

Текущее состояние: backend workspace `server/` хранит пользователей, password credentials, account access, каталог должностей, сессии и dispatcher submissions в MariaDB/MySQL. Admin API создаёт отдельные login identity/access, отклоняет повторный login, сбрасывает пароль, создаёт и редактирует должности; авторизация читает базовый кабинет, navigation items и capabilities из назначенной должности. `/api/admin/access-levels` удалён. Миграция `009_remove_account_access_levels` удалила старые presets, `010_dynamic_account_positions` ввела текущий каталог должностей, а `014_dispatcher_spreadsheet_import_source` добавила уникальный source key для повторяемого импорта. Database API отдаёт список таблиц и строки, update непервичных полей и delete по primary key; import API отдельно валидирует бизнес-данные, серверно выбирает единственный активный business account, схлопывает одинаковые строки по нормализованному содержимому и транзакционно добавляет только отсутствующие dispatcher submissions, используя уникальный business-scoped `dedupe_key` как защиту от гонок. Лимит server/client dispatcher history увеличен до 2000 записей, чтобы первичный импорт 572 строк не вытеснил incident/visitor lifecycle из рабочих представлений. Test/production разделены через `VITE_SMB_APP_ENV`, `SMB_APP_ENV`, `DEV_ACCESS_ENABLED`, отдельные cookie/env/БД; production использует login/password auth и запрещает dev-session/client fallback. Для локального Codex добавлен personal plugin `smb-jino-deploy`: он запускает существующий tracked dual-deploy по SSH, не хранит секреты, требует SSH-ключ и после публикации проверяет HTTP redirect и HTTPS health обеих сред. Полный audit trail, production impersonation/audit-модель и общая аналитическая БД ещё не реализованы.

Миграция `009_remove_account_access_levels` завершает переход к полностью индивидуальным настройкам: она не меняет сохранённые `navigation_items` и capabilities аккаунтов, удаляет все оставшиеся связи и затем удаляет колонку `access_level_id` вместе с таблицей пресетов. Endpoint `/api/admin/access-levels` и связанные frontend/backend-контракты удалены.

Результат: появляется реальная доверенная граница для данных, ролей, подтверждений, истории и интеграций.

Проверки: тесты API-контрактов, авторизации, валидации входа, миграций и audit trail.
