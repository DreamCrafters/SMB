# Качество ОЦ и выбор вагонов

Обязательно читать [laboratory.md](laboratory.md), [refractory.md](refractory.md) и [brands.md](brands.md).

- Для реестра `Огнеупорный цех → Вагоны` хранить необязательные server-owned `Садчик` и `Прессовщик`; строки без этих значений остаются читаемыми и исправляемыми. Раскрывающиеся списки обоих полей строить по текущей полной истории реестра и разрешать ручной ввод, а пустую новую форму заполнять из последней созданной записи. При выборе одного или нескольких вагонов в `Лаборатория → ОЦ → Качество сырцовой продукции` переносить марку, садчика и прессовщика из выбранного вагона с самой поздней датой садки; nullable значения не должны затирать уже введённые поля формы.

- `Журнал контроля качества сырья и соблюдения технологии` держать отдельной группой `ОЦ (Огнеупорный цех)` во вкладках ввода и руководительского просмотра лаборатории. Все перечисленные в форме поля обязательны; измерения хранить текстом, а смену, номер дезинтегратора и адресата рекомендации ограничивать server-owned вариантами. Текущую московскую дату отдавать через manage-only draft endpoint. Списки с возможностью добавления для лаборанта, мастера смены, марок глины и отощителя, номера мешалки и бегунов строить по полной истории самого журнала и сразу дополнять успешно сохранённым значением. Создание, исправление по стабильному `id`, неизменяемая before/after-ревизия и audit выполняются в одной транзакции; draft, списки и `PATCH` недоступны capability просмотра и admin preview. Руководительский `GET` поддерживает период и `name` только по маркам глины и отощителя, а общая таблица сохраняет группированные разделы исходного журнала.

- `Журнал контроля качества сырцовой продукции` держать второй отдельной формой группы `ОЦ` во вкладках ввода и руководительского просмотра лаборатории. Все поля обязательны; дата по умолчанию московская, номер пресса ограничен значениями `1–8`, марка изделия выбирается из общего `Журнала марок` и канонизируется backend-ом до DB-транзакции, а садчик и прессовщик дополняются из полной истории журнала. Вагон выбирать только по стабильному server-owned `id` из реестра `refractory_wagons`: требуется хотя бы один вагон, порядок выбора сохраняется, а номера отображаются через `;`. Реестр наполняет только server-gated журнал `Огнеупорный цех → Вагоны`: сотрудник ОЦ вводит канонически уникальный номер, дату садки и марку из общего `Журнала марок`; создание и исправление по стабильному `id` канонизируют марку до транзакции и сохраняют текущую запись, неизменяемую before/after-ревизию с серверным автором и обязательное audit-событие одной транзакцией. При создании или исправлении контроля сырцовой продукции backend пересчитывает дату контроля сырца для всех затронутых вагонов по их server-owned связям. Жизненный цикл обжига и сортировки строить только из подтверждённых отчётов `Печное отделение`: каждая строка имеет два независимых множественных выбора по стабильным ID — вагоны для обжига и рассортированные вагоны. Backend канонизирует номера, проверяет существование, совпадение марки вагона с маркой строки и отсутствие повторного выбора внутри одного типа события; один вагон разрешён одновременно в обоих типах и в следующих циклах. При подтверждении отчёта его `reportDate` записывать как report-linked событие в той же транзакции, заменяя события логического ключа `firing + дата + смена` при подтверждённой корректировке. Журнал вагонов выводит все даты обжига без ограничения пятью и последнюю дату сортировки; клиент не передаёт и не редактирует эти даты. Для длины, ширины и высоты второе значение автоматически повторяет первое до первой ручной правки второго поля; backend независимо валидирует оба значения. Размеры, вес, механическую прочность и плотность хранить как неотрицательные десятичные строки с поддержкой запятой. Создание, исправление по стабильному `id`, неизменяемая before/after-ревизия и audit выполняются в одной транзакции; руководительский просмотр остаётся read-only и фильтрует наименование только по марке изделия.

- При множественном выборе вагонов в `Журнале контроля качества сырцовой продукции` разрешать только вагоны с одной и той же известной нормализованной маркой: frontend не отмечает несовместимый следующий вагон и показывает понятное предупреждение, а backend повторно проверяет набор до любого изменения журнала или audit. Вагоны без исторической марки не считать отдельной маркой, чтобы legacy-записи оставались доступными.
