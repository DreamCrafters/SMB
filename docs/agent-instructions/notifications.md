# Разрешения и отправка Email/MAX

При изменении настроек аккаунтов/должностей также читать [access.md](access.md). Эти правила содержат специальное исключение для защиты аккаунтов при настройке рассылок.

- Административное разрешение рассылки хранить server-owned по паре `должность + тип сообщения` в `position_notification_permissions`, а персональные каналы — по паре `пользователь + тип сообщения` в `user_notification_settings`. Разрешение не выдаётся конкретному человеку: назначение должности сразу переносит на аккаунт её набор разрешённых рассылок. Вкладка `business.settings` не выдаётся должностям автоматически и включается администратором вручную как обычная рабочая вкладка. Во вложенной вкладке `Учётные записи → Уведомления` администратор выбирает должность и одним флажком `Вкл.` только разрешает ей тип уведомления; при каждом изменении этого разрешения персональные Email/MAX всех аккаунтов должности сбрасываются, а выключенный тип полностью скрывается из их настроек. Контакты остаются личными и редактируются отдельно для каждой учётной записи должности; там же администратор может включить её Email/MAX по каждому разрешённому типу — теми же правилами, что действуют в личной вкладке `Настройки`: канал доступен только при сохранённом контакте и только для разрешённого должности типа, а пользователь по-прежнему меняет свои каналы сам. Защита учётных записей и должностей на настройки рассылок намеренно не распространяется: любой администратор с `platform.manage_users` меняет разрешения и контакты рассылок в том числе у защищённого аккаунта и должности с правами админа. Единственная граница здесь — сама capability, а каждое изменение по-прежнему пишется в audit. Пользователь с вкладкой `Настройки` сам включает Email/MAX только для разрешённых типов и при наличии соответствующего контакта в `app_users`; удаление контакта снимает лишь недоступный персональный канал, но не административное разрешение. Персональные Email/MAX не импортировать из Google Sheets и редактировать только на сайте; экран `Учётные записи` разделять на вкладки `Учётные записи`, `Должности`, `Уведомления`. Клиент не определяет получателей: backend выбирает их по активной должности, статусу аккаунта, разрешению этой должности и персональному каналу. При передаче поручения Совета директоров на проверку отправлять Email/MAX всем возвращённым этой матрицей адресатам без дополнительного скрытого фильтра по должностям. Сбой внешней отправки после commit не должен откатывать сохранённое бизнес-действие и не должен блокировать другой канал; идентификаторы получателей не выводить в логи ошибок.

- Email/MAX-уведомления по открытиям и закрытиям инцидентов, посетителям, отчётам оборудования и выработке отправляются backend-ом только после успешного сохранения и получают адресатов из server-owned `user_notification_settings` с отдельными типами `incidents`, `visitors`, `equipment_reports` и `production_reports`; прежние Google Sheets колонки адресатов для этих сообщений больше не являются production-источником. Сообщение о закрытии инцидента должно быть самодостаточным и после номера показывать в порядке открытия исходные дату/время, место, тип, критичность и описание, затем введённые при закрытии корневые причины и предотвращающие меры, дату/время закрытия и утвердившего; исходные значения backend переносит из сохранённого открытия, а локальный test fallback повторяет то же правило. Формат выработки держать в общем серверном шаблоне Email/MAX для первичной отправки и исправления: служебный `reportMonth` в текст не выводить, заполненные пары марки и факта формовки/сортировки объединять по категории и номеру строки с единицей `т.`; неполные исторические пары не терять и сохранённый payload ради оформления не менять. В сообщении о выработке замеры банок выводить одним блоком `Содержимое банок:` — по строке на банку вида `- Банка N (содержимое), начало дня, по отгрузкам: A; по замерам B, на конец дня C / D` и отдельной строкой `Мастер ЦОШ`; остальные поля блока `Замеры банок` в текст не попадают. Содержимое банки брать из снимка самой сводки, а текущее назначение Лаборатории использовать запасным источником; отсутствующее значение показывать как `—`, а сводку без полей банок оставлять вовсе без этого блока. Отчёт оборудования отправлять одним сообщением на весь дневной пакет через `/api/dispatcher/equipment-report`; одиночный `/api/dispatcher/submissions` для `equipment` не должен рассылать уведомления, чтобы не создавать спам. Исправление отчёта рассылать тем же адресатам и по тем же каналам, что и первичную отправку: тема получает суффикс `— исправлено`, первой строкой идёт пометка о внесённых корректировках, а ниже — полный текст обновлённого отчёта без сокращений. Признак исправления вычислять на backend до сохранения: для `Выработки` — по уже существующей сводке за ту же дату отчёта, для отчёта оборудования — по существующему ключу дедупликации дневного пакета. Формы с идемпотентной вставкой (инциденты, посетители) исправлений не имеют: повтор с той же идентичностью игнорируется, а другое содержимое даёт новую запись. Новые pending-таблицы ОЦ по-прежнему отправлять диспетчерам из строк `2–20` Google Sheets колонок `Адресаты Диспетчеры (емейлы)`/`Адресаты Диспетчеры (МАКС)`, а подтверждённые таблицы — адресатам колонок `Адресаты ОЦ (емейлы)`/`Адресаты ОЦ (МАКС)` только после commit решения. Для backend-среды `SMB_APP_ENV=test` каждое Email- и MAX-сообщение завершать отдельной строкой `Примечание: Тестовое сообщение`; production-сообщения не помечать. SMTP/MAX-секреты держать только в `server/.env`, сбой внешней отправки не должен откатывать сохранённую форму или ревизию ОЦ. Если Jino/Node не доверяет сертификату `platform-api2.max.ru`, добавлять доверенный PEM через `MAX_CA_CERT_FILE`, а не отключать TLS глобально.
