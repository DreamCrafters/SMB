# Поручения Совета директоров

Для рассылок читать [notifications.md](notifications.md), для изменения прав — [access.md](access.md).

- Вкладку `Поручения Совета директоров` считать server-owned реестром с отдельными capabilities просмотра, создания, исполнения и проверки. В настройке неадминистративной должности выдавать не более одного взаимоисключающего варианта этой вкладки: только просмотр; просмотр и создание; либо создание, приёмка и возврат на доработку. Исполнение и отправку на проверку выдаёт источник `board` вкладки `Поручения` (задача 129); с задачи 131 его можно совмещать с созданием или приёмкой. Ограничение реестра активными поручениями (`isBoardAssignmentExecutorOnly`) действует только при исполнении без создания и приёмки; `Поручения мне` запрашивает список с `executionOnly=1`. Backend должен формировать capabilities из выбранного варианта, а не из названия должности; вариант приёмки включает создание поручений. Срок исполнения задавать структурированным расписанием: `daily`/`weekly`/`monthly`/`yearly`/`once`, дата начала и дата окончания; текстовый `due_date` сохранять только как производный снимок для отображения и совместимости. Пользователю только с правом исполнения (без создания и приёмки) backend должен отдавать только наступившие активные поручения со статусом `В работе` или `На доработке`; будущие, переданные на проверку и завершённые поручения не должны быть доступны и через карточку по ID. Просроченное исполнение остаётся активным до передачи на проверку. После приёмки повторяющегося поручения вычислять первую дату расписания после дня приёмки в пределах периода без накопления пропущенных повторов; месячные и годовые повторы привязывать к исходному дню с переносом на последний день короткого месяца. Пользователь с правом исполнения может переводить активное `В работе` или `На доработке` только в `На проверке`, а пользователь с правом приёмки — завершать или возвращать такое поручение. Каждый переход требует комментарий, который добавляется в append-only `board_assignment_comments` вместе с серверным автором, временем и полученным статусом в одной транзакции с изменением поручения и обязательным audit-событием. К живому незавершённому поручению пользователь с capability создания может прикрепить не более пяти PDF по 10 МБ каждый; хранить их в MariaDB/MySQL, проверять расширение, MIME и PDF-сигнатуру на backend, а загрузку и мягкое удаление проводить через authenticated endpoints с обязательным audit-событием. Удалённый из живого поручения файл сохранять для чтения из ранее зафиксированных снимков выполнения; публичные URL и физическое удаление исторического документа не использовать.

- Любой пользователь с capability `business.create_board_assignments` может редактировать все поля любого ещё не завершённого живого поручения независимо от автора; правка требует отдельный комментарий, добавляется в обычную историю комментариев, сохраняет before/after снимки в append-only ревизии и проходит одной транзакцией с audit-событием. Для повторяющегося поручения правка меняет только живую версию текущего и будущих исполнений и не меняет уже принятые периоды. При каждой приёмке до перехода к следующему повтору сохранять отдельный неизменяемый полный снимок выполненного периода со всеми полями, расписанием, датой исполнения и комментариями; историю выполнений читать только из этих снимков, а не восстанавливать из текущего состояния живой строки.

- Задача 131: вкладка `Поручения Совета директоров` (`mode="create"`) — кнопка `Добавить поручение` над реестром со статусами, карточка только для чтения; эта структура — образец для вкладок ГД и Коллегии. Очередь приёмки, приёмка/возврат и правка — в подвкладке вкладки `Поручения` (`mode="control"`).

- Интерфейс `Поручений Совета директоров` строить отдельно под каждый вариант доступа, а не одной универсальной раскладкой: просмотр — спокойный read-only реестр; создание — явный первый шаг постановки поручения; исполнение — во вкладке `Поручения`: строки активных задач в общей таблице и карточка СД (`BoardAssignmentExecutionCard`) с одной прямой кнопкой `Отправить на проверку` и перепоручением, без правки и приёмки; вкладка СД сама не исполняет; приёмка — отдельная очередь ожидающих решения и прямые кнопки `Принять исполнение`/`Вернуть на доработку`. Фильтр живого реестра должен позволять одновременно выбрать несколько статусов; пустой выбор означает все доступные статусы. Не показывать выбор статуса там, где доступные переходы уже однозначно определены ролью и текущим состоянием.

- Перепоручения создаются в существующем реестре гендиректора: одно СД допускает несколько дочерних заданий. Новое назначение требует серверного доступа к исходному СД и полномочий отправки гендиректора; исходное незавершённое СД блокируется в транзакции создания. Историю дочерних заданий может читать пользователь, которому доступно исходное СД. В карточке выполненного периода показывать актуальную историю отдельно от неизменяемого снимка, без создания из снимка. Дочерняя приёмка не меняет статус СД автоматически. Читать также [director-assignments.md](director-assignments.md).

- Текущий журнал и история используют компактный общий набор колонок; расширенный
  набор включается через `Все колонки реестра`. Дополнительные фильтры применяются
  к значениям соответствующих колонок сразу и учитываются счётчиками и PDF.
  Расписание целиком остаётся в дополнительных колонках и карточке.
- `POST /api/board-assignments/export.pdf` печатает выбранные серверные записи
  либо неизменяемые снимки исполнения. Клиент передаёт только источник, формат,
  ID и `expectedUpdatedAt`; текст и права сервер не принимает от клиента.
  Сохранять ограничения исполнителя на будущие и неактивные живые поручения.
  PDF журнала — альбомный A4 с датой, сутью, исполнителем, соисполнителями, сроком
  и статусом; карточка — портретный A4 с полным содержанием и полями подписи.
  Отдельного исполнителя в модели СД нет, поэтому поле не заполнять вымышленным
  именем. В истории использовать ID снимка и его значения, не текущую карточку.
