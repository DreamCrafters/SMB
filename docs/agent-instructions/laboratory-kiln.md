# Журнал печи 2

Обязательно читать [laboratory.md](laboratory.md); при изменении плотности/материалов и расчёта банок — [refractory.md](refractory.md).

- `Журнал печи 2` хранить отдельным append-only server-owned реестром под capability `business.manage_laboratory_results`: один ввод содержит все заданные параметры обжига, обязательный `Производимый материал` сразу после `Времени`, введённые имена мастера смены, обжигальщика и лаборанта, а authenticated session отдельно остаётся автором audit-события. `t в полевой камере`, `Проход ч/з сито 0,5` и `Загрузка печи в ковшах в час` необязательны при создании и исправлении: пустые значения сохранять как `NULL`, не подменять нулём и показывать `—` в обеих историях; остальные поля сохраняют прежнюю обязательность. Материал выбирается из общего `Журнала марок` и канонизируется backend-ом тем же путём, что остальные поля марок; записи, сохранённые до появления поля, читаются без материала и не участвуют в расчёте банок. Если в журнале есть хотя бы одна запись с материалом, форма подставляет материал последней такой записи и оставляет его после успешного сохранения; предыдущее значение берётся только из полной выборки журнала, а не из отфильтрованной истории, и любая ручная правка поля отменяет дальнейшую автоподстановку. Поля `Мастер смены` и `Обжигальщик` остаются редактируемыми, но предлагают отдельные раскрывающиеся списки всех уникальных ранее сохранённых значений соответствующего поля; варианты читать отдельным manage-only endpoint из полной истории, а не из ограниченной или отфильтрованной выдачи журнала, и не открывать руководительскому просмотру или admin preview. После успешного сохранения новое введённое значение должно сразу появляться в списке текущей формы. При первом открытии формы через отдельный manage-only draft endpoint читать последнюю фактически созданную запись из полной истории по `created_at desc, id desc` и один раз подставлять `Дату`, `Мастера смены`, `Обжигальщика`, `Лаборанта`, `Проход ч/з сито 0,5`, `Насыпной вес` и `Загрузку печи в ковшах в час`; для `Времени` подставлять значение той же записи плюс один час с сохранением минут и переходом `23:xx → 00:xx`. Дата и время самой записи не должны менять выбор источника, а ручной ввод любого из этих полей до завершения загрузки нельзя перезаписывать. Draft endpoint не открывать руководительскому просмотру или admin preview. После успешного сохранения значения новой записи сразу становятся источником следующей подстановки, включая расчёт нового `Времени`; остальные параметры очищаются или получают свои обычные значения. Запись и обязательный audit сохранять одной транзакцией. Фильтр по датам и поиску выполнять на backend, а `Средний насыпной вес` рассчитывать по ровно тем строкам, которые backend вернул в текущую отображаемую выборку; frontend только показывает готовое среднее.
