# Админский редактор БД и аудит

Читать [access.md](access.md) и правила всех затронутых бизнес-реестров: общий редактор БД и аудит не обходят их инварианты.

- Админский просмотр и редактирование БД должны оставаться server-gated по capability `platform.manage_analytics_database`: frontend только отображает и отправляет действия через backend API, секреты и приватные payload не выводить в UI-логи или ответы. Каталог БД должен быть статическим allowlist русскоязычных прикладных представлений с безопасными пользовательскими полями; сейчас это пользователи и диспетчерские записи. Доступы и должности менять только через профильные admin-экраны с их полными правилами. Системные, auth-, архивные и append-only исторические разделы не показывать, но их данные не удалять; для текущих представлений запрещены удаление строк и массовая очистка. Запрещено отдавать клиенту `SELECT *`, password hashes, session IDs, dedupe/source keys, сырые dispatcher payload или неизвестные будущие таблицы. Описание редактора строки формирует backend: для диспетчерской записи это поля server-owned определения конкретной формы и понятные варианты выбора, без отображения технических ID/NULL/JSON. Диспетчерская запись показывает номер инцидента отдельной нередактируемой колонкой. Поиск по разделу выполняет backend по всем показанным колонкам представления и ни по одному скрытому полю: статус сравнивается по русской подписи из своего же списка вариантов, дата и отметка времени дополнительно по напечатанному дню, шаблон `like` экранируется, длина запроса ограничена, а счётчик строк и постраничная навигация считаются уже по отфильтрованному набору. Помимо поиска раздел может объявлять server-owned фильтры и сортировки, и клиент рисует только объявленные: диспетчерские записи фильтруются по разделу формы и по периоду даты события, а сортируются по дате события с выбором направления. Дата события приводится к datetime из всех форматов payload, поэтому фильтр и сортировка работают одинаково для `DD.MM.YYYY`, отметок времени, ISO-импорта и старого месячного периода; счётчик строк и постраничная навигация считаются уже по отфильтрованному набору. Строки одной отправки объединять по server-owned ключу группы: дневной отчёт оборудования хранится по записи на единицу, а показывается одной свёрнутой строкой отправки, которая раскрывается и позволяет править каждую единицу отдельно. Формы, которые отправляются по одной, ключа группы не получают. Связующую идентичность записи (`reportDate`/`equipment`, номер закрываемого инцидента, связь выхода посетителя) через общий редактор не менять; изменение показателей оборудования обязано добавлять обычную ревизию полного дневного отчёта, а правка открытия инцидента обязана переносить дату/время, место, тип, критичность и описание в сохранённое закрытие того же номера, чтобы снятый при закрытии снимок не расходился с исправленным открытием. Правка через БД — ремонт уже сохранённой записи, а не новая отправка формы: обязательных пунктов в редакторе диспетчерской записи нет, требующие заполнения правила формы при такой правке не применяются, а пустое значение просто убирает поле из payload. Разбор значений, нормализация дат и чисел, ограничение длины, запрет неизвестных полей и защита связующей идентичности записи остаются в силе и при правке. Правку, отклонённую самими данными (нередактируемая колонка, неверный тип, слишком длинное значение), отдавать как `400` с текстом причины, а не как общий `500`, и показывать эту причину внутри модального редактора: страница под ним не видна, поэтому статус внизу экрана администратор не прочитает. Длинные текстовые колонки раздела показывать целиком с переносом, а не обрезать многоточием. Изменение пользователя дополнительно требует `platform.manage_users`, его статуса — `platform.manage_access`; смена влияющих на доступ статусов отзывает затронутые сессии.

- Журнал действий пользователей хранить на сервере как append-only `user_audit_events`: автора всегда определять из authenticated/dev server session; платформенный отчёт защищать capability `platform.view_audit`, а опциональную вкладку руководителя `business.user_actions` — отдельной capability `business.view_user_actions` с обязательным server-side ограничением событий и списка аккаунтов организационным scope. Клиентские события просмотров принимать только по статическому allowlist вкладок и экранов и повторно сверять с доступами активного аккаунта; для admin preview разрешать только экраны, которые реально доступны через `admin.account_preview`. В журнал включать входы/выходы, отправки форм, изменения данных, административные действия и открытия значимых вкладок/форм; не собирать каждый клик, focus, черновики, пароли, session IDs, токены, секреты или произвольный raw payload. Значения отправленных форм формировать только по server-owned описанию полей. Production-запись бизнес-/административного изменения и обязательного audit-события выполнять через общий `DatabaseTransactionRunner` в одной транзакции; сбой аудита должен откатывать изменение, а email/MAX запускать только после commit. Узкое исключение допустимо только для идемпотентного исторического backfill из tracked DB-миграции: источник должен быть явно зафиксирован, данные и соответствующие audit-события записываться в одной транзакции миграции с явным `system-*` автором, а повторное выполнение не должно создавать дубликаты; интерактивные и последующие импорты всегда используют обычную authenticated/dev session и `DatabaseTransactionRunner`. Отчёт показывает максимум последние три календарных месяца, но это только окно выборки: более старые audit-события и связанные данные не удалять и не очищать автоматически.
