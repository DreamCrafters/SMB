# Аккаунты, должности, сессии и preview

Для preview читать `docs/admin-account-preview.md`. Для контактов, разрешений и каналов рассылок обязательно читать [notifications.md](notifications.md): защита аккаунтов там имеет отдельное исключение. При изменении выдачи capability читать также правила соответствующей рабочей вкладки.

- Временное отключение входа для учётной записи реализовывать через серверный `app_users.status` (`active`/`suspended`), а не через клиентское состояние: endpoint должен требовать capability `platform.manage_access`, при отключении отзывать все текущие сессии пользователя, запрещать отключение собственной активной учётной записи и не восстанавливать `archived` через обычный toggle.

- Удаление учётной записи в admin UI реализовывать как подтверждаемое серверное архивирование, а не физическое удаление исторических строк: установить `app_users.status = archived`, деактивировать все `account_accesses`, отозвать сессии и скрыть аккаунт из активного списка. Запрещать удаление текущей учётной записи.

- Защиту критичных учётных записей хранить в server-owned `app_users.is_admin_protected`, а для аккаунта с должностью, у которой включены права админа, вычислять ту же эффективную защиту по активному `account_accesses`. Только канонический аккаунт с нормализованным логином `admin` может включать или снимать явную защиту у других активных аккаунтов; сам `admin` всегда защищён. Для любого другого управляющего аккаунта backend обязан под блокировкой повторно проверять оба источника защиты и запрещать сброс пароля, смену должности, изменение пользовательских полей через общий редактор БД, включение/отключение входа, архивирование и изменение уведомлений защищённой записи. Capability и навигация сами по себе не дают права обходить защиту; frontend только показывает server-owned результат и отключает недоступные действия.

- Права админа должности хранить отдельно от технического `account_positions.is_protected` в legacy-колонке `account_positions.is_admin_protected`. Только канонический аккаунт с нормализованным логином `admin` может включать или снимать их; для `administrator` они включены постоянно. Права админа добавляют должности только `admin.accounts` и capabilities управления обычными аккаунтами, должностями и уведомлениями; корневые панели `admin.account_preview`, `admin.database`, `admin.user_actions` и соответствующие полномочия не выдавать. Для любого другого администратора backend обязан под блокировкой запрещать изменение названия, рабочих вкладок и порядка должности с правами админа, её удаление и назначение такой должности аккаунту. Frontend только показывает отметку `Права админа` и отражает server-owned ограничения.

- Матрица `Учётные записи → Должности → Доступ по вкладке` доступна только каноническому аккаунту `admin`. Она показывает аккаунты, но изменяет server-owned набор рабочих вкладок их должностей: строки аккаунтов одной должности всегда связаны, персональные overrides не создавать. Индивидуальное и массовое изменение должно одной транзакцией повторно проверять исходного `admin`, блокировать целевые должности, пересчитывать capabilities, синхронизировать `account_accesses`, отзывать затронутые сессии и записывать audit; конфликт блокировок с параллельным назначением должности повторять целиком. Отключать разрешено любую вкладку, включая последнюю: должность без рабочих вкладок — допустимое состояние, её аккаунты сохраняют вход и видят пустую рабочую область.

- Общий порядок пунктов левой панели хранить server-owned как одну полную последовательность всех известных `AccountNavigationItem`. Менять её может только системный администратор через корневую вкладку `admin.navigation` и capability `platform.manage_navigation_order`; делегированным администраторам эту вкладку и capability не выдавать. Каждый аккаунт видит только разрешённое ему подмножество пунктов, отсортированное по общей последовательности. Эта же последовательность определяет стартовый экран: при входе открывается первая доступная аккаунту вкладка левой панели, а не первый пункт жёстко заданного в коде каталога. Автовыбор срабатывает один раз за вход и отменяется любым переходом пользователя. Backend принимает только полный каталог без пропусков и повторов, а при появлении нового пункта добавляет его к сохранённому порядку без потери пользовательской перестановки. Рядом с порядком тот же администратор и та же capability меняют названия разделов: хранится только отличие от названия по умолчанию, пустое значение возвращает разделу исходное имя, длина ограничена, а названия для неизвестных вкладок отклоняются. Переименование server-owned и применяется одинаково в левой панели и в админских списках вкладок, чтобы разделы везде назывались одинаково.

- Админский `Предпросмотр` считать режимом входа в выбранную должность, созданную учётную запись или отдельную рабочую вкладку. Показывать эти варианты тремя подвкладками `Типы аккаунтов`, `Созданные аккаунты` и `Вкладки`; для первых двух использовать server-backed каталоги, чтобы созданный в текущей сессии аккаунт появлялся при следующем открытии панели, а для третьей — единый каталог поддерживаемой рабочей навигации. Переиспользовать единое рабочее пространство, реальную навигацию, формы и guards выданных рабочих вкладок, а не отдельные урезанные mock/preview-копии. Сама вкладка `admin.account_preview` не должна порождать изменяющие `business.*` capabilities: backend разрешает по ней только GET рабочих данных, а POST/PATCH/DELETE по-прежнему требуют реальные capabilities вошедшего аккаунта. В превью смешанной должности исключать `admin.*` и `platform.*`, чтобы режим просмотра не открывал реальные административные действия; карточки без рабочих вкладок показывать, но не открывать до появления production impersonation/audit-модели.

- При создании учётных записей руководитель, диспетчер и работник должны получать отдельные login identity и access. Администратор имеет platform scope, все неадминистративные аккаунты — organization scope. Технические ID и scope-defaults формирует backend, frontend не должен требовать их ручного ввода. Повторный логин при создании отклонять без изменения существующей записи; для смены пароля использовать отдельный reset-flow. Список учётных записей сортировать сначала по server-owned порядку должностей, затем по имени пользователя, чтобы одинаковые должности шли подряд.

- Должность пользователя хранить отдельно от технического `accountType`. Для всех должностей использовать единое рабочее пространство, способное переключаться между выданными вкладками; исторические значения `business_owner`/`worker`/`dispatcher` допустимы только как внутренняя совместимость и для специальных session-правил, но не должны ограничивать навигацию или выбирать отдельный UI. Доступ к вкладкам левого rail хранить в server-issued access как стабильные ID и синхронизировать с server-side capabilities; изменение вкладок или прав админа должно отзывать активные сессии пользователя. В форме должности разрешать выбирать только `business.*`; `admin.accounts` вычислять из server-owned прав админа, а остальные `admin.*` оставлять только системной должности исходного администратора. Наличие `platform.manage_users` или `platform.manage_access` не даёт права включать права админа другой должности.

- Смену должности существующей учётной записи выполнять только через server-gated действие по capability `platform.manage_access`: клиент передаёт `accessId` и ID выбранной должности, а backend берёт `accountType`, вкладки и capabilities только из server-owned каталога должностей, транзакционно преобразует platform/organization scope, отзывает все сессии пользователя и пишет обязательное audit-событие со старой и новой должностью. Запрещать смену должности любого access текущего вошедшего пользователя; в UI применять выбор только отдельной кнопкой сохранения и объяснять, что изменённому пользователю нужно войти заново.

- Должность является server-owned источником названия, `navigation_items`, вычисленных capabilities и единого порядка отображения; аккаунт хранит только ссылку на назначенную должность и наследует её доступы. Порядок администратор меняет полным упорядоченным списком, и backend применяет его к каталогу должностей, аккаунтам, вариантам выбора должности и preview/dev-спискам; новую должность добавлять в конец. В UI `Должности и доступы` ручной кнопки сохранения порядка нет: после перемещения отправлять только итоговый полный список через 5 секунд без новых перемещений, сбрасывая задержку при каждом следующем действии; отмена до отправки должна очищать ожидающее изменение. Фоновое обновление аккаунтов/каталога не должно стирать ожидающий порядок, изменения состава должностей до его сохранения нужно блокировать, а сетевые и серверные ошибки `5xx` — повторять с той же пятисекундной задержкой до успеха, нового перемещения или отмены. Поле базового кабинета в API и UI должности отсутствует. Новая неадминистративная должность получает внутренний совместимый тип только на backend-е, а при редактировании существующей должности её технический тип не меняется. Изменение должности должно отзывать активные сессии всех связанных аккаунтов.

- Любую неадминистративную должность, включая созданную миграцией или другим программным способом, разрешено удалять только при `usageCount = 0`, выключенных правах админа и после явного подтверждения. Происхождение должности и технический флаг `isProtected` не должны запрещать удаление свободной обычной должности; должность администратора, должность с правами админа и назначенные аккаунтам должности не удалять. Проверку выполнять в UI, API и транзакционно в repository; связь `account_accesses.position_code` должна оставаться защищённой внешним ключом `ON DELETE RESTRICT`.

- Любая неадминистративная должность может сочетать любые рабочие вкладки: `Обзор`, `Диспетчерская`, `Работа`, `План выработки`, `Действия пользователей` и `Форма`. Backend обязан отклонять неизвестный или содержащий `admin.*` пользовательский набор, но пустой набор рабочих вкладок допустим для любой должности: должность с правами админа так не получает лишний доступ к бизнес-данным, а обычную должность администратор может полностью закрыть, не удаляя её и её аккаунты. Отключение прав админа у должности без рабочих вкладок разрешено и оставляет её без доступов. Канонический login `admin` отдельно включает права админа для должности; backend производно добавляет только `admin.accounts`, `platform.manage_users` и `platform.manage_access`. Другие администраторы могут менять рабочие вкладки только обычных должностей без этой отметки и не могут назначать аккаунтам должности с правами админа. Системные неадминистративные должности разрешено редактировать по тем же правилам, системного администратора — нет. В форме должности показывать только секцию `Рабочие вкладки`, а отметку `Права админа` — отдельной колонкой общего списка, доступной только исходному `admin`.

- В test-среде экран `Выбор доступа` должен получать актуальный server-backed каталог должностей через dev-only boundary и создавать dev-сессию по выбранной должности с её текущими вкладками/capabilities; не возвращать фиксированный список из четырёх технических типов кабинета. При недоступном backend локальный fallback может показывать только базовые системные должности. В production этот каталог и dev-session endpoint должны оставаться отключёнными.

- Сессии с техническим `accountType = dispatcher` должны автоматически завершаться ежедневно в `07:45` по московскому времени: production backend ограничивает `auth_sessions.expires_at` ближайшей границей, test/dev границы повторяют это поведение, а открытый frontend вызывает штатный logout по server-issued `expiresAt` или по ближайшим `07:45 МСК`. На остальные типы аккаунтов ежедневное ограничение не распространять.
