# Журнал марок и ссылки на марки

При изменении канонизации/слияния проверить затронутые формы и читать их инструкции: [production.md](production.md), [refractory.md](refractory.md), [laboratory.md](laboratory.md).

- Все текущие и будущие поля `Марка изделия`, включая общий админский редактор диспетчерской записи, используют единый server-owned `Журнал марок` в MariaDB/MySQL. Полный каталог создаётся и исправляется только в `Лаборатория → Номенклатура → Марки` под capability `business.manage_laboratory_results`: обязательное поле — `Наименование`, необязательные — `Описание`, `Класс`, `Отрасль применения`, `Норматив (ГОСТ, ТУ)`, `Геометрия Д*Ш*В`, `Al2O3`, `Fe2O3`, `Прочность`. Исправление сохраняет стабильный `id`, before/after-ревизию и обязательное audit-событие в одной транзакции. Миграция `050_product_brand_journal` один раз переносит только имена из прежней Google Sheets номенклатуры; `Вид изделия` не считать классом и не импортировать. После миграции приложение не читает и не изменяет Google Sheets для марок. `/api/production-brands` остаётся read-only списком наименований для всех поисковых селекторов; создавать марки из диспетчерских, огнеупорных и других производственных форм запрещено. Рядом с марками живёт вторая server-owned номенклатура `Сырьё` в собственной таблице, стартовый перечень которой миграция один раз переносит с вкладки `Сырьё` таблицы задач; дальше список накапливается только в системе, а Google Sheets для сырья не читается: та же карточка без `Геометрия Д*Ш*В` и `Прочность`, свой уникальный список наименований, свои before/after-ревизии и audit-события. Сырьё не смешивать с марками и не заводить признаком в `product_brands`: у него другой набор полей и другая область применения. `Наименование продукции` в `ОТК → Журнал верификаций` выбирается из сырья, а не из марок. Удаления и объединения у сырья пока нет — опечатку исправляет правка записи.

- Удаление марки выполнять только в `Лаборатория → Марки` как server-owned архивирование. Если backend находит текущие ссылки, UI обязан запросить другую активную марку, а backend — под общей DB-блокировкой одной транзакцией перенести изменяемые ссылки, архивировать исходную марку и записать audit; без замены используемую марку не удалять. Текущее назначение банки переносить новой append-only записью, а не изменением прежнего назначения. Явно подтверждённое объединение — единственное исключение, при котором строка марки переписывается в текущих диспетчерских и лабораторных записях; неизменяемые ревизии исправлений, ревизии отчётов ОЦ и прежние audit-события не менять. Сохранённые ревизии ОЦ при чтении канонизировать через server-owned цепочку `merged_into_id`, объединяя совпавшие строки выпуска ЦОШ без потери количества; использованием считать как последнюю ревизию каждой смены, так и отдельно действующую последнюю approved-ревизию ЦОШ. Все запросы, которые сначала канонизируют марку или читают её параметры, а затем сохраняют запись, включая назначение банки, обязаны удерживать ту же DB-блокировку до завершения ответа, чтобы после архивирования не появилась новая ссылка на старое имя. Ожидание этой блокировки внутри одного процесса сериализовать до получения соединения из пула, а закрытый HTTP-запрос удалять из очереди до получения соединения. Физически удалять строку `product_brands` запрещено.

- При отправке формы `Выработка`, таблицы огнеупорного цеха или лабораторной формы backend должен через один репозиторий проверить и канонизировать все ссылки на марки по актуальному `Журналу марок`; отсутствующую марку отклонять без сохранения отчёта. Сохранённые отчёты продолжают хранить строковое значение марки как исторический снимок.

- В таблицах огнеупорного цеха все поля `Марка изделия` получать через единый server-gated `Журнал марок`. Один поисковый список доступен в сводке оборудования, выпуске неформованных огнеупоров и печном отделении; сохранённую ранее марку оставлять историческим значением ревизии.
