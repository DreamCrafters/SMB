# Инициативы Коллегии

Проектная основа, решения пользователя и срезы — `docs/collegium-initiatives.md` от
корня проекта; читать её до изменений модуля. Для таблиц — [tables.md](tables.md),
для доступа — [access.md](access.md), для связи с поручениями —
[director-assignments.md](director-assignments.md).

- Вкладка `business.collegium_initiatives` имеет одно иерархическое значение уровня
  `view | participant | secretary | chair`; должность хранит кумулятивный набор
  capability, уровень читается обратно по старшей (`readCollegiumInitiativeAccess`).
  `resolveCapabilitiesForPosition` принимает уровень обязательным полем объекта
  уровней: каждый вызов при правке должности, защите, массовом переключении и
  создании обязан передать сохранённый или выбранный уровень, иначе председатель
  молча понизится. Уровни по коду должности не назначать.
- Карточка — server-owned снимок JSON с отдельными статусом и ревизией. Любая правка
  приходит с ожидаемой ревизией (`where id=? and revision=?` → `409`), пишет
  append-only ревизию (изменённые поля, причина вне черновика, статус) и аудит одной
  транзакцией. Пустое изменение ревизию не создаёт.
- Суммы хранить канонически `1234.50` (ввод с пробелами и запятой), явный `0` —
  заполненное значение. Снимок хранит код и подпись справочника.
- Люди в карточке — только `account:<userId>` действующих аккаунтов; в формах
  предлагать аккаунты с вкладкой инициатив. Поле, хранившее тот же id, при правке
  не перепроверяется, чтобы уход человека не блокировал остальные правки.
- Участник создаёт идею только от своего имени; другого инициатора указывает
  `secretary`+. Черновики видят автор, инициатор, владелец и `secretary`+.
  Участник правит свою или назначенную инициативу в `draft`, `rework`,
  `needs_elaboration`; секретарь — до вынесения в повестку.
- Таблица переходов (`collegiumInitiativeWorkflow.ts`) — единственный источник
  маршрута: сервер под блокировкой проверяет исходный статус, право и ревизию; смена
  статуса пишет ревизию с событием и аудит. Из `on_agenda`/`in_discussion` нельзя
  выйти приостановкой или возвратом — только через повестку, чтобы исход попал в
  протокол. Приостановка запоминает `suspendedFrom`, возобновление возвращает туда.
- Фильтр допуска к Коллегии — одна константа требований (`listCollegiumAdmissionGaps`):
  явный `0` в затратах — заполнено; четыре роли — действующие аккаунты с вкладкой;
  контролёр эффекта не совпадает с исполнителем и владельцем. Карточка показывает
  тот же список, что проверяет сервер.
- Комментарии и замечания не редактируются и не удаляются; меняется только
  отметка «устранено» (вопросы и замечания). Замечания оставляет `secretary`+,
  в том числе при возврате на доработку — каждое отдельным комментарием.
- Вложения: права, статус и лимиты проверять до чтения тела; тип — по сигнатуре
  (DOCX/XLSX по каталогу ZIP без макросов), расширение должно совпадать;
  метаданные и содержимое в разных таблицах; удаление мягкое; скачивание —
  `attachment` с `nosniff`. Файлы в БД учитывает синхронизация production → test:
  пачки вставки ограничены по байтам (`planSnapshotInsertBatches`).
- Заседание хранится одной записью с ревизией (повестка, снимки, проекты решений,
  протокол); блокировки — заседание → инициативы по id → аккаунты. Включение в
  повестку повторно проверяет фильтр допуска и сохраняет снимок карточки
  («версия для заседания»); карточка на повестке не редактируется.
- Решение вопроса — только проект в заседании, инициатива остаётся `in_discussion`.
  Утверждение протокола (`chair`) одной транзакцией применяет все решения к
  инициативам (события `meeting_decision`, замечания доработки, `lastDecision` с
  номером протокола = номером заседания) и запрещает дальнейшие изменения
  заседания, повестки, текста и материалов. Снятие с повестки и отмена заседания
  возвращают инициативы в `ready`.
