# Инициативы Коллегии

Проектная основа, решения пользователя и срезы — `docs/collegium-initiatives.md` от
корня проекта; читать её до изменений модуля. Для таблиц — [tables.md](tables.md),
для доступа — [access.md](access.md), для связи с поручениями —
[director-assignments.md](director-assignments.md).

- Вкладка `business.collegium_initiatives` имеет одно иерархическое значение уровня
  `view | participant | secretary | chair`; должность хранит кумулятивный набор
  capability, уровень читается обратно по старшей (`readCollegiumInitiativeAccess`).
  `resolveCapabilitiesForPosition` принимает уровень обязательным полем объекта
  уровней: каждый вызов при правке должности, защите, массовом переключении и
  создании обязан передать сохранённый или выбранный уровень, иначе председатель
  молча понизится. Уровни по коду должности не назначать.
- Карточка — server-owned снимок JSON с отдельными статусом и ревизией. Любая правка
  приходит с ожидаемой ревизией (`where id=? and revision=?` → `409`), пишет
  append-only ревизию (изменённые поля, причина вне черновика, статус) и аудит одной
  транзакцией. Пустое изменение ревизию не создаёт.
- Суммы хранить канонически `1234.50` (ввод с пробелами и запятой), явный `0` —
  заполненное значение. Снимок хранит код и подпись справочника.
- Справочники (`direction`, `effect_type`, `risk_level`, `site`, `kpi`) правит
  `secretary`+ во вкладке «Настройки» раздела, значимость уровня риска и пороги
  (`collegium_initiative_settings`, одна запись с ревизией) — `chair`. Код значения
  неизменяем, значения не удаляются, только архивируются (`is_active = 0`). Сервер
  отдаёт архивные значения с флагом; форма предлагает только действующие, а
  сохранение принимает архивный код лишь там, где он уже был в сохранённой
  карточке. Группировать по коду, показывать текущую подпись.
- Риски — `{ text, levelCode, levelLabel }`; старые карточки, ревизии и снимки
  повестки нормализует `normalizeCollegiumCard` в каждом читателе репозитория.
  Новые поля карточки добавлять туда же со значением «не заполнено». Изменение
  риска сравнивается по `{ text, levelCode }`, переименование уровня правкой не
  считается. Период эффекта — код из `collegiumEffectPeriods`; старый свободный
  текст сохраняется, только пока его не меняют, и не проходит допуск.
- Экономика ТЗ 11.3 и причины полного паспорта ТЗ 7.2 считает только сервер
  (`collegiumEconomics.ts`) в копейках `bigint`; норматив окупаемости сравнивается
  точно, а не по округлённому значению. Неокупаемая инициатива (чистый эффект ≤ 0
  при разовых затратах) превышает любой норматив.
- Полный паспорт — `card.passport`, сохраняется только `PUT /:id/passport` (свой
  бюджет тела 400 КБ, проверка `Content-Length` до чтения) отдельной ревизией с
  `changedFields: ["passport"]`; правка экспресс-карты переносит паспорт без
  изменений, реестр отдаёт карточки без паспорта. После решения Коллегии паспорт
  правят владелец и `secretary`+. Пробелы паспорта считаются по причинам ТЗ 7.2
  (`listCollegiumPassportGaps`) и блокируют допуск, включение в повестку, первое
  поручение из «Одобрена к пилоту» и решение СД. Ручное значение расчёта хранится
  рядом с расчётным и требует пояснения; ТЗ 7.2 проверяет расчётное.
- Плановые эффекты — `passport.effects`; ID выдаёт сервер, неизвестный ID в
  запросе — `409`. Без описанных эффектов учёт идёт по неявному эффекту `main`
  (`listCollegiumPlannedEffects`). Похожие эффекты ищутся только среди инициатив,
  видимых сохраняющему; без пояснения «не дубль» сохранение — `409`.
- Люди в карточке — только `account:<userId>` действующих аккаунтов; в формах
  предлагать аккаунты с вкладкой инициатив. Поле, хранившее тот же id, при правке
  не перепроверяется, чтобы уход человека не блокировал остальные правки.
- Участник создаёт идею только от своего имени; другого инициатора указывает
  `secretary`+. Пока инициатива ни разу не отправлялась на оценку
  (`workflow.submittedAt`), её видят только автор, инициатор, владелец и
  `secretary`+ — независимо от текущего статуса.
  Участник правит свою или назначенную инициативу в `draft`, `rework`,
  `needs_elaboration`; секретарь — до вынесения в повестку.
- Таблица переходов (`collegiumInitiativeWorkflow.ts`) — единственный источник
  маршрута: сервер под блокировкой проверяет исходный статус, право и ревизию; смена
  статуса пишет ревизию с событием и аудит. Из `on_agenda`/`in_discussion` нельзя
  выйти приостановкой или возвратом — только через повестку, чтобы исход попал в
  протокол. Приостановка запоминает `suspendedFrom`, возобновление возвращает туда.
- Фильтр допуска к Коллегии — одна константа требований (`listCollegiumAdmissionGaps`):
  явный `0` в затратах — заполнено; четыре роли — действующие аккаунты с вкладкой;
  контролёр эффекта не совпадает с исполнителем и владельцем. Карточка показывает
  тот же список, что проверяет сервер.
- Комментарии и замечания не редактируются и не удаляются; меняется только
  отметка «устранено» (вопросы и замечания). Замечания оставляет `secretary`+,
  в том числе при возврате на доработку — каждое отдельным комментарием.
- Вложения: права, статус и лимиты проверять до чтения тела; тип — по сигнатуре
  (DOCX/XLSX по каталогу ZIP без макросов), расширение должно совпадать;
  метаданные и содержимое в разных таблицах; удаление мягкое; скачивание —
  `attachment` с `nosniff`. Файлы в БД учитывает синхронизация production → test:
  пачки вставки ограничены по байтам (`planSnapshotInsertBatches`).
- Заседание хранится одной записью с ревизией (повестка, снимки, проекты решений,
  протокол); блокировки — заседание → инициативы по id → аккаунты. Включение в
  повестку повторно проверяет фильтр допуска и сохраняет снимок карточки
  («версия для заседания»); карточка на повестке не редактируется.
- Решение вопроса — только проект в заседании, инициатива остаётся `in_discussion`.
  Утверждение протокола (`chair`) одной транзакцией применяет все решения к
  инициативам (события `meeting_decision`, замечания доработки, `lastDecision` с
  номером протокола = номером заседания) и запрещает дальнейшие изменения
  заседания, повестки, текста и материалов. Снятие с повестки и отмена заседания
  возвращают инициативы в `ready`.
- Поручения из инициативы создаются только в реестре `collegium`
  (`canLinkInitiative`): `sourceInitiativeId` неизменяем (сравнение через `?? null`,
  у старых поручений поля нет); сервис реестра вызывает порт
  `assignmentLinks.lockForAssignment` до блокировки аккаунтов и
  `recordAssignmentCreated` после создания в той же транзакции — первое поручение
  переводит инициативу из `approved_*` в `in_progress`. Модуль инициатив не пишет в
  таблицы реестра напрямую, а читает связанные поручения через
  `listBySourceInitiative`.
- Эффект подтверждают две подписи разных аккаунтов: текущий контролёр эффекта и
  финансовый верификатор (`workflow.verifiers`, назначает `secretary`+ вместе с
  заменой контролёра). Уровень `chair` сам по себе права подписи не даёт и не
  запрещает. Подписант не был владельцем или исполнителем после допуска и не
  автор факта; подпись привязана к версии факта и к текущему держателю роли.
  `confirm_effect`/`reject_effect` — только подписанты, при двух подписях у каждого
  эффекта, закрытых поручениях и итоговом результате (описание, источник,
  вывод); подтверждение пишет снимок `effectConfirmation.effects`. Плановый и
  подтверждённый эффект во всех отчётах читать только через
  `readCollegiumPlannedKopecks`/`readCollegiumConfirmedKopecks`. Корректировка —
  `reopen_effect` (`chair`, с комментарием), в том числе из «Закрыта»; прежнее
  состояние хранит `effectSnapshot` ревизии. Факты привязаны к плановым эффектам:
  удалить эффект с фактом нельзя.
- Совместный эффект: таблицы `collegium_effect_groups`/`_members` — источник
  уникальности и блокировок (группа → участники блокирующим чтением → инициативы
  по id); в `workflow.effectShares` и `effectFacts` участников — копии доли и
  единственного факта группы, записанные в той же транзакции, с ревизией и
  аудитом каждого участника. Факт по эффекту в группе вносится только для группы;
  доли меняются, пока ни один участник не прошёл проверку эффекта; изменение
  снимает подписи. `main` в группу не входит, эффекты одной группы — не дубли.
- Проект протокола хранит версию повестки (`agendaVersion`), которая растёт при
  изменении реквизитов, повестки и решений; утверждается только проект, совпадающий
  с текущей версией. Длина протокола ограничена так, чтобы JSON помещался в лимит
  тела запроса.
- Файлы до 7 МБ: mysql2 передаёт содержимое в SQL шестнадцатеричной строкой, а
  лимит пакета MariaDB по умолчанию — 16 МБ. Объём владельца считает и мягко
  удалённые файлы. Номера выдаёт один upsert счётчика; блокировка аккаунта при
  записи — только строка `app_users`; deadlock и ожидание блокировки отдаются как
  `409`. Ошибки порта инициатив для реестра поручений — `DirectorAssignmentError`.
- Фильтры реестра (ТЗ 13.2) применяет только сервер (`collegiumRegistry.ts`);
  выгрузки XLSX/PDF строятся из того же отфильтрованного списка видимых
  пользователю инициатив. XLSX пишет собственный `xlsxWriter.ts` без зависимостей;
  печатная карточка и протокол — через общий `pdfRenderer`, проект протокола —
  с водяным знаком «ПРОЕКТ». Связанные поручения для просрочки читаются одним
  запросом `listWithInitiativeLink` (проверка `json_type = 'STRING'`, потому что
  `json_unquote` превращает JSON `null` в строку `'null'`).
- Уведомления модуля (тип рассылки `collegium_initiatives`) не отправляются из
  сервисов: методы принимают исходящую очередь (`CollegiumOutbox`) и кладут в неё
  описания внутри транзакции, HTTP-обработчик отправляет после `sendJson` через
  `deliverCollegiumNotifications`. Получатель — адресат события, сейчас видящий
  инициативы и включивший канал; автор действия исключается; каждое письмо — одному
  адресату; в лог только код `collegium_notifications.delivery_failed`. Новый тип
  рассылки добавлять одновременно в серверный и клиентский каталоги.
- Фоновые напоминания (`collegiumReminders.ts`, раннер в `integrations/`) включает
  `COLLEGIUM_REMINDERS_ENABLED` (по умолчанию только production — копия БД в test
  содержит настоящие контакты). Отправка только в рабочий день по Москве; срок в
  выходной переносится на предыдущий рабочий день; напоминания за 2 и 1 рабочий
  день до срока доработки и даты заседания, «день просрочки» — первый рабочий день
  после срока; эскалация просроченного поручения Коллегии — один раз, в этот день,
  владельцу и всем `chair` (без накопленного хвоста). Ключ доставки включает цикл
  объекта (для доработки — `rework.requestedAt`); аренда и не больше 3 попыток.
  Сроки поручений Коллегии напоминает реестр поручений — здесь не дублировать.
- «Требует моего действия» (`GET /api/collegium-initiatives/attention`, ветка до
  общего разбора пути) строится из тех же правил переходов, что и действия сервера,
  с проверкой независимости подтверждающего эффект; это уведомление в интерфейсе по
  ТЗ 12.1, отдельного центра уведомлений в проекте нет.
- Дашборд и его PDF (`/dashboard`, `/dashboard.pdf`, ветки до общего разбора пути)
  считает только сервер, `buildCollegiumDashboard`, по видимым пользователю
  инициативам; суммы — в копейках без `Number`. Новые показатели добавлять туда же,
  а не во frontend.
