# Общие правила лаборатории

Для конкретного журнала читать его файл из таблицы в `AGENTS.md`; для таблиц — [tables.md](tables.md), для марок — [brands.md](brands.md).

- Истории всех текущих и будущих лабораторных журналов в рабочей вкладке лаборанта должны открывать исправление по клику на назначенную идентифицирующую колонку. Исправление выполняет только backend по стабильному server-owned `id`: текущая запись обновляется, а неизменяемые before/after-снимки с автором активной сессии и обязательное audit-событие сохраняются одной транзакцией. Руководительская вкладка и admin preview остаются read-only.

- Лаборатория является одной назначаемой должности вкладкой `business.laboratory_results` с capability `business.manage_laboratory_results`, а не отдельным техническим `accountType`. Системная должность `Лаборант` получает только эту вкладку; production login создаётся через обычный admin-flow учётных записей. Разделы результатов испытаний `Входящий контроль` и `Контроль готовой продукции` скрыты из корневого ряда вкладки: насыпной вес банок считается по журналу печи 2, поэтому лаборант их больше не заполняет. Код разделов сохранён и включается обратно списком `visibleControlSections` в `src/LaboratoryResults.tsx`; сохранённые результаты и их протоколы остаются доступны через `business.laboratory_review` и API. В корневом ряду остаются соседние кнопки `Банки` и `Номенклатура` с вложенными `Марки` и `Сырьё`, группа `ЦЗЛ` с журналами `Журнал печи 2`, `Регистрация проб` и `Химические анализы`, соседняя группа `ОТК` с журналом `Пробы неформованной продукции`, а также группа `ОЦ` с журналами качества сырья и соблюдения технологии и качества сырцовой продукции. Полный каталог поддерживаемых показателей с ГОСТ и виды готовой продукции читать только backend-ом из вкладки Google Sheets `Лаборатория`; frontend не хранит fallback-список, не принимает произвольные показатели и всегда показывает все поддерживаемые поля. Во входящем контроле `Объект испытаний` является свободным текстовым полем и не проверяется по Google Sheets; один отчёт содержит одну или несколько проб с собственными номером пробы или идентификатором транспорта и хотя бы одним показателем у каждой. Цель испытаний и примечание к протоколу обязательны в обоих разделах; цель по умолчанию можно отредактировать перед отправкой. Для готовой продукции конкретную марку дополнительно проверять и канонизировать через общий `Журнал марок`; внешние Google API-чтения матрицы завершать до DB-транзакции. Автора результата испытаний всегда брать из `ServerUserProfile.displayName`; клиентское значение автора игнорировать. Результат и обязательное audit-событие сохранять одной транзакцией, историю не перезаписывать. Печатный протокол формировать защищённым backend PDF-endpoint: постоянную шапку держать в server-owned шаблоне, условные строки определять отметками профиля сырья/готовой продукции из матрицы, свободный объект входящего контроля сопоставлять с профилем нормализованным вхождением, а при сохранении фиксировать снимок показателей и ГОСТов внутри payload результата. Для legacy-записей без снимка разрешён fallback к текущей матрице.

- Просмотр лаборатории для руководства держать отдельной назначаемой вкладкой `business.laboratory_review` с capability `business.view_laboratory_results`. Она read-only: backend разрешает по этой capability только профильные `GET`, включая шесть лабораторных журналов (`rotary-kiln-2-journal`, `sample-registration-journal`, `chemical-analysis-journal`, `unshaped-product-sample-journal`, `raw-material-quality-journal`, `green-product-quality-journal`), и защищённые PDF-протоколы; любые `POST`, `PATCH`, form-only endpoint, банки и остальные лабораторные действия требуют `business.manage_laboratory_results`. Вкладка не содержит форм ввода. Таблицы журналов разноформатные, поэтому вкладка не сводит их в одну таблицу: корневой ряд содержит `Все испытания` и группы `ЦЗЛ`, `ОТК` и `ОЦ`, а внутри каждой группы открывается по одной кнопке на журнал; в режиме `Все испытания` подходящие журналы выводятся отдельными таблицами одна за другой со своим заголовком в порядке кнопок. Остальные фильтры — период по профильной дате и поиск по наименованию номенклатуры; их кнопки включают соответствующие поля и при выключении очищают значения. Журнал выводится, только если поддерживает все включённые фильтры: наименование есть у результатов, регистрации проб, химических анализов, проб неформованной продукции и обоих журналов ОЦ. Неподходящие журналы не скрывать молча: перечислять их с причиной в примечании. Состав кнопок, видимых журналов и причины считать в `src/services/laboratoryReviewJournals.ts`, а не в разметке. Backend-поиск `name` обязан экранировать `%`, `_` и `\`: у результатов искать одновременно по объекту и марке, у регистрации проб и химических анализов — только по `sample_name`, у проб неформованной продукции — только по `product_name`, у журнала качества сырья ОЦ — только по `clay_brand` и `temper_brand`, а у журнала качества сырцовой продукции — только по `product_brand`, чтобы фильтр не срабатывал на остальные поля. Общий `query` и точные `material`/`brand` остаются фильтрами рабочей вкладки. Общие форматы таблиц держать в `src/LaboratoryResultsTable.tsx` и `src/LaboratoryJournalTables.tsx`. Термин `Выходящий контроль` используется только в этой вкладке и означает тот же раздел `finished_product`, что и `Контроль готовой продукции` у лаборанта.
