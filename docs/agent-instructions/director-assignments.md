# Поручения гендиректора и кадровый справочник

Читать также `docs/director-assignments.md` от корня проекта и инструкции
`access.md`, `tables.md`, `ui.md`. Для импорта — `google-sheets.md`.

- Это отдельный реестр от поручений Совета директоров; общие статусы и расписания
  переиспользуются, данные и полномочия не смешиваются.
- Режим вкладки (`send` / `receive` / `both`) хранить в capabilities должности и менять
  только через штатную настройку доступов. Не привязывать отправку к имени или
  коду `general_director`; импорт не назначает эту вкладку и её режимы.
  `both` сохраняет управление и явное `business.execute_director_assignments`;
  исполнение по-прежнему требует собственное наступившее поручение. Не расширять
  прежний `send` автоматически.
- Новые назначения и правки выбирают только активные аккаунты организации по
  стабильному `account:<userId>`. Кадровые ID backend отклоняет и не предлагает
  в списке. Старые поручения сохраняют явные кадровые связи; исполнение требует
  действующий аккаунт, имена не являются связью. Блокировать адресата при записи.
  Импорт истории не читает `Сотрудники` и не создаёт кадры, аккаунты или права;
  исходные имена остаются историческими полями для ручного уточнения назначения.
- В совместном режиме отдельно показывать `Мои поручения` и отправку/контроль.
  Собственные назначения определять на сервере по текущему userId; не фильтровать
  их списком разрешённых действий (он исключает будущие сроки и проверку).
  Типовой предпросмотр прав не меняет личность получателя; `account:<accessId>`
  использует личность выбранного аккаунта с отдельным авторством администратора в аудите.
- Видимость для ответственного не ограничивать проверкой исполнения: показывать
  все свои незавершённые назначения, в том числе будущие, на проверке и требующие
  уточнения. Читать действующую связь с аккаунтом; выполнение отдельно проверяет
  состояние, срок и полноту данных. Завершённую историю этим не открывать.
- Метку связи ответственного с аккаунтом вычислять на сервере по текущей связи,
  а не по ФИО или сохранённому снимку `responsible`. Связь не означает наличие
  доступа к разделу. Снимки истории не помечать текущим состоянием аккаунта.
- Приёмка сохраняет полный неизменяемый снимок до продвижения расписания.
  Изменение расписания не открывает принятые периоды повторно. PDF из снимков
  физически не удалять. Ревизия, изменение и аудит выполняются одной транзакцией.
- Прямое завершение ГД разрешено ответственному исполнителю своего наступившего
  поручения и пользователю с режимом отправки/контроля. Не требовать предварительной
  проверки; сохранять обязательный комментарий, ревизию, снимок и аудит. Повторное
  завершение закрытой записи запрещать. Права брать из capabilities и текущей связи
  аккаунта, не из названия должности; правила приёмки СД этим не расширять.
- В импорте сохранять исходные поля и завершённость. Неполные/неоднозначные
  значения помечать для уточнения, не подбирать аккаунт по фамилии. Повторяющиеся
  исходные номера не объединять без проверки даты и содержания.

- Связь `sourceBoardAssignmentId` после создания неизменяема, включая переходы из/в пустую связь. Для нового связанного поручения проверять доступ к незавершённому СД под блокировкой; последующие действия дочернего поручения продолжают собственный цикл независимо от закрытия СД. Исторические события перепоручений сохраняют ответственного на момент события по append-only ревизиям.

- Напоминания о сроке выполняются на backend независимо от входа пользователя.
  Использовать текущий срок, реальные связи участников и разрешённые личные
  каналы типа `general_director_assignments`. Состояние доставки хранить в БД
  отдельно по поручению, сроку, интервалу, пользователю и каналу; не подменять
  его памятью процесса и не включать рассылку автоматически в копии test-БД.

- У завершённого поручения единственный текущий статус `Завершено`: сервер снимает
  `needsClarification` в новом снимке и нормализует прежние завершённые записи при
  чтении, не перезаписывая append-only историю. Предупреждения и исходные поля
  импорта сохранять. Следующий активный повтор не считать исправленным только
  из-за приёмки предыдущего периода.
