# Локальный запуск, Jino и среды

Также читать `docs/local-server-run.md`; для тестов на Jino — [tests.md](tests.md), для 1С — [warehouse-1c.md](warehouse-1c.md), для test/dev-входа — [access.md](access.md).

- Перед локальным запуском Vite проверять слушатели `5173`/`5174` и не оставлять несколько frontend-процессов одного checkout. Если внешний браузер показывает старое поведение или частично потерянные стили при актуальных файлах сервера, сначала сравнить реально отданные CSS/JS через `curl`, затем проверить страницу на чистом origin/временном порту с принудительной пересборкой; исправление на новом origin означает устаревшую вкладку/HMR-состояние, после диагностики нужно остановить лишний процесс и вернуться к одному стандартному адресу `http://127.0.0.1:5173/`.

- В remote/server-PC/VPS режиме открывать в сеть только backend API; MariaDB/MySQL держать доступной только локально для backend или по явно разрешённому IP, не публиковать порт `3306` наружу без отдельного осознанного решения.

- Test и production считать двумя средами одного кода, а не двумя расходящимися приложениями: текущий Jino-вариант деплоит оба домена из одной ветки, frontend собирается два раза через `npm run build:web:test` и `npm run build:web:production`, а backend runtime остаётся раздельным по доменам из-за разных `server/.env`, `DATABASE_URL`, cookie name и БД. В production всегда `SMB_APP_ENV=production`, `VITE_SMB_APP_ENV=production`, `DEV_ACCESS_ENABLED=false`; dev-session endpoints, role-picker и клиентские `sessionStorage`/`localStorage` auth/data fallback не должны работать как production-auth или production-хранение.

- Полную синхронизацию production → test считать отдельной разрушительной test-only операцией: backend требует `SMB_APP_ENV=test`, capability `platform.manage_analytics_database`, явный `PRODUCTION_SNAPSHOT_ENABLED=true`, отдельный read-only `PRODUCTION_DATABASE_URL`, точное совпадение `PRODUCTION_SNAPSHOT_TARGET_DATABASE` с test `DATABASE_URL` и разные имена source/target БД. До мутации проверять равенство таблиц, DDL и `schema_migrations`, отсутствие триггеров и InnoDB для всех таблиц. Все записи test-backend, migration/auth CLI и синхронизацию сериализовать общим server-wide advisory lock; строки всех таблиц заменять внутри одной транзакции без `DROP/CREATE`, чтобы ошибка или остановка процесса сохраняла прежнее состояние test. Production использовать только для чтения, test полностью заменять снимком данных, а в том же коммите оставлять `auth_sessions` пустой. Никогда не показывать URL/пароль production в UI, ответах или логах и не включать endpoint/UI в production.

- Текущий Jino deployment-контекст: production домен `smb.aonmou.ru` использует `~/domains/smb.aonmou.ru/app`, test домен `test.smb.aonmou.ru` использует `~/domains/test.smb.aonmou.ru/app`; собранная статика публикуется в соответствующий `public_html`, Node entrypoint домена — соответствующий `app.js`.

- При deploy с `SMB_RUN_TESTS=true` запускать тесты на managed Jino только последовательно через `npm run test:jino` с `--test-concurrency=1`: обычный параллельный `node --test` превышает лимит процессов/потоков и может зависнуть после `pthread_create: Resource temporarily unavailable`. В одном test-файле держать не больше одного Vite SSR-сервера на каждый build env: закрытые графы модулей удерживают нативную память до завершения процесса и managed Jino убивает такой файл через `SIGKILL`. Если env один на весь файл — поднимать сервер один раз на уровне модуля; если сценарии действительно меняют env — кэшировать серверы в `Map` по env и выставлять нужные `VITE_*` явно внутри хелпера создания, а не полагаться на ambient-окружение и `.env`. Закрывать все накопленные серверы в `test.after`, а не в `finally` каждого сценария. Сценарии, которым нужен один и тот же env, обязаны получать один и тот же сервер, даже если различаются props. Не отключать тесты ради обхода лимита; локальный `npm test` оставлять параллельным.

- Первичную настройку SSH-ключа на Jino выполнять через панель `Управление → Консоль` или файловый менеджер: добавить публичный ключ в `~/.ssh/authorized_keys`, сохранить существующие ключи и выставить права `0700` на `.ssh` и `0600` на `authorized_keys`. Из локальных deploy-инструментов открывать отдельную панель хостинга `https://cp-hosting.jino.ru/`, а не общий корень `https://cp.jino.ru/`; после выбора контейнера пользователь переходит в `Управление → Консоль`. До проверки входа убедиться, что услуга `Поддержка SSH` подключена, в `Управление → SSH-подключение` задан SSH-пароль и текущий IP разрешён. Если verbose SSH-лог содержит `Server accepts key`, а затем `Connection closed`, ключ уже установлен и повторять `ssh-copy-id`/добавление ключа не нужно: исправлять услугу, SSH-пароль или IP allowlist. Не считать `ssh-copy-id` надёжным основным путём для managed hosting Jino.

- Успешно опубликованную версию каждой Jino-среды фиксировать только после копирования frontend и restart backend в `${domainRoot}/.smb-deploy-state` с `branch`, `commit` и UTC-временем; status bar и другие deploy-инструменты должны сравнивать этот marker с commit выбранной ветки в `origin`, а не считать один только HEAD серверного checkout доказательством успешной публикации.

- Для обоих Jino-доменов принудительный HTTP → HTTPS redirect выполнять на Apache/Jino boundary через tracked `public/.htaccess` с `X-Forwarded-Protocol`; deploy обязан публиковать dotfiles. Не разрешать HTTP-origin в production CORS и не снимать `Secure` с auth-cookie: отсутствие redirect нужно исправлять на уровне хостинга и проверять для `/`, `/health` и `/api/*`.

- Рабочая Jino managed DB — `j53403317_bot1` с пользователем `j53403317_robot`; при запуске backend на Jino использовать DB host `localhost`, а если TCP-подключение даёт `user@127.0.0.1` access denied, подключать backend через `socketPath=/var/lib/mysql/mysql.sock` в `DATABASE_URL`; при внешней проверке/VPS использовать `mysql.584e7697571.hosting.myjino.ru` с IP allowlist.
