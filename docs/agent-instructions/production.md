# Выработка, планы и фильтры марок

Для марок читать [brands.md](brands.md); для замеров/весов банок — [refractory.md](refractory.md); для отправки отчёта — [notifications.md](notifications.md).

- В руководительской `Диспетчерская → Выработка` фильтры по марке в `Формовке` и `Сортировке` должны независимо и нормализованно искать внутри `facts`, исключать из найденной строки несовпавшие марки и пересчитывать суточный/месячный факт только по оставшимся маркам. План категории по маркам не распределять, поэтому при активном фильтре марочные строки не показывают план и отклонение.

- Диспетчерская форма `Выработка` является server-owned дневной сводкой: дата отчёта обязательна, дополнительно нужен хотя бы один показатель. Диспетчер вводит суточный факт, марку изделия, суточные показатели фракций грануляции, а в блоке `Замеры банок` — до четырёх замеров каждой банки, `Засыпали`, `Отгрузили` и обязательного мастера ЦОШ. Первый замер каждой банки обязателен; план, поля месяца, отклонения, расход, среднее, плотность, объём и расчётные веса вручную не вводятся. Таблицу строить по образцу `Банки!G1:K17`; frontend показывает live-пересчёт, но backend при сохранении заново читает текущие назначения банок, последние плотности `Журнала печи 2` и справочник объёма, удаляет присланные производные `jarStart*`/`jarEnd*`/`jarShipmentStart*`/`jarShipmentEnd*` и сохраняет собственный снимок расчёта. Начало дня по замерам брать из конца сводки предыдущей календарной даты, начало дня по отгрузкам — из конца последней сводки строго раньше даты отчёта, конец дня по обоим весам — из текущего серверного расчёта. Подтверждённую сводку ЦОШ выбранной даты разрешено использовать только для начального заполнения legacy-отчёта; в обычной диспетчерской форме поля редактируемы, а в admin preview остаются read-only. История `Диспетчерская → Выработка → Замеры банок` обязана создавать строку при наличии любого из четырёх итоговых значений, показывать начало, конец и расход отдельно `По замерам` и `По отгрузкам` и считать оба набора итогов; отчёты только с `jarShipment*` не скрывать. В полной таблице выбранной даты показывать сохранённое в диспетчерской ревизии содержимое банки, а для legacy-записи без снимка — текущее назначение Лаборатории. Формовка, сортировка, неформованная продукция и шамот используют один общий `Журнал марок` и одинаковые горизонтальные таблицы: диспетчер добавляет марочные столбцы с полем `Факт за сутки`, каждый столбец обязан ссылаться на марку общей номенклатуры, а повтор марки внутри категории запрещён. Любой заполненный факт категории, включая `0`, требует выбранную марку, а выбранная марка требует заполненный факт; это правило проверяют frontend перед отправкой и backend. Для фактов формовки и сортировки первое `mousedown` по ещё неактивному полю должно отменять только нативный повторный шаг и синхронно ставить фокус; повторные нажатия по уже активному полю оставлять браузеру для обычной установки каретки. Переход между этими полями не должен запускать React-обновление или замену DOM-узла на `blur`. Новую марку диспетчер не создаёт: добавление и исправление доступны только в `Лаборатория → Марки`; backend канонизирует метку при отправке по текущему журналу. Месячные факт и план категории рассчитывать с первого дня календарного месяца по дату отчёта включительно по последней записи каждого дня, отклонение считать как месячный факт минус месячный план, расход банки — как начало дня минус конец дня. Для live-расчётов backend возвращает накопительный план выбранной даты и сохранённый месячный факт только предыдущих дней; frontend добавляет сумму текущих черновых фактов марочных столбцов, показывает read-only `План за месяц`, `Факт за месяц` и `Отклонение` и не добавляет эти значения в payload. Поэтому сохранённый факт редактируемого дня не учитывается дважды. Старые отчёты с одиночными полями формовки и сортировки продолжают читаться и при следующей отправке преобразуются в динамические марочные поля. Аналитика сохраняет накопленный месячный факт каждой динамической марки, не распределяя по маркам план категории. Расчётные таблицы формирует backend, а frontend только фильтрует и отображает строки; исключение — арифметическое добавление ещё не сохранённого суточного факта к server-owned месячному факту предыдущих дней. Локальный test fallback повторяет доступные расчёты лишь для явно тестового режима.

- В субботу и воскресенье диспетчер может отправить `Выработку` с заполненной `Сортировкой` и без факта `Формовки`: незавершённую строку Формовки с выбранной маркой, но пустым фактом считать пустой и не сохранять. Факт Формовки без марки по-прежнему отклонять; на рабочих днях и для остальных категорий требование полной пары `марка + факт` не ослаблять. Одинаковое правило применять в UI, локальном test fallback и backend.

- Месячный план выработки вводит должность `Экономист` через отдельную server-gated вкладку `business.production_plan` с capability `business.manage_production_plan`. На месяц предусмотрены четыре независимых положительных плана с точностью не более двух знаков после запятой: формовка, сортировка, неформованная продукция/контейнеры и цех обжига шамота; интерфейс принимает точку и запятую, нормализуя запятую в точку. План категории является суммой по всем её маркам и не хранится на уровне марки. Экономист свободно выбирает месяц и любую категорию, а каждая категория сохраняется отдельно и сразу обновляет составную месячную сводку. Категория имеет собственный подтверждаемый календарь: экономист выбирает пресет `Все дни` или `Только рабочие` (понедельник–пятница), а затем может вручную добавить или убрать любую дату. Для каждой категории до предпоследнего подтверждённого дня ставить целое значение `ceil(месячный план категории / количество дней)`, на последний — точный остаток с точностью до сотых без отрицательного значения. Каждое сохранение категории блокирует последний снимок выбранного месяца, добавляет составную append-only ревизию и обязательное audit-событие в одной транзакции, чтобы параллельные изменения разных категорий не затирали друг друга; frontend не рассчитывает и не хранит сохранённый итоговый план самостоятельно. Диспетчерская форма читает с сервера дневные и накопительные планы вместе с сохранённым месячным фактом предыдущих дней, показывает `Не задан` для категории без плана и не добавляет расчётные значения в payload.

- В форме `Выработка` выбор `Дата отчёта` обязан загружать последнюю сохранённую сводку этого дня и восстанавливать обычные и динамические поля. Повторная отправка сохраняет новую append-only версию, а текущие таблицы и месячные расчёты используют последнюю версию дня.
