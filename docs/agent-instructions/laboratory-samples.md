# Регистрация проб, химанализы и ОТК

Обязательно читать [laboratory.md](laboratory.md); для отображения истории — [tables.md](tables.md).

- Химанализы в журналах ОТК показывать как актуальные server-owned данные, связанные по стабильному ID пробы: формованная продукция и верификации получают анализ исходной регистрации, неформованная продукция — собственный анализ с запасным переходом к исходной регистрации. Выбирать последний анализ по `sequence_id` целиком, не дополнять его пустые показатели из более старых анализов; ручные legacy-показатели исходной регистрации использовать только при отсутствии связанного анализа. По совпадению видимого кода пробы анализы не привязывать. В ответах дочерних журналов держать показатели во вложенном `chemicalAnalysis`, чтобы партия, влажность и примечание анализа не затирали одноимённые поля самой пробы; форму ввода пробы и ревизии её собственных полей результатами анализа не расширять.

- В `ЦЗЛ → Химические анализы` свободную пробу выбирать единым server-backed combobox `Код лабораторной пробы`, без отдельного поискового поля. Ввод кода, номера или наименования передавать backend как `sampleQuery`, подсказки подписывать источником и датами и поддерживать клавиатурный выбор стрелками и Enter с закрытием по Escape, а после явного выбора хранить только стабильную ссылку `sampleSource + sampleId`. Ручная правка текста обязана сбрасывать прежний выбор; исправляемая связанная проба остаётся доступной как сохранённая опция, даже если обновление подсказок завершилось ошибкой.

- В `ЦЗЛ → Регистрация проб` синхронизация дат всегда односторонняя: ручное изменение `Даты отбора` устанавливает такую же `Дату регистрации`, но отдельное изменение `Даты регистрации` никогда не меняет `Дату отбора`. Каждое последующее изменение даты отбора снова синхронизирует дату регистрации.

- В `ЦЗЛ → Регистрация проб` поле `Лаборант (отбор проб)` по умолчанию получает имя вошедшего пользователя, а после успешной первичной регистрации введённое значение становится значением следующих записей текущей frontend-сессии того же профиля; исправление истории этот выбор не меняет. Поле остаётся редактируемым и предлагает все уникальные ранее сохранённые значения из полной истории через manage-only form endpoint; новое сохранённое значение сразу добавлять в список.

- В `ЦЗЛ → Химические анализы` поле `Лаборант` следует тому же сессионному правилу: имя профиля является начальным значением, а непустое значение успешно созданного анализа переносится в следующие новые записи текущей frontend-сессии и сохраняется при переходе между вкладками; исправление истории этот выбор не меняет. Раскрывающийся список строить по уникальным значениям полной server-owned истории через manage-only form endpoint и сразу дополнять сохранённым значением.

- В `ЦЗЛ → Регистрация проб` поле `Место отбора пробы` по умолчанию получает место из последней созданной server-owned записи. Поздний ответ со списком мест не должен затирать уже начатый ручной ввод или более новое успешно сохранённое место. После первичной регистрации сохранённое место становится значением следующей записи; после исправления заново определять последнюю запись по server-owned истории, чтобы исправление самой свежей регистрации обновляло автоподстановку, а исправление более старой — нет.

- `Регистрация проб` хранить отдельным server-owned реестром под capability `business.manage_laboratory_results`; в форме вводить реквизиты регистрации и отбора и необязательное `Водопоглощение`, сохраняя заполненное значение текстом для поддержки десятичной запятой, а пустое — как `NULL` с отображением `—`. Следующий `№ пробы` предлагать backend-ом по максимальному начальному числу из полной истории, а `Код лабораторной пробы` начинать с заготовки `YY.номер`: год брать из текущей московской календарной даты, номер — из первого числового фрагмента `№ пробы`; оба поля оставлять редактируемыми, автоматически синхронизировать код с номером только до первой ручной правки кода и после сохранения запрашивать новую заготовку. Историю сортировать backend-ом по начальному числовому значению `№ пробы` по убыванию. Первичную регистрацию сохранять как новую запись, а исправление существующей выполнять только с capability управления лабораторией по её стабильному server-owned `id`, не разрывая связи с химическими анализами; текущие значения, неизменяемую before/after-ревизию с серверным автором и обязательное audit-событие записывать одной транзакцией. В управленческой вкладке коды оставлять read-only. Form-only endpoint и исправление не открывать capability просмотра или admin preview. Исторические записи до появления показателя читать без него и показывать `—`; остальные химические значения не возвращать в форму регистрации. `Химические анализы` хранить отдельным append-only реестром: лаборант выбирает свободную пробу из `Регистрации проб` или `Проб неформованной продукции`, frontend передаёт дискриминированную server-owned ссылку `sampleSource` + `sampleId`, а backend до сохранения и повторно под блокировкой строки внутри транзакции проверяет существование пробы и отсутствие другого анализа. Уже связанная проба не показывается в раскрывающемся списке; одинаковые код, номер и наименование различать по источнику и датам. Список должен иметь server-side поиск по обоим полным журналам, чтобы оставались доступны записи старше окна последних 500 проб. В химическом анализе обязательна только ссылка на пробу; номер лабораторного анализа, номер партии, дата анализа, лаборант, все химические показатели и примечания необязательны. Следующий номер лабораторного анализа считать backend-ом по полной истории как максимальное полностью числовое сохранённое значение плюс один и отдавать через manage-only form endpoint; frontend подставляет его при открытии и после сохранения, но оставляет поле редактируемым и не перезаписывает ручной ввод. Пустой номер партии сохранять как `NULL`, не включать в audit-значения отправки и показывать в истории как `—`; при исправлении audit должен явно показывать переход между значением и `—`. Химические показатели сохранять текстом для поддержки запятых и квалификаторов вроде `< 0,1`; для `Al2O3`, `Fe2O3`, `SiO2`, `CaO2`, `P2O5` и `ппп` backend принимает только неотрицательное число с необязательным квалификатором верхней границы `<`, `<=` или `≤` и отклоняет создание или исправление, если сумма числовых значений больше 100. Запись, связь с пробой, синхронизацию read-only номера у неформованной пробы и обязательный audit сохранять одной транзакцией. Исправление анализа может переносить его только на другую свободную пробу и обязано очистить прежнюю связь; номер в регистрации получать из связанного анализа, а у неформованной пробы синхронизировать server-owned `chemical_analysis_number`. Один источник допускает не более одного нового анализа: репозиторий блокирует строку пробы, а таблица `laboratory_chemical_analysis_sample_claims` атомарно резервирует пару `sampleSource` + `sampleId`. Миграция заполняет резерв последним анализом каждой старой пробы и не удаляет допустимую ранее историю дублей. Печатный `Протокол отбора проб` строить только backend-ом из повторно отфильтрованных позиций журнала, не принимать строки с клиента и сохранять бумажную структуру бланка: портретный A4 с полями партии и подписей, кодом лабораторной пробы, номером анализа, отдельными колонками Al₂O₃/Fe₂O₃/ппп, пустой колонкой огнеупорности и остальными сохранёнными показателями в `Прочих показателях`. История регистрации показывает последний по `sequence_id` связанный анализ, а прежние вручную введённые химические значения использует только как legacy fallback при отсутствии связанного анализа. Журналы фильтровать на backend по профильной дате и текстовому поиску.

- `Пробы неформованной продукции` хранить отдельным server-owned журналом под capability `business.manage_laboratory_results`. Следующий номер, код вида `YY.номер`, текущую московскую дату и последнего отборщика отдавать через manage-only draft endpoint; год брать из текущей московской календарной даты, а номер — из первого числового фрагмента `№ пробы`. Ручной ввод не перезаписывать поздним ответом. Наименование продукции выбирать из общего `Журнала марок` и канонизировать backend-ом до DB-транзакции. Одно поле `№ партии` соответствует дублирующейся колонке исходной задачи. Обязательны все пользовательские поля кроме примечания; массу партии, влажность, зерновой состав и огнеупорность хранить текстом. `№ хим. анализа` не принимать от клиента: поле остаётся nullable/read-only и заполняется либо очищается только при сохранении связи из журнала химических анализов в той же транзакции. Значение `Пригодность` ограничить `Да`/`Нет`/`м.б.` и раскрашивать всю строку зелёным/красным/жёлтым. Исправление выполнять по стабильному `id` с before/after-ревизией и audit в одной транзакции; form-only endpoint и `PATCH` недоступны capability просмотра и admin preview. Руководительский GET поддерживает период по дате пробы и `name` только по наименованию продукции.

- В форме `ЦЗЛ → Химические анализы` постоянное предупреждение о сумме контролируемых показателей не более 100 показывать заметным красным полужирным текстом; точная проверка создания и исправления остаётся server-owned.

При изменении выбора химанализов для журналов ОТК дополнительно запускать `python3 scripts/check-laboratory-sample-chemical-analysis.py` после `npm install`. Проверка исполняет фактические repository SELECT на изолированных SQLite-данных, покрывает выбор анализа и связи и не подключается к рабочей БД; она не заменяет проверку специфики MariaDB.
