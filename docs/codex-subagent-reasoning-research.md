# Можно ли жёстко выбирать reasoning кастомного субагента Codex

Проверено 14 июля 2026 года по актуальному Codex Manual, локальной конфигурации Codex и фактическому контракту инструмента субагентов в этой сессии.

## Короткий вывод

**Создать три кастомных субагента с `high`, `xhigh` и `ultra` — да.** В локальной конфигурации они уже созданы.

**Жёстко выбрать один из них из текущего AI-вызова `collaboration.spawn_agent` — нет.** В доступном контракте этого инструмента отсутствует параметр `agent_type`, `profile`, `model` или `model_reasoning_effort`. Передача имени в `task_name` лишь именует задачу и не выбирает конфигурацию агента.

Поэтому требование вида «всегда запускай именно `reasoning_xhigh`» в `AGENTS.md` в этой среде является пожеланием оркестратору, а не технической гарантией. Сейчас гарантировать уровень reasoning для дочернего агента из этого чата нельзя.

## Что именно возможно

| Возможность | Ответ | Основание |
| --- | --- | --- |
| Создать отдельные TOML-агенты | Да | Codex поддерживает файлы в `~/.codex/agents/` и `.codex/agents/`. |
| Задать каждому `model_reasoning_effort` | Да | Это официально поддерживаемое поле custom agent file. |
| Использовать `high`, `xhigh`, `ultra` с локальным `gpt-5.6-sol` | Да | Текущий локальный каталог модели объявляет поддержку всех трёх уровней. |
| Попросить Codex CLI/IDE/app использовать агента по имени | Да | Официальный manual говорит, что `name` используется при запуске и обращении к агенту. |
| Передать имя профиля как обязательный параметр текущего `collaboration.spawn_agent` | Нет | Такого поля нет в фактической схеме доступного инструмента. |
| Гарантировать через один только `AGENTS.md`, что дочерний поток получил нужный reasoning | Нет | Инструкция влияет на решение модели, но не добавляет отсутствующий параметр в API запуска. |

## 1. Создание custom agent TOML

Официальная документация разрешает личные агенты в `~/.codex/agents/` и проектные агенты в `.codex/agents/`. Обязательны `name`, `description`, `developer_instructions`; среди поддерживаемых дополнительных полей прямо указаны `model` и `model_reasoning_effort`. Источником идентичности является поле `name`, совпадение с именем файла необязательно. См. [официальный раздел Custom agents](https://learn.chatgpt.com/docs/agent-configuration/subagents.md#custom-agents).

В текущей локальной конфигурации уже существуют:

- `~/.codex/agents/reasoning-high.toml` с `name = "reasoning_high"` и effort `high`;
- `~/.codex/agents/reasoning-xhigh.toml` с `name = "reasoning_xhigh"` и effort `xhigh`;
- `~/.codex/agents/reasoning-ultra.toml` с `name = "reasoning_ultra"` и effort `ultra`.

Во всех трёх указан `model = "gpt-5.6-sol"`. Локальный каталог Codex 0.144.2 (`~/.codex/models_cache.json`) перечисляет для этой модели `high`, `xhigh`, `max` и `ultra`, поэтому сами три конфигурации совместимы с текущим каталогом модели. В общем случае `ultra` работает только с моделью и тарифом, где этот уровень доступен; это ограничение отдельно зафиксировано в [официальном разделе Reasoning effort](https://learn.chatgpt.com/docs/agent-configuration/subagents.md#reasoning-effort-model_reasoning_effort).

## 2. Выбор в Codex CLI, IDE и app

Официальный manual сообщает, что локальные клиенты Codex загружают custom agent files как конфигурационные слои для порождённых сессий, а поле `name` используется Codex «when spawning or referring to this agent». Следовательно, в обычном локальном Codex пользователь может явно попросить: «используй `reasoning_xhigh`». Активный тип агента следует проверять в интерфейсе активности либо через событие `SubagentStart.agent_type`; наличие такого поля описано в [официальной документации hooks](https://learn.chatgpt.com/docs/hooks.md#subagentstart).

Однако документация не обещает отдельный универсальный UI-переключатель custom agent для каждой поверхности. Основной задокументированный путь — обращение к агенту по имени и проверка реально запущенного типа. Поэтому после создания или изменения TOML разумно начинать новую локальную сессию и проверять отображаемый `agent_type`, прежде чем считать выбор подтверждённым.

## 3. Возможность текущего AI-агента жёстко выбрать профиль

Фактическая схема доступного здесь вызова `collaboration.spawn_agent` содержит только:

```text
task_name
message
fork_turns
```

Она не содержит `agent_type`, `profile`, `model` или `model_reasoning_effort`. Поле `task_name` по описанию создаёт каноническое имя подзадачи (`/root/...`), а не выбирает custom agent.

Runtime-проверка уже запущенных в этой среде дочерних потоков подтверждает ограничение: их `thread_spawn.agent_role` равен `null`, а фактический `turn_context` показывает effort `high`, несмотря на наличие трёх TOML-файлов. Приватное содержимое журналов в этот отчёт не переносилось.

Итог для текущего чата: AI может сформулировать задачу «работай как `reasoning_xhigh`», но не может технически зафиксировать `model_reasoning_effort = "xhigh"` при вызове имеющегося инструмента. Это разные гарантии.

## Практическое решение

Если нужна именно строгая гарантия, необходим один из вариантов:

1. Использовать поверхность Codex, чей spawn-инструмент принимает `agent_type`, и передавать `reasoning_high`, `reasoning_xhigh` или `reasoning_ultra` явно.
2. Расширить текущий `collaboration.spawn_agent` параметром выбора custom agent/profile и проверять возвращённый `agent_type`.
3. Пока такого параметра нет, изменить `AGENTS.md`: требовать профильный запуск **при технической доступности выбора**, а иначе разрешать обычного субагента с явной фиксацией ограничения.

Один только TOML или текст в `AGENTS.md` не исправляет отсутствие параметра выбора в runtime-инструменте.
