# Предпросмотр администратора

В разделе есть три независимых способа выбора:

- `Типы аккаунтов` — рабочие права должности, без смены личности.
- `Созданные аккаунты` — конкретный активный аккаунт: его имя, все вкладки,
  объединённые права должностей, личные поручения, настройки и доступные действия.
- `Вкладки` — права одной рабочей вкладки; можно выбрать её уровень.

## Конкретный аккаунт

Клиент передаёт `X-SMB-Account-Preview: account:<accessId>`. Перед открытием
запрашивается серверный профиль; локальный fallback не используется. Сервер
на каждом запросе заново проверяет настоящую сессию администратора, доступ к
предпросмотру, root-признак администратора и наличие активного целевого аккаунта.
Для dev используется только доверенная dev-root проверка; совпадение ID с
production-root полномочий не даёт. Неактивная, неизвестная или недопустимая
цель отклоняется, без возврата к действиям настоящего администратора.

Эффективные `userId`, `accountId`, имя, scope, capabilities и навигация берутся
из текущей серверной записи выбранного аккаунта. Поручения и персональные
настройки читаются для этого человека. Права администратора к правам цели не
добавляются. Это распространяется и на административные вкладки, если они есть
у цели, и на настройку таблиц. После переходов по вкладкам режим сохраняется.

Пароль цели не требуется; новая auth-сессия цели не создаётся. Настоящая
администраторская сессия остаётся обязательной и определяет срок авторизации.
Кнопка выхода из предпросмотра возвращает к администратору, не разлогинивая его.
Обновление страницы сбрасывает предпросмотр. Счётчики и очереди личных отчётов
перезагружаются при смене аккаунта, старые ответы отменяются.

## Действия и журнал

Действия настоящие: сохраняют данные и запускают обычные уведомления. Авторство
прикладных данных соответствует эффективному аккаунту; в журнале действий
обязательно указывается настоящий администратор и целевой аккаунт.
`accountPreviewContext` изолирует контекст каждого HTTP-запроса через
`AsyncLocalStorage`; общий `auditRepository.record` сохраняет администратора в
полях автора, добавляет пометку в описание и ID/имя цели в детали. Это работает
и для записей из доменных сервисов. Параллельные запросы не делят этот контекст;
обычные запросы и фоновые задачи вне него сохраняют прежнее авторство.

Аудит остаётся в существующих транзакциях: его ошибка откатывает изменение.
Секреты и пароль аккаунта в контекст или журнал не копируются. Жёлтая плашка
показывает режим и поясняет, что действия сохраняются от имени выбранного лица.

## Тип должности и отдельная вкладка

Прежние адреса `position:<id>`, `navigation:<item>` и
`navigation:<item>:<level>` сохраняются. Они меняют рабочие права, но не личность
вошедшего администратора. Поэтому `Мои поручения` здесь принадлежат администратору.
Смешанные административные вкладки в типовом рабочем предпросмотре скрываются.
Для проверки данных конкретного человека нужно выбрать `Созданные аккаунты`.

Заголовок содержит только адрес цели; клиентские capabilities не принимаются.
Он добавляется общей функцией `buildDevAccessHeaders`, очищается при выходе
из режима и при запуске приложения. Нельзя хранить действующий просмотр
только в заголовке без соответствующего состояния интерфейса.
