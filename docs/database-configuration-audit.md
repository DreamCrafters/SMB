# Аудит хардкода конкретных аккаунтов

Дата: 23.09.2026. Первичный аудит выполнен по коду `89c15d5`, выводы уточнены по прямому пояснению пользователя после `7bf5ad0`.

## Уточнённое правило

Проверки прав и общая логика авторизации в коде допустимы: `canManage || canExecute`, проверка capability, роли или режима, проверка принадлежности поручения текущему пользователю по ID из БД и authenticated session.

Запрещён хардкод **конкретных аккаунтов**: специальные права, действия, адресаты или исключения по фиксированному userId/accountId, логину, email или ФИО. Назначения конкретным аккаунтам и признаки их полномочий должны храниться в БД. Код проверяет полученные полномочия и применяет общие правила.

Первичная трактовка была чрезмерно широкой. Требование переносить в БД все матрицы capabilities, переходы состояний, справочники и числовые константы из него не следует. Предыдущие 24 группы — инвентаризация источников значений, **не 24 подтверждённых нарушения уточнённого правила**. Автоматическая очередь массового переноса отменена. Более узкие существующие требования проекта к хранению бизнес-данных и отдельным справочникам сохраняются.

## Задача 119

Замечание к `canManage || canExecute` снято. В [directorAssignmentsService.ts](../server/src/domain/directorAssignmentsService.ts) `directorAssignmentPermissions` читает capabilities профиля, а `canExecuteDirectorAssignment` проверяет текущую связь ответственного с аккаунтом из БД, активность и доступность поручения. В ветке завершения нет фиксированного логина, ФИО, userId или accountId конкретного исполнителя, гендиректора или помощника.

Сравнение `assignment.responsible?.userId === profile.userId` допустимо: обе стороны получены из данных, а не из зашитого идентификатора. Форма [DirectorAssignments.tsx](../src/DirectorAssignments.tsx) отображает серверные права. Отдельная DB-настройка действия завершения по этому уточнению не требуется. Транзакционная запись комментария, ревизии, снимка и аудита сохраняется без изменений.

## Что не считать хардкодом аккаунта

- Идентификаторы capabilities, названия режимов и общая композиция прав, применяемая одинаково к любому аккаунту с соответствующим доступом.
- Код роли `general_director` сам по себе не является идентификатором конкретного человека. Проверка такой роли оценивается по профильным правилам модуля, а не автоматически объявляется персональным исключением. Например, для доступа к вкладке ГД проект по-прежнему требует capabilities вместо вывода из названия должности.
- ID пользователя, прочитанный из поручения/БД/сессии, сравнение текущего и целевого пользователя для запрета самоизменения, проверка принадлежности записи.
- Синтетические аккаунты в изолированных тестовых фикстурах. Ветка специального разрешения по такому ID в работающем приложении — другой случай, описанный выше.
- Имя подписанта в шаблоне PDF — фиксированный реквизит, но само по себе не привязка прав к аккаунту. Его изменение требует отдельной задачи на реквизиты, а не изменения авторизации.
- Алгоритмы, технические ограничения, CSS и обычные подписи интерфейса. Их наличие в исходниках не нарушает уточнённый запрет.
